# 14: Backup & restore

**Goal:** if the main server burns down, you follow one tested procedure and everything comes back: dashboard, settings, secrets, apps, databases and uploaded files. Restoring a single database is two clicks. Backups are on by default as soon as a destination exists, and the dashboard warns until one does.

Per-resource backup chores (database dumps here, volume backups there), a control plane whose own state is an afterthought and no "replace this dead server" path make recovery hard. launchroom avoids that: all intent lives in one database, all runtime objects are labelled, and launchroomd rebuilds servers from desired state. So **only state that can't be recreated is backed up**.

User guides on the site: [Backups](https://launchroom.vantezzen.io/docs/databases/backups), [Restore and disaster recovery](https://launchroom.vantezzen.io/docs/databases/restore-and-disaster-recovery), [Point-in-time recovery](https://launchroom.vantezzen.io/docs/databases/point-in-time-recovery), [Cloudflare R2](https://launchroom.vantezzen.io/docs/databases/backups-cloudflare-r2), [Hetzner Object Storage](https://launchroom.vantezzen.io/docs/databases/backups-hetzner).

## 1. What needs backing up (and what doesn't)

| Data | Recreatable? | Backed up as |
|---|---|---|
| Control-plane DB (teams, projects, services, variables, revisions, deployments, servers…) | No | Logical `pg_dump`, encrypted |
| Control-plane keys (`APP_KEY`, `LAUNCHROOM_KEK`, signing key) and `.env` | No (without them encrypted values are garbage, and daemons won't trust a new key) | Part of the control-plane backup, additionally sealed to the **recovery passphrase** |
| Database services (Postgres, MySQL, Redis, MongoDB, ClickHouse) | No | Engine-native logical dumps (RDB for Redis, a native BACKUP for ClickHouse), streamed |
| App volumes (uploads, SQLite files, anything mounted) | No | File-level snapshots |
| Headscale state | Mostly (nodes can re-register) | Included in the control-plane backup, so the mesh recovers without re-registering |
| Registry images | **Yes**: rebuildable from git at the recorded commit, and base images re-pullable | Optional. Recommended: put Zot's storage on S3 (§9.11), which makes the registry itself durable |
| Containers, networks, Caddy config, NodeStates | Yes, from the DB | Not backed up |
| Certificates | Yes (re-issued) | Not backed up (with shared certificate storage they survive anyway) |
| Build cache, logs, metrics | Yes / not critical | Not backed up |

## 2. Engine: restic

launchroom builds on **restic** (BSD-2) instead of its own backup format. It provides:
- client-side **encryption** (the S3 provider sees nothing);
- **deduplication** and incremental snapshots (volumes back up fast after the first run; repeated dumps dedupe well);
- snapshot **tags** and retention policies (`forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6`);
- **integrity checks** (`restic check`);
- native support for S3-compatible backends (AWS, Cloudflare R2, Backblaze B2, Hetzner Object Storage, MinIO, Wasabi…);
- a single static binary.

restic is bundled in the launchroomd image at a pinned, checksum-verified version, and launchroomd runs it with argv only, never a shell, with streams piped in-process. A separate backup system image was rejected: it is one more image to pin and pull, and with restic in launchroomd the stream from `docker exec` goes straight into restic's stdin (§9.1).

- **Database dumps**: an exec through the Engine API runs the engine's dump tool in the DB container (argv generated by launchroomd per engine), and stdout is streamed to `restic backup --stdin --stdin-filename <engine file>`. Nothing is staged on local disk, so a full disk doesn't break backups. Both exit codes are checked: a failed dump fails the backup even if restic succeeded (a valid tiny archive of a failed dump is a common bug in other tools).
- **Volumes** (services that are not databases): a helper container that is created but never started mounts the named volume **read-only**, and the Engine API's archive endpoint streams the volume as a tar into `restic backup --stdin --stdin-filename volume.tar`. restic's content-defined chunking still deduplicates unchanged files between runs. A per-volume setting chooses "live" (default, uploads-style data) or "pause" (the service's containers are paused until the tar is read, for SQLite files or anything written in place). Database volumes are never file-copied while running; they use dumps. Details in §9.12.
- **Control plane**: the dashboard itself (a queued job on the control plane, not launchroomd; §9.1) streams `pg_dump` of its database into `restic backup --stdin`, seals the key bundle (`APP_KEY`, KEK, signing and registry keys, the `.env` secrets, Headscale's state) to the recovery key ([§4](#4-the-recovery-kit)) and stores it as a second snapshot of the same run (§9.6).

Tags on every snapshot: `instance:<id>`, `kind:{control-plane|database|volume|base_backup|wal}`, `team`, `project`, `environment`, `service`, `server`. Database snapshots also carry `engine:<engine>` and `reason:<reason>`; volume snapshots `volume:<vol id>` and `reason:<reason>`; control-plane snapshots `run:<bkr id>`, `part:{database|keys}` and `reason:<reason>`. Restore UIs are built from `restic snapshots --json` filtered by tags, so a fresh dashboard can see every backup in a repository with no DB of its own.

## 3. Destinations & schedules

- **Backup destinations** (team-level; one instance-level destination for the control plane): S3-compatible endpoint, bucket, prefix, credentials (envelope-encrypted, sealed to launchroomd per task), plus the restic repository password (generated, stored encrypted, included in the recovery kit). The dashboard offers S3 destinations only. Details in §9.2.
- **Endpoint check.** The endpoint is validated with the `SafeHttpClient` rules ([09](09-security.md) R5: https, public addresses only, no credentials or path).
  - An **instance-owner-only**, audited per-destination override allows a LAN or mesh endpoint and plain http. Team admins can't set it, and can keep an existing override only on the endpoint it was granted for.
  - Even with the override, loopback, link-local and cloud-metadata, unspecified and multicast addresses and the control plane's own compose services (`postgres`, `valkey`, `reverb`, `dashboard`, …, `*.internal`, `*.localhost`) are refused.
  - restic, not launchroom's HTTP client, connects, so the check runs before saving and again before every dashboard-side restic run.
- **Test destination** opens the repository (initialising it on first use: the write test) and lists its snapshots (the read test). The test runs restic in the dashboard container after the same guard, so for owner-approved private destinations the control plane connects to the LAN host (the reason the override is owner-only).
- **Defaults once a destination is configured**:

| What | Schedule | Retention |
|---|---|---|
| Control plane | every 6 h, plus before every upgrade | 7 daily, 4 weekly, 6 monthly |
| Database services (production) | daily at a staggered time | 7 daily, 4 weekly, 3 monthly |
| Database services (other persistent envs) | daily | 7 daily |
| Volumes | daily | 7 daily, 4 weekly |
| Preview environments | none | not backed up |

  Schedules are editable per service (5-field cron, retention, on/off).
- **Automatic safety snapshots** (to the default destination; skipped without one) before risky operations:
  - control-plane upgrade (`pre_upgrade`, [11](11-installation-and-dev.md) §4.1);
  - "restore into this service" (`pre_restore`, §9.5);
  - deleting anything that holds data: a **final backup** (dump or volume snapshot) is taken before an environment, project, preview or service with backups configured is torn down, and the deletion waits for it (§9.13).
- **Maintenance**: retention `forget` per schedule and one `prune` per repository per day (§9.3). launchroomd also supports `check` with a read subset as a `backup_maintenance` operation.
- **Verification**: a weekly automatic test restore of each database and volume into a throwaway container, followed by engine checks (table and row counts, `pg_amcheck`, `CHECK TABLE`, `redis-check-rdb`, a full read of volume tars), shown as "Last verified 2 days ago" (§10.4). An unverified backup is a hope, not a backup.

Visibility: every database and volume shows "last successful backup N hours ago" on its canvas node (a warning badge if stale or failing) and in its Backups tab. Failures raise alerts (§10.6). Settings → Backups lists all destinations, schedules, sizes, failures and the recovery kit status.

## 4. The recovery kit

Backups are useless without the keys, and keys inside the backup are useless without something outside it. So:

- The instance owner sets a **recovery passphrase** and downloads a **recovery kit**: a text file with the destination endpoint, bucket, prefix, region, S3 credentials and the restic repository password (§9.6). Setting or rotating the passphrase, or moving the control-plane repository, requires a new kit.
- The control-plane snapshot contains `APP_KEY`, `LAUNCHROOM_KEK`, the signing key and Headscale's keys sealed to a key derived from the passphrase (Argon2id, `crypto_box_seal`). An attacker with S3 access and the repository password still can't decrypt app secrets without the passphrase.
- Instance owners see a banner until they confirm the kit was saved. Rotating the passphrase re-seals the key bundle in the next snapshot.

## 5. Restore flows

These flows bring data back after a loss. A planned move of a running server, including the dashboard's own, is not a restore: it copies the live data with nothing lost and needs no backup destination (§13).

### 5.1 Restore a database or volume (dashboard running)

Service → Backups → pick a snapshot (time, size, origin) → choose:
- **Restore as a new service** (default, safe): creates `postgres-restored-2026-10-17` (or, for a service with volumes, a copy of it with the same settings, variables and volume paths) in the same environment, restores into it, and lets you inspect it. You can then **swap** (§9.16): in that environment the services connected to the original are connected to the restored service, the original's domains and own connections move to it, and the original is retired, all as staged changes (type-to-confirm; Deploy applies them, Discard undoes them).
- **Restore into this service** (destructive, type-to-confirm): takes a safety snapshot first, stops dependents, restores (drop and recreate the DB from the dump, or restore files into the volume), then restarts. Volumes: the service itself is stopped while its volume is replaced and starts again afterwards (§9.12). Databases: the services connected to it in that environment are stopped first and start again afterwards, also when the restore fails (§9.5).

Downloading a backup and restoring into another environment are not implemented; see the [roadmap backlog](12-roadmap.md#backlog).

### 5.2 Main server died (full disaster recovery)

```
1. New server, Docker installed.
2. curl -fsSL https://launchroom.vantezzen.io/install | sh -s -- --restore
   → asks for the S3 destination + repo password (or reads the recovery kit file) + recovery passphrase
   → restores the newest control-plane run (or --snapshot): DB, keys, .env, Headscale state (§9.6)
   → starts the stack. The new local launchroomd enrolls as a fresh server.
3. Dashboard opens in "Recovery mode" with a checklist:
   a. "The previous control-plane server <old-name> is unreachable. Replace it with this server?" → yes
      → the new server inherits the old one's roles and labels, and the old server is marked replaced (its keys are revoked)
   b. DNS: "Point dash.example.com and *.apps.example.com to <new IP>" (or update the edge list), with live checks
   c. Workloads that lived on the old server are re-placed here (and on other runtime servers if allowed)
   d. Stateful services that lived on the old server are restored from their latest backups
      → restore tasks run in parallel → dependent apps start after them
   e. Images: pulled from the registry if its storage was on S3; otherwise launchroom rebuilds each active
      deployment from its recorded commit SHA (build inputs are in the revision, so the result is equivalent)
4. Other servers: their launchroomd keeps running the whole time. If the control-plane URL stayed the same, they
   reconnect automatically (same signing key). Otherwise each needs one change: set LR_CONTROL_PLANE_URL in
   launchroomd/.env there and run `docker compose up -d` in that folder.
```

`install.sh --restore` enrolls the new server's launchroomd with `launchroom:servers:bootstrap-local --force --recovery`, which keeps the dead control-plane server in the restored database (no longer marked control plane) and switches the dashboard into recovery mode. `/recovery` is the checklist (steps a–e plus "other servers reconnected"), and step a is the "Replace server" flow of §5.3 with the dead control-plane server as the old one (§9.15).

Recommendation shown during setup: use a **stable hostname** for the dashboard (`dash.example.com`, not an IP), so recovery only needs a DNS change and every launchroomd reconnects by itself.

### 5.3 Any other server died

The same as steps 3c–3e, through Servers → (dead server) → **Replace server**: pick a replacement (an existing server or a newly enrolled one). Stateless workloads have usually already been re-placed automatically ([02](02-architecture.md) §6). Stateful ones are restored from their latest backups. See §9.14.

**Replace vs move.** Replace is for a server that is gone: data comes from the latest backups, so writes after them are lost. A server that still runs is moved instead (Servers → server → **Move to another server**, §13.2): its databases and volumes are copied live, each stopped only for its own copy.

### 5.4 Recovery objectives (defaults)

| Scenario | Data loss (RPO) | Time to recover (RTO, rough) |
|---|---|---|
| Single DB restore | ≤ 24 h (≤ 1 h with an hourly schedule) | minutes, depending on size |
| Main server lost | control plane ≤ 6 h; DBs per schedule | ~15–30 min plus DB restore time plus DNS TTL |
| Non-main server lost | per schedule for its stateful services; none for stateless | stateless: automatic within ~2 min; stateful: minutes after confirming |

With point-in-time recovery on (Postgres 15+, §10) a database's RPO drops to about a minute: WAL is archived continuously and any second inside the window (7 days by default) can be restored.

## 6. Reuse: preview cloning

The same snapshot machinery powers the "Clone from another database" preview strategy ([06](06-variables-environments.md) §5, §5.1):
- The user picks a **source database** (any database service they can access in the project, typically staging; production needs an admin toggle with a PII warning).
- The clone restores the source's **latest successful backup** (no load on the source DB). A source without one is refused ("Back it up first").
- **Size guard**: the picker shows each candidate's last dump size. A per-team limit (`teams.settings.previewCloneLimitMb`, default 1024 MB compressed) blocks cloning larger databases into previews, and the user is told why. The guard compares the latest run's `size_bytes`.
- Optional **sanitize command** (runs after restore, before the apps deploy), recommended whenever the source is production. It is an argv run once in the **database's image** on the preview network with the database's env (for example `psql -c "…"`). Commands that need the app image (`php artisan db:anonymize`) belong in a preview-targeted release command.
- The clone is a `restore_runs` row with mode `new_service` whose target is the preview's own (new) database instance, advanced by the normal tick (`AdvanceRestores`, launchroomd `restore` task pinned to the database's server).

## 7. Tasks, drivers and data

- Task types: `backup` (`{kind, target, destination, tags}`), `restore` (`{snapshot, target, mode}`), `backup_maintenance` (`forget` / `prune` / `check`), `backup_snapshots` (`{destination, tags}` → `restic snapshots --json`), `verify_restore` (§10.4). All specs are typed; argv is built by launchroomd, never from user strings ([03](03-daemon-protocol.md) §7).
- **launchroomd owns the executed argv per engine**, built from the engine enum, never from spec strings. Credentials come from the workload's sealed env in its verified NodeState and are passed as exec env (never argv, so they don't show in `ps`). The dashboard's engine driver methods ([04](04-build-and-deploy.md) §10) are descriptive.
- Control-plane DB tables are listed in [07](07-data-model.md) (`backup_destinations`, `backup_schedules`, `backup_runs`, `restore_runs`, …). Snapshots are not mirrored into the DB; `restic snapshots --json` is the source of truth, cached briefly.
- Restic repository passwords and S3 credentials are envelope-encrypted, sealed to launchroomd for each task, and never logged.
- Load: schedules are staggered (hash of the instance id → minute offset), at most one heavy backup task runs per server at a time, and throwaway containers run with a lower CPU weight.

## 9. Implementation

### 9.1 Who runs restic

| What | Where | Why |
|---|---|---|
| Database backup / restore | launchroomd on the server that runs the database (task pinned to it) | the dump runs inside the DB container via the Engine API exec stream and goes straight into restic's stdin |
| Snapshot listing, retention (`forget`, `prune`, `check`) of team repositories | launchroomd (the database's server, else any online server of the team) | the repository credentials reach servers only sealed per task |
| Control-plane backup, "test destination", `launchroom:restore` | the dashboard container (queued job / console) | the dashboard owns its database and key files; works before any server is enrolled; `install --restore` has no launchroomd yet |

restic is pinned at **0.19.1** (SHA-256 per architecture) in the launchroomd image (`/usr/local/bin/restic`, `LR_RESTIC_BINARY` overrides; in dev it sits next to the launchroomd binary) and in the dashboard image, which also ships the **Postgres 18** client tools from the PGDG apt repository (signing key pinned by fingerprint). Process execution in the dashboard is confined to `App\Services\Backups\Process` (argv only, credentials via env, masked output, only used from jobs and console commands; enforced by arch tests, [10](10-codebase-conventions.md) §2.2 rule 8).

### 9.2 Destinations

- `backup_destinations`: S3 only in the UI; `team_id` null = the single instance (control-plane) destination, managed by instance owners only. Team destinations need `backups.manage` (owner/admin).
- Endpoint grammar = launchroomd's `S3Endpoint` (`http(s)://host[:port]`, nothing else). Without the private-network override: https and every DNS record public (UrlGuard). With it (audited `backup.destination_private_network_allowed`): any host, http allowed; launchroomd still refuses plain http unless the host is in its local `LR_BACKUP_INSECURE_HOSTS`.
- Secrets: a per-destination DEK wrapped by the KEK (`backup_destination:<id>`), values bound to `backup_destination|<team|instance>|<id>|<field>`. The restic repository password is generated (256 bit, URL-safe) unless an existing one is given. Columns are `$hidden`; Data objects never contain them.
- Repository: `s3:<endpoint>/<bucket>[/<prefix>]`. Bucket, prefix and region grammars match launchroomd's.
- Provider guides: [Cloudflare R2](https://launchroom.vantezzen.io/docs/databases/backups-cloudflare-r2), [Hetzner Object Storage](https://launchroom.vantezzen.io/docs/databases/backups-hetzner).

### 9.3 Tasks (protocol v1, see protocol/CHANGELOG.md)

- Destination credentials are a sealed `TaskEnv` bound to server + task with exactly `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `RESTIC_PASSWORD`. Backup tasks have `max_attempts = 1` (a blind retry would take another snapshot or re-run a restore); one heavy task per server at a time.
- Per engine launchroomd writes one stdin file: `postgres.dump` (`pg_dump --format=custom`), `mysql.sql` / `mariadb.sql`, `redis.rdb` / `valkey.rdb` (`--rdb -`), `mongodb.archive`, `clickhouse.zip` (§11). Both exit codes are checked; a failed dump fails the task and the stray snapshot is forgotten. Restore needs the matching file, so engines can't be mixed.
- Restore: Postgres `pg_restore --clean --if-exists --no-owner --no-privileges --single-transaction --exit-on-error`; MySQL `mysql` from stdin; MongoDB and ClickHouse: §11. Redis and Valkey are backup only.
- Retention: a daily `forget` per schedule restricted to the subject's tags (`kind:database`, `environment:`, `service:`; volumes per volume) applied as one group (scheduled, pre-delete and pre-restore snapshots all count), pruning when something was removed; plus one `prune` per repository per day. Control plane: the dashboard runs `forget` per part (`kind:control-plane,part:database` / `part:keys`, grouped by host) and `prune`.

### 9.4 Schedules, runs, statuses

- A team's default destination (the first one, or the one marked default) creates a schedule for every database in production and persistent environments: daily at `M H * * *` UTC with `M = crc32(instance id) % 60`, `H = (crc32 / 60) % 6 + 1` (01:00–06:59 UTC); retention production 7d/4w/3m, persistent 7d. The instance destination creates the control-plane schedule `M */6 * * *`, retention 7d/4w/6m. Schedules are editable (5-field cron, retention, on/off).
- `launchroom:backups:tick` (every minute): new default schedules, run ↔ task sync (also catches lost leases), due schedules (once per minute), daily maintenance jobs, restore advancement. Completion hooks (`DaemonTaskFinished` listener) sync runs immediately.
- `backup_runs` per attempt (at most one in flight per database, partial unique index). A due backup that can't start (database down) is recorded as a failed run unless the database was never deployed.
- Health per database (`App\Services\Backups\BackupStatuses`, `ServiceBackupStatusData.status`): `ok`, `stale` (no success for 36 h), `failing` (latest finished run failed), `running`, `none`, `unconfigured`.

### 9.5 Restores and safety snapshots

- **Restore as new service** (needs `projects.manage` + `deployments.create`): adds `<name>-restored-<date>` with the same engine and version **to the source's environment only**, deploys it when nothing else is staged there (otherwise it stays staged and the restore waits up to 24 h for it to run), then a `restore` task runs on its server.
- **Restore into this service** (needs `backups.manage`): typed confirmation (the service slug), a `pre_restore` safety snapshot first; the restore task starts only after it succeeded (if it fails, nothing is changed).
- **Dependents are held** (`App\Services\Backups\RestoreHolds`) during an in-place database restore:
  - once the safety snapshot succeeded the run turns `restoring` without a task, and the current instances in that environment of every service connected to the database leave their servers' NodeStates (launchroomd stops them; the database keeps running);
  - the restore task is created once none of their workloads reports up any more, or after `launchroom.backups.restore_hold_wait_seconds` (120 s; an unreachable server can't confirm, and Postgres restores are a single transaction anyway);
  - the task's end (success or failure) re-renders their servers and they start again; a database that stops while its dependents are held fails the restore after the same wait and releases them;
  - while held, web dependents have no upstream (their routes return errors): a restore into a database is a maintenance window.
- The snapshot must belong to the database (a recorded run, or the cached repository listing filtered by its tags).
- Safety snapshots for other code: `App\Actions\Backups\TakeSafetySnapshot::handle($instance, BackupReason::PreDelete|PreRestore|PreDeploy|PreUpgrade, $user, $actor)` returns the run, or null when there is nothing to protect or no destination. Deletions use final backups (§9.13). Control-plane upgrades run `php artisan launchroom:backups:control-plane --reason=pre_upgrade --wait` (exit ≠ 0 on failure).

### 9.6 Recovery kit and key bundle

- **Passphrase.** It is never stored. Argon2id (`crypto_pwhash`, MODERATE limits, stored with the salt in `instance_settings.recovery_kdf`) derives a seed → X25519 key pair (`crypto_box_seed_keypair`). Only the public key is stored (`recovery_public_key`), so scheduled backups can seal without knowing the passphrase, and re-deriving it verifies a passphrase (`hash_equals`).
- **Key bundle.** Plaintext `launchroom-keys/1`: `{appUrl, env: {APP_KEY, APP_PREVIOUS_KEYS, DB_PASSWORD, REDIS_PASSWORD, REVERB_APP_ID/KEY/SECRET}, files: {kek, signing.ed25519, registry-token.es256.pem, registry-token.pub.pem}, headscale}`, sealed (`crypto_box_seal`) into `launchroom-recovery-bundle/<n>` `{format, kdf, publicKey, sealed, …}` and stored as `control-plane.keys.json`; the DB dump is `control-plane.pgdump`.
- **Authenticated bundles** (`launchroom-recovery-bundle/2`). Sealing is anonymous (anyone with the public key, which is stored in the bundle, can seal), so sealing alone gives confidentiality only. Format 2 adds:
  - `binding {run, databaseSnapshot}`: the run id and the restic id of the run's database snapshot (content-addressed);
  - `mac`: an HMAC-SHA256 over format, binding, public key and sealed bytes with a key derived from the passphrase (keyed BLAKE2b of the Argon2id seed, context `launchroom-recovery-bundle-mac/1`).

  The dashboard stores that MAC key (`instance_settings.recovery_mac_key`, encrypted with APP_KEY, hidden) when the passphrase is set, so scheduled backups can authenticate without the passphrase. The restore derives it from the passphrase, checks the MAC before opening, and refuses a run whose database snapshot or run id differs from the binding ("does not belong to its key bundle … nothing was restored"). Someone with bucket write access and the recovery kit but without the passphrase can't plant a database dump or a key bundle.
- **Format 1** (`launchroom-recovery-bundle/1`, no binding or MAC) is what a passphrase without a MAC key produces; setting the passphrase again switches to format 2. A format-1 bundle still restores, with a warning on stderr. Accepting format 1 leaves a downgrade path.
- **Headscale state** (`headscale: {name: base64}` in the same format): `noise_private.key`, `derp_server_private.key`, `db.sqlite` and `db.sqlite-wal` (never `-shm`, SQLite rebuilds it), at most 64 MB.
  - Read from `LAUNCHROOM_HEADSCALE_STATE_PATH` (`launchroom.mesh.headscale_state_path`): a read-only mount of Headscale's `/var/lib/headscale` into the dashboard containers (`data/headscale/lib` in production, the `headscale` volume in `make up-multi`).
  - Headscale keeps running during the backup, so the database is copied without a lock: the files are re-read until two consecutive passes see the same sizes and mtimes (≤ 5 tries, else the backup fails), and SQLite replays the copied WAL on open. A checkpoint racing the copy is what the retry detects.
  - No state path or no state = nothing included. With the embedded mesh on (`mesh_enabled_at` and `LAUNCHROOM_HEADSCALE_URL` set) missing keys fail the backup, since a restore without them strands every server's mesh client.
  - Permissions: Headscale creates its keys 0600 root. The installer (and `make up-multi`) gives the dashboard's group read access (0640), lets the group enter `data/headscale/lib` (0750; it is created 0700 under umask 077) and read the database files. Restored state is written root:dashboard-group 0640.
  - With the same noise key and database, every server's mesh client reconnects to the restored Headscale with its old node, IP and tags; nothing re-registers (verified in dev with `launchroom:restore --skip-database`). Bundles without the field still parse.
- **Recovery kit.** A text file with `key: value` lines between `-----BEGIN/END LAUNCHROOM RECOVERY KIT-----`: `version`, `instance-url`, `endpoint`, `bucket`, `prefix`, `region`, `access-key-id`, `secret-access-key`, `repository-password`, `repository`. It contains the S3 credentials (so a lost server can be rebuilt from the kit alone) but never the passphrase. Downloads are password-confirmed and audited. Setting or rotating the passphrase or moving the control-plane repository clears `recovery_kit_confirmed_at`; instance owners see a banner until they confirm the new kit.

### 9.7 Restore CLI (`php artisan launchroom:restore`), used by `install.sh --restore`

```
php artisan launchroom:restore [--kit=FILE] [--endpoint=URL --bucket=NAME --prefix=P --region=R] [--allow-http]
    [--passphrase-file=FILE] [--list] [--snapshot=latest|bkr_…|<snapshot id prefix>]
    [--database=NAME] [--create-database] [--skip-database] [--keys-out=DIR] [--force] [--json] [--no-interaction]
```

- Secrets never in argv. Precedence for each value: option (non-secret ones only) > environment `LR_RESTORE_ENDPOINT`, `LR_RESTORE_BUCKET`, `LR_RESTORE_PREFIX`, `LR_RESTORE_REGION`, `LR_RESTORE_ACCESS_KEY_ID`, `LR_RESTORE_SECRET_ACCESS_KEY`, `LR_RESTORE_REPOSITORY_PASSWORD`, `LR_RECOVERY_PASSPHRASE` (or `--passphrase-file`) > kit file > interactive prompt (hidden input). Non-interactive runs fail on a missing value.
- `--list` prints the complete control-plane runs (database + keys parts with the same `run:` tag), newest first (`--json`: `[{run, time, databaseSnapshot, keysSnapshot, reason}]`).
- Restore order:
  1. open the key bundle (a wrong passphrase, or a bundle that does not authenticate or is not bound to this run's database snapshot, stops before anything changes);
  2. `pg_restore --clean --if-exists --single-transaction` into `--database` (default: the configured one; refuses a database with tables unless `--force` or confirmed interactively; `--create-database` creates a missing one);
  3. write `<keys-out>/keys/{kek, signing.ed25519, registry-token.es256.pem, registry-public/registry-token.pub.pem}` (0400, public key 0444) and `<keys-out>/restored.env` (0600, `NAME=value` lines; values outside `[A-Za-z0-9_.:/+=,-]` are double-quoted; plus `APP_URL`). Existing files are refused unless `--force`.
- After the database: the control-plane run that was in flight in the dump (the dump is taken while its own run is `running`) is marked `succeeded` with its database snapshot, and any other in-flight control-plane run `failed` ("Interrupted: …") by `App\Services\Backups\RestoredControlPlaneRuns`. Otherwise every later backup would join the restored "running" run and none would run. Independently, `StartControlPlaneBackup` gives up an in-flight run older than the task timeout + 10 min (a dead worker) and starts a new one.
- `restic init` from the dashboard (`ResticCli::openOrInit`: destination test, control-plane backup) is serialised per repository with a cache lock and re-checks `cat config` under it: two concurrent inits on an empty bucket leave a key that can't decrypt the config ("ciphertext verification failed") and a repository that never opens again.
- `--json` output: `{run, time, database, databaseBytes, keysOut, files, env (names), appUrl}`. Exit 0 on success, 1 on any failure (message on stderr).
- After it: copy the key files into `data/keys`, merge `APP_KEY`, `APP_PREVIOUS_KEYS`, `REVERB_*` (and `APP_URL`) into `.env`, run `php artisan migrate --force` (newer releases migrate on top of the restored schema), start the stack. `install.sh --restore` does exactly this ([11](11-installation-and-dev.md) §2.2).

### 9.9 Volumes of deleted environments, projects and previews

Their Docker volumes are retired, not deleted on the spot ([05](05-networking-ingress.md) §1.1): kept for `launchroom.volumes.retention_hours` (7 days; previews `preview_retention_hours`), then deleted through an explicit NodeState `deleteVolumes` request. A volume whose service had backups (a successful run or an enabled schedule) is only deleted once its **final backup** exists (taken by the deletion before the teardown, recorded as `volume_retirements.final_backup_snapshot`, §9.13) or the deletion was explicitly overridden ("Delete without final backup", recorded as `confirmed_at/by`). A retirement that has neither keeps a manual gate: "Allow deletion" on the server page (owner/admin, recent password, audited).

### 9.11 Registry storage on S3

By default Zot keeps images in `data/zot/storage` on the control-plane disk: after a control-plane loss they are rebuilt from the recorded commits and base images are re-mirrored (§5.2 step 3e). With **Settings → Registry** (instance owners, recent password, audited) Zot's storage moves to an S3-compatible bucket, so a restored control plane pulls every image again straight away.

- **Data**: `registry_storage` (singleton `id = 1`; no row = local disk): `endpoint`, `bucket`, `region`, `prefix` (default `registry`), `force_path_style` (default on), `allow_private_network`, the credentials envelope-encrypted like a backup destination (a DEK wrapped by the KEK, context `registry_storage:instance`, value bound to `registry_storage|instance|credentials`; re-wrapped by `launchroom:keys:rotate-kek`), `updated_by`. `instance_settings.registry_config_hash` / `registry_config_written_at` record the last config written to disk. The endpoint and bucket go through the backup `EndpointGuard` (https + public addresses; the audited private-network override allows LAN or mesh and http, never loopback, metadata or the control plane's own services). Audit: `instance.registry_storage_configured`, `instance.registry_storage_private_network_allowed`, `instance.registry_storage_removed`, `instance.registry_config_written`.
- **Rendering**: `App\Services\Registry\ZotConfig` renders the full `config.json`. Local storage renders exactly the installer template `deploy/images/zot/config.json` (realm `APP_URL/registry/token`; a test keeps them equal). S3 swaps in Zot's `s3` storage driver (`rootdirectory /<prefix>`, `regionendpoint`, `region` default `us-east-1`, `forcepathstyle`, `secure` = https, `accesskey` / `secretkey`) and sets:
  - `dedupe: false`, `remoteCache: false`. Zot's S3 dedupe stores duplicates as placeholders resolved through a cache database; without DynamoDB or Redis that cache is a local file on the control-plane disk, and losing it would make every deduplicated blob unresolvable. Without dedupe each repository holds its own copy of shared layers (more bucket space; `cache/**` and `mirror/**` are pruned by the same retention).
  - `extensions.sync.downloadDir: /var/lib/registry/.sync`: Zot refuses on-demand mirroring into remote storage without a local staging directory.

  GC and retention (`apps/**` 10 tags, `cache/**` 2, `mirror/**` pulled within 30 days) work unchanged on S3.
- **Apply**: saving only stores the settings. `./launchroom registry apply` on the control-plane server runs `php artisan launchroom:registry:config --write` (writes `LAUNCHROOM_ZOT_CONFIG_PATH` = `/data/zot/config.json` in the dashboard container, the bind-mounted `data/zot/config.json`, mode 0600, in place; prints `changed` / `unchanged` and records the hash) and restarts `zot` when it changed. `./launchroom registry show` (or the command without `--write`) prints the config with the credentials redacted. The installer runs the same render after every install and upgrade (the template is only written for a new install), so an upgrade never reverts to local storage and `install --restore` brings the S3 config back with the restored database. The settings page shows "Saved, not in use yet" until the written hash matches the rendered config.
- **Trade-offs**:
  - durable registry (survives the control-plane server, nothing to rebuild after §5.2);
  - higher pull latency and per-request costs (every layer pull goes Zot → bucket; servers' Docker image stores still cache what they run);
  - more bucket space (no dedupe), a dependency on the bucket being reachable for pushes and pulls, and a registry restart (seconds) when switching.

  **Switching does not migrate images** in either direction: existing local images are not copied into the bucket (or back); the next deploy of each service rebuilds or re-mirrors its image (running containers are unaffected). Use a bucket of its own (not the backup bucket), with a key that may read, write, list and delete.
- Restarting Zot is the operator's one command (`./launchroom registry apply`); the dashboard can't restart it.
- **Dev**: the dev dashboard has no `LAUNCHROOM_ZOT_CONFIG_PATH` (the dev Zot reads the repository's `dev/zot/config.json`), so `--write` refuses there and the page stays at "not in use yet"; `launchroom:registry:config` prints the rendered config.
- **Verified in dev**: the renderer's S3 config (versitygw, private-network override) started Zot; a pushed image and an on-demand mirror pull landed under `registry/` in the bucket, and a fresh Zot container without any local state served the same digest and catalog from the bucket alone.

### 9.12 Volume backups

- **Subject**: every service that is not a database and has volumes (`App\Services\Backups\BackupSubjects`); databases keep using dumps, their volume is never file-copied. App and image services get volumes in Settings → Volumes (`AddServiceVolume`, staged; mount path grammar = launchroomd's `ContainerPath`, not `/proc`, `/sys`, `/dev`, not nested in another volume; audited `service.volume_added`). A service with a volume is placed like a database: one replica, pinned to the server its volume was created on (`Placer`).
- **Data**: `volumes.backup_consistency` (`live` default | `pause`, owners/admins, audited `backup.volume_updated`); schedules with subject `volume` (one per service instance, all its volumes); runs with `volume_id` (one run per volume; at most one in flight per volume); `restore_runs.subject` + `volume_id` (the volume restored into). Defaults: daily, staggered, 7 daily + 4 weekly (`RetentionData::volume()`), production and persistent environments; retention `forget` runs per volume (tags `kind:volume,environment,service,volume`).
- **Task**: `backup` kind `volume` `{target: {volume, consistency}}`, `restore` kind `volume` `{target: {volume}, mode}`, pinned to the volume's server (`Volume.server_id`), sealed credentials as for databases.
- **launchroomd backup** (`internal/backup/volume.go`, `internal/docker/volumes.go`):
  - finds the managed volume by its `launchroom.volume` label (service volumes only, never `lr-system-…`);
  - imports a local helper image `launchroom-local/volume-helper:1` once (an archive holding only the `/data` mount point; it is never run);
  - creates `lr-vol-<random>` (managed + `launchroom.helper=volume`, network `none`, `cap-drop ALL`) mounting the volume at `/data` (read-only for backups);
  - with `pause`, pauses the running containers that use the volume until the tar has been read (`docker pause` / `unpause`, always undone);
  - `GET /containers/{id}/archive?path=/data` → `restic backup --stdin --stdin-filename volume.tar --tag …`. A read error forgets the half snapshot and fails the task (live reads of files that grow while being archived can fail this way: use `pause`).
- **launchroomd restore**: the snapshot must hold exactly `/volume.tar`. launchroomd waits (10 min) until no container uses the volume, removes it, recreates it with the same name and labels, and runs `restic dump` → filter → `PUT /containers/{id}/archive?path=/`.
- **Restore filter** (`internal/backup/restoretar.go`) keeps only what a workload with all capabilities dropped could have created itself:
  - names under `data/` (clean, relative), regular files, directories, symlinks, hard links to an earlier file of the archive;
  - FIFOs are skipped; device nodes and other special entries refuse the restore;
  - setuid and setgid bits, extended attributes (`security.capability`, ACLs, SELinux labels) and owner names are dropped;
  - numeric owners are kept on purpose (`CopyUIDGID`): database engines and many images refuse data not owned by their own UID, and a file owned by another UID grants nothing without `CAP_CHOWN` / `CAP_FOWNER`.

  Helpers are removed after use and swept before the next volume operation; one heavy backup task per server at a time.
- **Holding the service** (`App\Services\Backups\RestoreHolds`): while a volume restore is `restoring`, the target instance's workloads (and its volume declaration) are left out of its server's NodeState, so launchroomd stops them; the restore task's completion re-renders the server and they start again. In place: safety snapshot first (`pre_restore`, a volume run), then the hold. As new: a copy of the service (same source, settings, variables that apply to the environment, volume paths) is added to the environment and deployed; once its workload ran on its server, the restore holds it, replaces the empty volume and starts it again.
- **UI**: the Backups tab lists the volumes with their consistency (canvas node `volume`); snapshots show the volume's mount path.
- **Verified**: `TestVolumeBackupAndRestoreThroughRestic` (ITEST: real restic 0.19.1 + versitygw): a paused backup leaves the service running, a second live snapshot dedupes, a restore waits for a busy volume, replaces changed and removes added files, keeps owners, modes and labels, and leaves no helper. In dev, an nginx service's uploads volume was backed up, the file deleted, and a restore as new served the original file again.

### 9.13 Final backups before deletion

- **When**: deleting an environment (also a preview teardown), a project, or deploying a staged service removal, for every instance with backups configured (an enabled schedule or a successful run) whose data exists (a deployed database, volumes placed on a server) and a destination exists (`App\Services\Backups\FinalBackups::needed`). Nothing configured → the deletion runs immediately.
- **How**: `deletion_requests` (`del_…`, per subject `project | environment | service_instance`, one open request per subject): `backing_up → ready | blocked`, `blocked → backing_up (retry) | overridden`, `ready | overridden → completed`, `cancelled` (removal discarded or subject gone).
  - The delete action starts `pre_delete` runs (dumps, volume snapshots; a backup already in flight counts) while the workloads still run and returns "waiting" (UI: a pending-deletion card with the runs).
  - The backup tick (`AdvanceDeletions`) turns it `ready` when all succeeded and then deletes environments and projects (`ContinueDeletion`). Preview environments are finished by the preview tick (pending close), staged service removals by the next Deploy (`FinalBackups::assertCleared` refuses the Deploy while the final backup runs or after it failed).
  - A run that fails or can't start (for example the database isn't running or the server is offline) blocks the deletion with the reason; so does `final_backup_timeout_minutes` (6.5 h). Nothing is deleted while blocked.
- **Override**: "Delete without final backup" needs owner or admin (`backups.manage`) and a recent password (`POST /deletions/{del}/skip-final-backup`, or `skipFinalBackup` in the delete request); audited `backup.final_backup_skipped`. "Retry final backup" needs the delete permission. The volumes of an overridden deletion are recorded as confirmed (`confirmed_at/by`).
- **Afterwards**: retirements record the final snapshot (`volume_retirements.final_backup_snapshot`; the run row goes with its service); snapshots stay in the destination and are listed by the repository with `reason:pre_delete`.
- **Verified in dev**: deleting a persistent environment with a seeded Postgres waited for the final backup (a few seconds), then the tick deleted the environment; the retirement carries the snapshot, and `pg_restore` of it shows the seeded row. A staged removal of a volume service made the Deploy wait ("The final backup of files is still running") until its volume snapshot succeeded, then tore it down.

### 9.14 Replace server

- **Wizard**: Servers → (unreachable or offline server, not the control plane) → **Replace server** (`/servers/{srv}/replace`, `servers.manage`; starting it needs a recent password). It shows what lived there (`ServerReplacementPlan`: every non-removed instance with a placement or a volume there; stateful = has a volume there, with its latest successful backup and age, "starts empty" otherwise), online candidates, and a link to enroll a new server. Removed services are excluded from the plan.
- **ReplaceServer** (one transaction, audited `server.replaced`):
  - the replacement inherits roles (union), labels (the dead server's; the replacement's own win) and the control-plane flag;
  - volumes pinned to the dead server move to it (they are restored or start empty); the dead server's placements are dropped;
  - the dead server gets an empty **decommission** NodeState (no roles → no system containers, no workloads, no routes; volumes are never deleted), is revoked (`RevokeServer`: key denied, pinned tasks cancelled, mesh node removed) and marked `replaced_by_server_id/replaced_at`;
  - `AuthenticateDaemon` still lets a replaced server `GET /daemon/v1/state`, which only serves that last state: if it ever comes back it stops everything. Leases, reports, nudges and registry tokens answer 401;
  - allow and deny lists naming the dead server stand for the replacement (`Placer::serverIds`).
- **Restores**: for each chosen stateful service one in-place `restore_run` per database or volume (latest snapshot, no safety snapshot, `server_replacement_id`), waiting for the service to run on the replacement (`AdvanceRestores`; volume restores hold it, §9.12).
- **Progress** (`server_replacements`, `AdvanceServerReplacements`, right away and every backup tick): stateful services are redeployed first (pinned by their volumes) and restored; once all are restored, done or failed, stateless services that ran there are redeployed (re-placed by the scheduler), unless they already run elsewhere (automatic rescheduling); then the run completes ("N of M need attention" when something failed). The page polls while it runs. Redeploys reuse the registry image (the registry is on the control plane); in recovery mode lost images are rebuilt (§9.15).
- **Verified in dev**: Postgres + PostgREST pinned to server-2 by a label; server-2 stopped; after it turned unreachable, the replacement took about 2.5 min: server-1 got the label, Postgres and an uploads volume were restored on server-1, PostgREST was re-placed after them and served the backed-up rows (rows written after the backup are gone, as expected). When server-2 started again, its launchroomd fetched the decommission state, removed every workload and system container except the mesh client within 5 s, and every other request got 401; volumes stayed on its disk.

### 9.15 Recovery mode

- **Entering**: `install.sh --restore` restores the database, keys, `.env` and Headscale state (§9.7, §9.6), starts the stack and enrolls the new server's launchroomd with `launchroom:servers:bootstrap-local --force --recovery`. The previous control-plane server stays in the restored database (no longer `is_control_plane`, not revoked) and `instance_settings.recovery_state` `{startedAt, previousControlPlaneServerId, replacementId}` is set. The installer prints the `/recovery` link.
- **Dashboard**: instance owners land on `/recovery` (and see a banner everywhere) until they finish. Checklist (`RecoveryChecklist`):
  - (a) replace the previous control-plane server with this one: `ReplaceServer` with `recovery: true` (allowed while the old row still says online), restoring every stateful service that has a backup;
  - (b) DNS: live checks that the dashboard host and `*.<apps domain>` point at the edge addresses;
  - (c/d) the replacement's progress;
  - (e) images: active deployments whose image is gone from the registry (`RegistryManifests` HEAD on Zot) are listed and rebuilt from their recorded commits ("Rebuild N images": the lost images are marked pruned and no longer reusable, then `RedeployService` builds at the same commit); services re-placed by (a) do the same automatically;
  - "other servers reconnected" (seen since the restore; same URL and signing key → they reconnect by themselves).

  "Finish recovery" clears the state (audited `instance.recovery_finished` with what was left open).
- **Covered by `make test-install`** (restore scenario, [11](11-installation-and-dev.md) §2.4): owner + project + passphrase + destination, control-plane backup to versitygw, `launchroom uninstall`, `install.sh --recovery-kit FILE --restore-allow-http`; asserts the restored data, `APP_KEY` and signing key, the new local launchroomd online, recovery mode pointing at the kept previous server and a successful backup afterwards. The checklist steps themselves (replacement, DNS, rebuilds, finishing) are covered by Pest.

### 9.16 Swap after a restore as a new service

- **What it does** (`App\Actions\Backups\SwapRestoredService`, `POST backups/services/{instance}/restores/{rsr_…}/swap`, `ManageProjects`, audited `backup.restore_swapped`): for a **succeeded** restore as a new service whose original and copy are both still part of the environment, in **that environment only**:
  - every service with a current instance there that is connected to the original gets the same connection (mode, style) to the copy, so its injected variables (`DATABASE_URL`, `DB_*`, `<SLUG>_URL`) reference the copy;
  - the original's own connections (for example an app with a volume → its database) are given to the copy;
  - the original's domains (generated and custom) move to the copy (routes still come from the applied revision until Deploy);
  - the original's removal is staged (`RemoveService`: with a final backup when it has backups, §9.13; its volume is kept like every removal).
- **Why connections instead of rewiring the data**: connections are project-wide but only apply where both ends run (`CurrentEnvironmentSpec`). The copy runs in this environment only, so other environments keep using the original; here, once the original is removed, only the copy's connections apply. Swapping volume rows instead was rejected: NodeStates render volumes from live rows (not from the applied revision), so it could not be staged, and a database's data directory carries the copy's generated credentials.
- **Confirmation**: the dialog on the original's Backups tab ("Swap in…" next to a finished restore) requires typing the original's slug. Nothing changes on the servers until Deploy; Discard reverts it (added connections are deleted with their variables, moved domains go back to the service that had them in the applied revision, the removal and its final-backup gate are cancelled). A swap is offered once: afterwards the original is no longer part of the environment.
- **Limits**: preview environments that share the base database keep the original until it is gone from the base; renaming the copy back to the original's name is a normal rename.

## 10. Point-in-time recovery, verification, metrics and alerts

### 10.1 Point-in-time recovery for Postgres: the choices (D34)

| Question | Choice | Why |
|---|---|---|
| Archiving | Postgres' bundled **`basic_archive`** module (`archive_library`, Postgres 15+) copies each completed WAL segment into `<volume>/launchroom-wal` | `archive_command` is a string Postgres runs through `/bin/sh -c`; even a constant one contradicts "no shell strings" ([09](09-security.md) R1) and needs a helper inside every DB image. `basic_archive` is in every official image (16/17/18-alpine), writes atomically (temp file + rename), and Postgres keeps a segment in `pg_wal` until it is archived, so nothing is lost while shipping lags. The directory is in the data volume, so a container replacement loses nothing either |
| Shipping | **launchroomd** ships the directory every 30 s into **restic** (one snapshot per batch, `wal.tar`, tags `kind:wal`, `environment`, `service`, …), then deletes exactly the stored files | Same repository, encryption, credentials and retention (`forget --keep-within`) as every other backup; no second tool or S3 client. Direct per-segment S3 uploads (wal-g, pgBackRest) would need their own encryption format, S3 client and credentials path; wal-g also needs file access to `PGDATA` (a sidecar mounting the volume) or the shell `archive_command`. Restic's per-snapshot cost is fine at one batch per ≥ 30 s (snapshots are cached locally, listing is per tag). It keeps running while the dashboard is down (D18): the spec is in the NodeState |
| Base backups | `pg_basebackup --format=tar --wal-method=fetch` streamed through `docker exec` into `restic backup --stdin` (`postgres-base.tar`), daily on the archive's own staggered cron (07:00–12:59 UTC) and right after turning it on or after an in-place restore | Self-contained (the WAL needed for consistency is inside), so verification and restores work even if early WAL is missing. Logical dumps keep running on their schedule (they restore across versions and feed preview clones) |
| Replay | the base backup + every WAL batch since it is laid into the **emptied volume** with a `standby.signal`, and Postgres replays it in a **throwaway container** of the database's own image (no network, `listen_addresses=''`, cap-drop ALL + the engine's capabilities, the workload's limits, `recovery_target_time` + `recovery_target_action=promote`) | Standby mode reads WAL from `pg_wal` and needs no `restore_command` (another shell string). Without a target, or when the archive ends before it, launchroomd promotes with `pg_promote()` once replay stops advancing for 8 s. Then it sets the target's own password (stdin, never argv; a copy has its own credentials), checks its database exists and stops Postgres cleanly with Docker's stop (`SIGINT`, fast shutdown; the throwaway runs without an init, D42) |
| Window | from the oldest kept base backup to the newest shipped WAL; RPO ≈ 1 minute (`archive_timeout=60` + the 30 s interval) | |

Rejected: wal-g and pgBackRest (shell `archive_command` or file access to PGDATA from a sidecar, a second encryption and credential path, more binaries to pin), `pg_receivewal` as a long-running exec (dies with the container, writes into the container filesystem), a `restore_command` helper binary (still a shell string run by Postgres).

**Policy floor**: nothing privileged; the throwaway uses the workload's own digest-pinned image (`policy.Check` + `CheckContainer`, present locally, never pulled), `NetworkMode: none`, `no-new-privileges`, log limits, CPU shares 256, no init process but a typed stop (the engine's signal, 2 min; D42, [03](03-daemon-protocol.md) §8). The only extra exec is `mkdir` / `ls` / `rm` of the fixed archive directory **as the `postgres` user** (`ExecOptions.User`).

### 10.2 Turning it on, shipping, status

- Backups tab → Point-in-time recovery (owners/admins, `backups.manage`; audited `backup.point_in_time_updated`) creates `wal_archives` (destination: the database's schedule's, else the team default; `keep_days` 1–35, default 7). Postgres restarts once: NodeStates render the workload's args with `-c archive_mode=on -c archive_library=basic_archive -c basic_archive.archive_directory=<mount>/launchroom-wal -c archive_timeout=60` (only when the start command is Postgres itself) plus `walArchive {directory, destination (credentials sealed as a WorkloadEnv to the server + workload), tags, interval: 30s}`, only for serving workloads on servers whose launchroomd has the `pointInTime` feature. A fingerprint of the destination stands in for the sealed box, so re-renders don't create new versions.
- launchroomd (`internal/backup/walarchive.go`, `WalArchiver`): one shipper per workload. Each cycle runs `mkdir -p` + `ls` on the directory, takes completed files (`^[0-9A-F]{24}(\.partial|\.[0-9A-F]{8}\.backup)?$`, `^[0-9A-F]{8}\.history$`; never basic_archive's temp files), at most 64 (1 GiB) per batch, streams them out of the container (Engine API archive) into `restic backup --stdin`, and deletes exactly those files after the snapshot exists. A failed upload deletes nothing. Status per workload in `Report.walArchives` (`active` / `waiting` / `failing`, last stored time and segment, pending files, message), recorded forward-only by `RecordWalArchives`.
- Retention (daily): `forget --keep-last 1 --keep-within (keep_days+1)·24h` on the base backups (`kind:base_backup,environment,service`) and on the WAL (`kind:wal,…`), then one prune per repository per day.

### 10.3 Restoring to a point in time

- Backups tab → the timeline's first entry **Any point in time** ("From Oct 12, 03:00 to about a minute ago") opens a local date-time picker (seconds) with **Newest**. Restore offers the usual "As a new service" / "Into postgres" option cards and typed confirmation. `POST …/restore {pointInTime: true, at?, mode, confirmation?}`.
- `StartRestore` picks the newest succeeded base backup finished at or before the time, refuses times outside the window, and creates a `restore_runs` row with `subject = base_backup`, `point_in_time` (null: the newest point) and the target data volume. In place: safety dump first (`pre_restore`), then the database **and** its dependents are held (`RestoreHolds`). As new: the copy is provisioned and deployed, then held while its volume is replaced.
- `AdvanceRestores` sends a `restore` task of kind `base_backup` pinned to the volume's server with `runtime`: the target's deployment image, mount path, `PGDATA` (`/var/lib/postgresql/18/docker` for 18, `/var/lib/postgresql/data` before), the archive directory when restoring in place with point-in-time recovery on (so the new timeline's history is archived), and the target's `POSTGRES_*` sealed to the task. The result's `restoredTo` (the last replayed transaction) is shown in History ("Restored as … · to Oct 19, 14:43").
- After an in-place restore the window restarts: the next tick takes a new base backup (on the new timeline). Times between a restore point and when the restore ran resolve to the restored timeline (`recovery_target_timeline=latest`).

### 10.4 Automatic restore verification

- Weekly per service with an enabled schedule or point-in-time recovery (`verification.every_days`, at the minute `crc32(instance)%60` so they spread), and "Verify now" on the protection card (`backups.services.verify`, Deploy permission, audited `backup.verification_started`). `StartVerification` verifies the newest base backup (with its WAL) when point-in-time recovery is on, else the newest dump or volume snapshot; one at a time per service (`backup_verifications`).
- The `verify_restore` task runs on the server the backup was taken on (it has the engine image; nothing is pulled), takes the heavy-backup slot, and uses a fresh managed volume `lr-verify-…` plus a container `lr-verify-…` (labels `launchroom.helper=verify`, swept before the next one) with no network and `verification.{cpus, memory_mb, pids}` (1 CPU, 1 GiB, 512):
  - Postgres dumps: fresh `verify` role and database, `pg_restore`, exact table and row counts (`query_to_xml` count per table), `pg_amcheck --install-missing` (heap + B-tree).
  - Base backups: the §10.3 replay to the newest point, then the same checks as the source's role and database.
  - MySQL and MariaDB dumps: fresh server, load, counts from `information_schema`, `CHECK TABLE` on every table (the slim images ship no `mysqlcheck`).
  - Redis and Valkey: the RDB file is copied into a container whose command is `redis-check-rdb` / `valkey-check-rdb`.
  - MongoDB and ClickHouse: §11.
  - Volumes: `restic dump` through the restore filter of §9.12 (every entry allowed, every blob's hash checked on the way), counting files and bytes; no container.
- A check that fails makes `passed: false` (the task succeeds); a verification that can't run fails the task. Both turn the verification `failed` with the reason. Protection card: "Last verified · 2 days ago" (✓/✕); History shows what was restored and found.

### 10.5 Metrics on the Backups tab

`trend`: the last 30 finished runs of one kind (dumps or volume snapshots; base backups only when there is nothing else), with size and `duration_ms` (from the task result). Shown as a bar strip (height = size, failed = short red bar with ✕) and three facts: succeeded n of m, usual duration (median), last size.

### 10.6 Alerts

`EvaluateBackupAlerts` (every backup tick) computes four problems per protected service and raises or resolves them through `App\Events\Backups\BackupAlertRaised` / `BackupAlertResolved`, which `ForwardBackupAlerts` hands to the alerts API ([15](15-observability.md) §3.2, rule `backup_failed` for all four, told apart by the subject key):

| Problem | Subject | Severity | Resolves |
|---|---|---|---|
| Newest backup run (dump, volume, base) failed | `backup:<sin_…>` | critical | the next one succeeded |
| Newest verification failed | `backup_verify:<sin_…>` | critical | the next one passed |
| Scheduled but no success for `stale_after_hours` (36 h) | `backup_overdue:<sin_…>` | warning | a backup succeeded |
| WAL lagging: on for > 15 min and failing for 15 min, no report for 15 min, or segments waiting and nothing stored for 15 min (`point_in_time.lag_alert_minutes`) | `wal_archive:<sin_…>` | warning | WAL is stored again |

Raised again at most every 30 minutes while it lasts (the alerts API dedups); texts never carry errors or log excerpts.

### 10.7 Verified

- `TestPointInTimeRecoveryRoundTrip` (ITEST, real restic 0.19.1 + versitygw + postgres:18-alpine): archiving with `basic_archive`, shipping WAL files, a base backup; restore to the newest point into another volume with another password (all rows over TCP with the new password); restore in place to a time between two inserts (only the earlier rows; the new timeline's `.history` archived and shipped afterwards; no replay container left); verification of the base backup with WAL (`restoredTo` set) and of a dump (amcheck passed, no throwaway left).
- `TestVerifyRedisMySQLAndVolume`: `redis-check-rdb`, MySQL 8.4 restore + `CHECK TABLE`, a volume snapshot read.
- In dev: point-in-time recovery on a busy Postgres stored WAL about every 30 s; rows inserted and then deleted 10 s later; a restore as a new service to a time between the two brought back the inserted rows, served with the copy's own generated password.

### 10.8 Known limits

- **Clean stops (D42).** Database workloads and the throwaway containers run without an init process and with a typed stop ([03](03-daemon-protocol.md) §8), so Docker's stop is a clean engine shutdown and the replay needs no `pg_ctl stop`. With an init, the init ran as root without `CAP_KILL`, couldn't forward the stop signal to the engine's own user, and the engine was killed (crash recovery on the next start). Verified: `TestDatabaseStopsCleanly` (Postgres, MySQL, Redis, Valkey: drain stop, restart on a new deployment, redeploy while running; `make test-daemon-integration ITEST=pgstop`).
- Point-in-time recovery needs Postgres 15+ and the image's default start command; other engines keep daily dumps.
- Verification runs on the database's own server (resource-capped, lower CPU weight) because the image is there; running it on a build server would need a pull path for engine images.

## 11. MongoDB and ClickHouse (D47)

Both are managed engines at parity with the others: pinned images, generated credentials, references, TCP health checks, clean stops, backups, restore (as new and in place), automatic verification and the Data tab. Tasks for them go only to servers whose launchroomd announces the feature `mongoClickhouse` (older versions refuse the engine names in task specs); otherwise the action says "Update launchroomd on … to back up MongoDB" (scheduled runs record that as a failed run).

| Question | MongoDB | ClickHouse |
|---|---|---|
| Images (config `launchroom.database_engines`) | `mongo` 8.0 (default) and 7.0, by index digest | `clickhouse/clickhouse-server` 26.8 (default) and 26.3 `-alpine` (LTS only), by index digest |
| Credentials | `MONGO_INITDB_ROOT_USERNAME=app`, a generated password, `MONGO_INITDB_DATABASE=app`; the image creates the root user and turns auth on | `CLICKHOUSE_USER=app` with `CLICKHOUSE_DEFAULT_ACCESS_MANAGEMENT=1` and a generated password (written by the entrypoint as a config file). **No `CLICKHOUSE_DB`**: the entrypoint would create it through a temporary server it then `kill`s, which root can't do to the `clickhouse` user without `CAP_KILL` (D42), so the start fails. Apps use the `default` database (`CLICKHOUSE_DATABASE=default`, ignored by the entrypoint) or create their own (Plausible does) |
| References | `MONGO_URL` (= `DATABASE_URL`, `…/app?authSource=admin`), `MONGOHOST`, `MONGOPORT`, `MONGOUSER`, `MONGOPASSWORD`, `MONGODATABASE` | `CLICKHOUSE_URL` (`http://user:pw@host:8123/db`), `CLICKHOUSE_HOST`, `CLICKHOUSE_PORT` (8123, the service port), `CLICKHOUSE_NATIVE_PORT` (9000, same server only), `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`, `CLICKHOUSE_DATABASE` |
| Clean stop (D42) | `SIGTERM`, 60 s, no init: the entrypoint drops privileges with `gosu` and `exec`s mongod (PID 1) | `SIGTERM`, 60 s, no init: the entrypoint `exec`s `clickhouse su clickhouse:clickhouse clickhouse-server` (PID 1) |
| Backup | `mongodump --archive --gzip --db=<db>` of the workload's database into `restic --stdin` as `mongodb.archive` | native `BACKUP DATABASE <db> AS launchroom TO File('launchroom-<random>.zip')` into the volume's `backups/` (the image's default `backups.allowed_path`), streamed out through the Engine API archive endpoint into restic as `clickhouse.zip`, then deleted |
| Restore | `mongorestore --archive --gzip --drop --nsFrom='$db$.$coll$' --nsTo='<db>.$coll$'` (lands in the target's database whatever it is called) | the zip is laid into `backups/`, `DROP DATABASE IF EXISTS <db> SYNC`, `RESTORE DATABASE launchroom AS <db>`, zip deleted |
| Verification | throwaway mongod (no users, no network), `mongorestore` into `verify`, collections + documents counted, `validate` on every collection (check `validate`) | throwaway server (default user, loopback only), `RESTORE … AS verify`, tables + `total_rows`, `CHECK TABLE` on every `*MergeTree` table (check `checktable`) |
| Data tab | collections browser (`getCollectionInfos` + estimated counts), documents page by page (`_id` order), database commands as JSON | tables (`system.tables`), rows, SQL |

**Why these choices.**

- **mongodump, not a file copy**: it is in every official image (database tools ship with it), consistent per collection, and restores across versions and into another database name (`--nsFrom/--nsTo`). One database (the workload's `MONGO_INITDB_DATABASE`), as Postgres and MySQL dump one database: the `admin` database (users) is never in a backup, so a restore never overwrites the target's own credentials. The tools have no password environment variable and a password in argv shows in `ps`, so launchroomd writes it as the **first line of stdin**: with `--username` and no `--password` they read it there (stdin is not a terminal) byte by byte, and the archive follows untouched on restores. A password with a line break is refused.
- **Native BACKUP for ClickHouse, not `clickhouse-backup`**: Altinity's tool is a second binary (a sidecar mounting the volume, its own config and S3 path) and duplicates what restic does; a logical export (`SELECT … FORMAT Native` per table plus `SHOW CREATE`) is not one consistent stream and loses engine settings. The native BACKUP is consistent per table (hard-linked parts), includes the schema of every table engine, and needs no config change because the official image allows `backups/`. The cost is disk: the zip is staged in the data volume until it has been streamed (about the compressed size of the database). The database is stored as `launchroom` inside the backup so it restores under any name. Passwords travel as `CLICKHOUSE_USER` / `CLICKHOUSE_PASSWORD` in the exec env (the client reads them).
- **Stops**: verified by `TestDatabaseStopsCleanly/mongodb` and `/clickhouse` (`make test-daemon-integration ITEST=p5eng`): no init, the engine is PID 1, the drain stop exits 0 in about 1–3 s (MongoDB logs `"Now exiting"`; ClickHouse logs to files, a SIGTERM shutdown exits 0 where a kill is 137), and the next start shows no recovery (`Detected unclean shutdown`; ClickHouse's `… - unclean restart` read from its log file by exec).
- **Verified**: `TestMongoBackupRestoreVerify` (MongoDB 7.0: archive with the password on stdin, in-place restore undoes a change, restore into a copy with another database name and password, verification of collections and documents, validate OK) and `TestClickHouseBackupRestoreVerify` (26.8: native BACKUP streamed out, no staged zip left, in-place and as-new restores, verification with CHECK TABLE). In dev both run on the fake servers and are browsed and queried in the Data tab.
- **Known limits**: MongoDB 8.0 refuses to start on Linux kernels from 6.19 until a fixed release (SERVER-121912, tcmalloc's rseq use; 9.0.x accepts ≥ 7.0.14). Pick 7.0 on such servers until a fixed 8.0 is pinned. ClickHouse in-place restores drop the database first (the safety snapshot is the way back, as everywhere). Point-in-time recovery is Postgres-only.

## 12. Import and export (D55)

Moving data **in** (a dump file or a reachable database into a managed database; an archive into a service volume) and **out** (a decrypted dump or volume tarball, from a backup or right now). The case that drove it: moving an app such as Umami from another platform without losing its data. User guides: [Move apps from another platform](https://launchroom.vantezzen.io/docs/migrate/from-another-platform), [Import and export](https://launchroom.vantezzen.io/docs/databases/import-and-export).

| Subject | Import from a file | Import from a URL | Export (backup or now) |
|---|---|---|---|
| Postgres | `pg_dump -Fc`, plain SQL (`.sql`, `.sql.gz`) | `postgres://`, `postgresql://` | `pg_dump -Fc` (`.dump`) |
| MySQL | `mysqldump` / `mariadb-dump` SQL (`.sql`, `.sql.gz`) | `mysql://`, `mariadb://` | SQL, gzipped (`.sql.gz`) |

### 12.1 Transfers: chunked, resumable, encrypted at rest

Every file goes through the dashboard as a **transfer** (`data_transfers`, `dtr_…`), in chunks:

- **Chunk size 8 MiB** (`launchroom.transfers.chunk_bytes`). A chunk is one request: the browser and the CLI upload chunk *n* with `PUT …/chunks/{n}`; launchroomd fetches chunk *n* of an upload and uploads chunk *n* of an export the same way. 8 MiB keeps a failed request cheap to retry on a slow line, keeps three copies of a chunk (body, plaintext, ciphertext) far below PHP's `memory_limit` with several uploads at once, stays under `post_max_size` (32 MiB) and common proxy limits, and makes a 10 GB dump about 1,250 requests. Larger chunks would cut request overhead a little and make every retry and memory peak bigger.
- **Resumable**: chunks are idempotent (a repeated `PUT` of chunk *n* replaces it). `GET` of a transfer lists the received chunk indices, so a reloaded page or a re-run CLI continues where it stopped; the browser remembers the transfer id per file (name, size, last modified) in `localStorage`, the CLI in `~/.config/launchroom/uploads.json` (path, size, mtime).
- **Integrity**: each chunk carries `X-Chunk-Sha256` (hex SHA-256 of the chunk), checked on receipt. The file's digest is **SHA-256 over the chunks' raw SHA-256 digests in order** (computable chunk by chunk in a browser, where Web Crypto has no streaming hash). The browser hashes with WebCrypto, or with a small pure SHA-256 when the dashboard is reached over plain HTTP (WebCrypto exists only in secure contexts; the console uses the same fallback). It goes into the signed task spec (`TransferRef.sha256`), and launchroomd checks it before it changes anything. Exports report the same digest (`DataExportResult.sha256`), checked against the received chunks.
- **Storage**: `LAUNCHROOM_TRANSFERS_PATH` (`/data/transfers`, the install's `data/transfers` mounted into every dashboard container; dev: `storage/app/private/transfers`), one directory per transfer, one file per chunk; directories without a live row are swept after 10 idle minutes. Each chunk is encrypted with a per-transfer data key (XChaCha20-Poly1305, associated data `transfer|<dtr>|<n>`), wrapped by the KEK (`transfer:<dtr>`, rewrapped by `launchroom:keys:rotate-kek`). A chunk is decrypted only to answer launchroomd or to stream the download. The disk must have the declared size plus 1 GiB free, else the upload is refused before it starts.
- **Lifetimes**: an upload is kept while an import uses it and 24 h after its last use (`upload_ttl_hours`), an unfinished one 24 h after its last chunk; an export 60 min after it is ready (`download_ttl_minutes`) or until it has been downloaded. `launchroom:transfers:sweep` (every 5 min) deletes the rest, including those of removed services.

Streaming the download through PHP holds one web worker per download (decrypting chunk by chunk, constant memory). Rejected: serving the files with `X-Sendfile` (needs them unencrypted on disk), streaming launchroomd → browser live through the session relay (Reverb frames are 4 KiB and MACed; a browser can't resume and a dashboard restart would break it), presigned S3 URLs (needs a bucket, and the decrypted dump would sit in it).

### 12.2 Tasks (daemon feature `dataTransfer`)

Four typed tasks, pinned to the server that runs the database (its serving placement) or holds the volume, one attempt for imports (a blind retry would import again), two for exports (chunks are idempotent), deadline `launchroom.transfers.task_timeout_seconds` (6 h); all take the server's heavy-backup slot except inspections. launchroomd announces `dataTransfer` and leases these tasks only while its local `LR_DATA_TRANSFERS` (install `.env`, default `on`) is not `off`; the dashboard offers import and export only for servers that announced it ("Update launchroomd on … to import data"). Specs and results: `protocol/schema/v1/task.json` (`DbImportSpec`, `VolumeImportSpec`, `DbExportSpec`, `VolumeExportSpec`), `task-completion.json` (`dataImport`, `dataExport`).

| Task | Does |
|---|---|
| `db_import` mode `inspect` | Target: empty or not, tables (collections), size, server version, by fixed queries through the engine's client in the database container. With a URL source: connects to it from a throwaway (below) and reports its version, or fails with "Couldn't reach … from <server>". Changes nothing. |
| `db_import` mode `import` | Fetches the file (or connects to the URL), checks format and versions, checks the target is empty unless `replace`, drops and recreates the database when `replace`, restores, and reports what the target holds now. |
| `volume_import` | `inspect`: empty or not, the volume root's owner. `import`: fetches the archive, checks it, empties the volume when `replace`, extracts it through a volume helper. |
| `db_export` | `pg_dump -Fc` / `mysqldump` (gzipped) / `mongodump --archive --gzip` / ClickHouse `BACKUP` / `--rdb` of the running database (the backup argv), or `restic dump` of a backup snapshot; uploaded in chunks. |
| `volume_export` | The live volume through a read-only volume helper (`consistency: pause` freezes its users while it is read) or `restic dump` of a volume snapshot, re-rooted (`data/` → `./`, `data/x` → `x`, owners and modes kept, device nodes skipped) and gzipped; uploaded in chunks. |

**Transport.** launchroomd fetches upload chunks with `GET /daemon/v1/transfers/{dtr}/chunks/{n}` (signed request; the 200 body is the chunk, signed like every 2xx body, `X-LR-Signature`) and uploads export chunks with `PUT /daemon/v1/transfers/{dtr}/chunks/{n}` (body = chunk, covered by the request signature's `content-digest`). The dashboard answers only for a transfer whose import or export run's task is **leased by this server** (else 404), refuses chunks beyond the transfer's size or larger than its chunk size (422), and limits these routes with their own `daemon-transfers` limiter (1,200/min per server). Requests have a 5-minute timeout and are retried 5 times with backoff.

**Fetching** writes `<data>/transfers/<task>.part` (resumed by a re-leased attempt, removed when the task ends, swept after 24 h), checks free disk space first (size + 1 GiB), verifies every response signature and then the file digest, and only then reads it.

### 12.3 Database imports in launchroomd

- **Format and versions are read from the file**, never from the dashboard (`internal/backup/sniff.go`): gzip magic → gunzip while reading; `PGDMP` → custom format, whose header carries the source server's and pg_dump's versions; `-- PostgreSQL database dump` / `-- Dumped from database version` → plain SQL (`-- PostgreSQL database cluster dump` is refused: "dump one database with pg_dump"); `-- MySQL dump` / `-- MariaDB dump` / MariaDB's sandbox line → mysqldump SQL (`-- Server version`); the mongodump archive magic `0x8199e26d` → archive (its header's `server_version`; collections compressed with `--gzip` are detected from the first block). Anything else: "launchroom couldn't recognise this file. Supported: …".
- **Versions**: a dump from the same or an older major version imports; a newer one fails before anything changes, naming both: "This dump comes from PostgreSQL 18.1, but postgres runs PostgreSQL 17. Pick 18 for the database, or dump with an older pg_dump." The target's version is read from the running database. Postgres compares the source server **and** the pg_dump major (a plain dump of pg_dump 17 sets `transaction_timeout`, which 16 doesn't know; pg_restore refuses newer archive formats). MySQL and MongoDB compare the source server's version; a MariaDB dump into MySQL is imported with a warning (no comparable versions).
- **Throwaway container**: the restore and a URL source's dump run in `lr-import-<random>` (label `launchroom.helper=import`, swept before the next import; inspections that check a URL use `lr-import-check-<random>`, `launchroom.helper=import-check`, swept after 10 minutes): the target workload's own image (digest-pinned, from the verified NodeState, present locally, never pulled), entrypoint `sleep <deadline>`, attached **only to the database's environment network** (taken from the verified NodeState, not from the task), cap-drop ALL, `no-new-privileges`, no init with a typed stop, the spec's limits and CPU weight 256, no volumes, log limits. launchroomd makes sure the firewall covers the network before it starts it (fail closed), so the throwaway has exactly a workload's reach: its own environment and the internet, no mesh, no other environment, no private ranges, no metadata. The client tools inside it connect to the database container's address on that network; credentials only in the exec env (`PGPASSWORD`, `MYSQL_PWD`) or stdin (MongoDB), never argv. A dump's client-side commands (`\!` in psql) can at most reach what that throwaway reaches; `mysql --binary-mode` turns the client's own commands off.
- **Replace everything**: Postgres `DROP DATABASE … WITH (FORCE)` and `CREATE DATABASE … OWNER …` over `template1`; MySQL `DROP DATABASE` / `CREATE DATABASE`; MongoDB `dropDatabase()` (mongosh, fixed script, env-only input). Without `replace` a database with any table (collection) refuses the import, also when the inspection said it was empty.
- **Restore**: Postgres custom `pg_restore --no-owner --no-privileges --single-transaction --exit-on-error`; plain SQL `psql -X -v ON_ERROR_STOP=1 --single-transaction`, with `ALTER … OWNER TO …`, `GRANT` and `REVOKE` lines outside `COPY` data left out (roles of the old server don't exist here). MySQL `mysql --binary-mode` with a line filter (`internal/backup/mysqlfilter.go`): `DEFINER=…` clauses removed outside `INSERT` lines (objects then belong to the database's own user), GTID and `SQL_LOG_BIN` statements skipped (they need privileges and only matter to replication), MariaDB's sandbox line skipped, `CREATE DATABASE` / `USE` dropped so everything lands in the target database (a dump with two databases is refused). MongoDB `mongorestore --archive [--gzip] --nsFrom='$db$.$coll$' --nsTo='<db>.$coll$' --nsExclude admin.*/config.*/local.* --stopOnError` (a dump of several databases is refused). Each adjustment is a result warning.
- **URL sources**: `SOURCE_URL` arrives as a sealed TaskEnv bound to the server and task; launchroomd parses it (scheme by engine, host, port, user, password, database, `sslmode`/`ssl-mode`), uses it once and keeps it out of logs, errors and argv (masked like every exec env value): Postgres `PGHOST`/`PGPORT`/`PGUSER`/`PGPASSWORD`/`PGDATABASE`/`PGSSLMODE` env, `pg_dump -Fc` into `pg_restore`; MySQL `MYSQL_PWD` env, `mysqldump --single-transaction --routines --triggers --events --no-tablespaces --hex-blob --set-gtid-purged=OFF --column-statistics=0` through the filter into `mysql`; MongoDB `mongodump --uri <URL without the password>` with the password as stdin's first line. launchroomd pipes the dump into the restore itself (counts bytes, checks both exit codes). An unreachable source fails before the target is touched.
- Plain SQL without a dump tool's header is imported as the target engine's SQL, with the warning "The file doesn't say which tool made it; it was imported as SQL". MySQL's drop and recreate uses `MYSQL_ROOT_PASSWORD` when the workload has it; the restore itself runs as the app user.
- **Errors** carry the useful end of the tool's stderr (last three lines, ≤ 512 bytes, credentials masked): "pg_restore failed: … relation "events" already exists".

### 12.4 Volume imports in launchroomd

- The archive is converted entry by entry into the tar launchroomd uploads into a never-started volume helper (`PUT /containers/{id}/archive?path=/`), names under `data/` (`internal/backup/importarchive.go`). **Refused**: absolute names, `..`, names through an earlier symlink, symlinks that are absolute or resolve outside the archive, hard links to anything but an earlier file, device nodes, sockets and unknown types, more than 100× the archive's size or 1 GiB (whichever is larger) of content (archive bombs). Skipped: FIFOs, the archive's root entry (`./`). Dropped: setuid/setgid bits, extended attributes, owner names. `stripComponents` works like tar's.
- Before anything changes, launchroomd reads the whole archive once (a dry run), so an unsafe archive is refused with the volume untouched. Symlinks are resolved the way the kernel does, through the archive's other links, at most 40 hops. Volume inspections read only the first entries and don't sweep helpers (they run beside backups).
- **Owners**: kept from tar archives (numeric) or set for every entry (`owner`); zip entries (no owners) get the volume root's owner. The volume's root folder keeps its owner and mode across a replace (images that run as non-root need it), or gets `owner` when set. Modes come from the archive (zip: its Unix mode bits when present, else 0644/0755).
- **Replace contents** recreates the volume (name and labels kept) like a restore; **Merge** extracts over what is there (same names overwritten). Either way the dashboard holds the service while the task runs, and launchroomd waits until no container uses the volume.
- **dockerd-guard** (R35): uploads into volume helpers are no longer passed through. The guard re-encodes them entry by entry and allows exactly this shape: destination `/`, `copyUIDGID` allowed (a volume helper has no user, so the archive's numeric owners are kept either way), names `data` or below (clean, relative), directories, regular files, symlinks, hard links to an earlier file; FIFOs skipped; setuid/setgid bits and PAX records dropped; device nodes and other types refused. It works as a stream, so a refused entry is never forwarded. Symlink targets are not checked there (a workload could create any symlink itself); launchroomd's converter checks them (`internal/guard`, tests in `helper_upload_test.go`, `FuzzRewriteVolumeTar`). Restores of volume snapshots use the same shape.

### 12.5 Dashboard

- **Data**: `data_transfers` (direction `upload|download`, purpose `database_import|volume_import|database_export|volume_export`, status `receiving → ready`, `failed`, `expired`; size, chunk size and count, per-chunk digests, file digest, detected format, wrapped key, link token hash and expiry, `$hidden` secrets), `data_import_runs` (`imp_…`: target instance, volume, source kind `file|url`, display label (file name, or the URL without user and password), `replace`, `stop_dependents`, `strip_components`, owner, safety snapshot run, daemon task, result fields, error), `data_export_runs` (`exp_…`: instance, volume, source `live|snapshot`, snapshot id, transfer, task, result, error).
- **Import runs**: `waiting_for_safety_backup → holding → importing → succeeded | failed`, or `cancelled` before the task starts (transition table on `ImportRunStatus`). `StartImport` (one transaction): the target runs (or the volume exists on a server) on a server with `dataTransfer`; a file must be a `ready` upload of this instance with a matching purpose, whose detected format fits the engine and whose versions are not newer than the target's (refused in the dashboard already, naming both versions; launchroomd checks again); `replace` needs the typed confirmation (the service's slug). Database imports take a safety snapshot when replacing (`TakeSafetySnapshot`), volume imports always (`StartVolumeBackup`, merge or replace), both with reason `pre_restore`; without a backup destination the confirmation says there is none. The dashboard doesn't check emptiness itself (the inspection is advisory): launchroomd refuses a database that isn't empty without `replace` ("… isn't empty (14 tables). Choose Replace everything …"). The run records the target's server (`server_id`); a URL import whose database moved before its task was created fails. `AdvanceImports` (`launchroom:transfers:tick` every minute, and right away when a safety snapshot or task finishes): safety snapshot done → `holding` (dependents with `stop_dependents`, the service itself for volumes; `RestoreHolds` includes import runs) → once released or after `restore_hold_wait_seconds` the task is created → `importing` → result; the task's end releases the holds.
- **URL secrets**: the URL is sealed to the target server for a pre-generated task id when the user starts the run (`sealed_source`, `$hidden`), moved into the task spec when the task is created and wiped from the run. The dashboard can't open it again; the display label never has user or password.
- **Inspections** are `db_import`/`volume_import` tasks with mode `inspect`, started by the import dialog (and by "Check connection" with the sealed URL), remembered for 10 minutes per instance and user; their result is shown before anything is chosen.
- **Exports**: `StartExport` (backups.manage, recent password) creates the download transfer (`receiving`) and the task; daemon chunks fill it; the task's completion checks size, chunk count and digest → `ready` (else failed and deleted). **Download links** (`POST …/exports/{exp}/link`, backups.manage, recent password): a random 256-bit token (`lr_dl_…`) (only its SHA-256 stored), valid for 5 minutes and **one use**, bound to the user who created it; `GET /transfers/download/{token}` (web) and `GET /api/v1/downloads/{token}` (API) stream it with `Content-Length` and `Content-Disposition: attachment; filename="<service>-<YYYYMMDD-HHmm>.<ext>"`. A new link can be made while the export is kept.
- **Permissions**: everything here needs `backups.manage` (owners and admins): an import writes data wholesale (same power as restoring in place), an export takes decrypted data off the platform. Starting an export and making a link also need a password confirmed in the last 15 minutes (inline, 423 + `requiresPassword`). Tokens need the opt-in ability **`data:transfer`** (grants `backups.manage` on the transfer, import and export endpoints only; password-confirmed when the token is created, like `secrets:read`).
- **Audit**: `data.import_started` (source kind, file name and format or URL host, replace, stop dependents), `data.import_finished` (outcome, tables/files, size, duration), `data.import_source_checked` (host), `data.export_started` (live or snapshot), `data.export_downloaded` (size, via token or browser, IP). Never URLs with credentials, never file contents.

### 12.6 Dashboard UX

The Backups tab of a database or a service with volumes gets a **Move data** section (`features/data-transfer/`) with **Import data…** (databases) / **Import files…** (per volume) and **Download now**; a selected backup snapshot offers **Download** next to Restore. Engines without imports say so in one line.

- **Import dialog** (a sheet with steps): *Source* (option cards "From a dump file", default, and "From a connection URL"; the file uploads right away with a progress bar, speed and time left, and resumes after a reload; detected format and version are shown when it's done: "PostgreSQL custom dump · from PostgreSQL 15.8 · 220 MB"; the URL has **Check connection**), *Target* (from the inspection: "postgres is empty" or "postgres has 14 tables (48 MB)": then "Replace everything" or Cancel; for volumes "Replace contents" or "Merge", strip the top folder when the archive has a single one, owner "Keep from the archive" or UID:GID with the volume's current owner as default; the services that will stop, with "Stop umami while importing" on by default), *Review* ("What will happen", numbered: safety snapshot, stop umami, drop and recreate, import the file, start umami again), typed confirmation when replacing.
- **Runs** appear as rows in the section with live steps (Uploaded · Safety snapshot · Stopping apps · Fetching on <server> · Importing · Done) and the outcome ("Imported 14 tables · 48 MB · in 1m 13s", warnings, or the error with "Try again"), and in History.
- **Download**: password prompt inline when needed, then "Preparing download · 120 MB so far", then **Download <file> (412 MB)**; the button makes a fresh one-time link each time.

### 12.7 API and CLI

`/api/v1` (ability `data:transfer`): `POST environments/{env}/services/{svc}/transfers` `{purpose, fileName, sizeBytes, volume?}` → transfer; `GET transfers/{dtr}`; `PUT transfers/{dtr}/chunks/{n}` (raw body, `X-Chunk-Sha256`); `POST transfers/{dtr}/complete` → detected format; `DELETE transfers/{dtr}`; `POST environments/{env}/services/{svc}/imports` `{transfer, replace, stopDependents, confirmation?, volume?, stripComponents?, owner?}`; `GET imports/{imp}`; `POST environments/{env}/services/{svc}/exports` `{volume?, snapshot?}`; `GET exports/{exp}`; `POST exports/{exp}/link` → `{url, expiresAt}`; `GET downloads/{token}`.

CLI: `launchroom db import <service> <file> [--replace] [--keep-apps-running] [--yes]` (uploads with progress and resumes, then follows the run), `launchroom db export <service> [-o file] [--backup <snapshot>]`, `launchroom volume export <service> <mount path|vol_…> [-o file] [--backup <snapshot>]` (downloads to `<file>.part`, renames when complete and the size matches). Replacing asks for the service name on a terminal (`--yes` skips; without a terminal it refuses, exit 2).

### 12.8 Limits

- The file must fit on the control-plane server's disk while it is imported (and once more on the target server while launchroomd reads it).
- MySQL dumps with users, `--all-databases` or several databases are refused; MariaDB-only syntax (system-versioned tables, `uca1400` collations) fails in MySQL with MySQL's own error.
- A URL import needs the source to be reachable from the target server's environment network: private and mesh addresses are blocked like for apps (use a dump file, or allow the range locally with `LR_FIREWALL_ALLOW_PRIVATE`).
- Point-in-time downloads, Redis/Valkey and ClickHouse imports and volume imports from a URL are not supported.

## 13. Move to a new server (D56)

Moving everything on a running server to another machine, including the dashboard's own server, without losing data. The case that drove it: install launchroom on a temporary cloud VPS, move apps there from another platform (D55), then move the whole install (dashboard, apps, databases, volumes, domains) to the final VPS, which may have another CPU architecture, and delete the temporary one. User guide: [Move launchroom to a new server](https://launchroom.vantezzen.io/docs/migrate/move-to-a-new-server).

### 13.1 Why a move is not a restore

| | Restore (§5.2, §5.3, §9.14) | Move (this section) |
|---|---|---|
| Source server | gone (unreachable, offline) | online, keeps serving until each service's turn |
| Data | the latest backup: writes after it are lost | copied live after its writers stopped: nothing lost |
| Needs a backup destination (S3) | yes | no; a fresh backup first is optional |
| Downtime | until restored | stateless: none; each database or volume: its own copy |
| Dashboard | `install.sh --restore` + recovery mode | `install.sh --move` + a short write freeze |

Neither move requires S3. Data travels through the dashboard with D55's transfers.

### 13.2 Server moves

Servers → (server) → **Move to another server** (`/servers/{srv}/move`, ServerPolicy `move` = ManageServers; starting and retiring need a recent password and the source's name typed). The source must be online and not the control plane (that one moves through Settings → Move launchroom, §13.4).

**Data.** `server_moves` (`smv_`): `source_server_id`, `target_server_id`, `control_plane`, `status` (`ServerMoveStatus`: `running → ready → completed`, `running | ready → cancelling → cancelled`, `ready → running` when a failed item is retried), `options.backupFirst`, `plan` (platforms, downtime, copy size, warnings, DNS records as they were at the start), `edge_added`. At most one open move per source (partial unique index); a server that is part of an open move, as source or target, can't be part of another. `server_move_items` (`smi_`): one per service instance with a workload or a volume on the source, `kind`, `position`, `status` (`MoveItemStatus`), `failed_step`, `message`, `expected_bytes` (the latest backup's size), `copied_bytes`, `deployment_id`, `prebuild_deployment_id`, `backup_run_id`, `transfers` (per volume: `{volume, backup, export, import}` public ids), `target_version`, `attempts`, `stopped_at`, `cutover_at`.

**Plan** (`App\Services\Moves\MovePlanner`, shown before the start and checked again under a lock by `StartServerMove`):

- Item kinds (`MoveItemKind`):
  - `stateless`: no volume on the source. Redeployed (`RedeployService`); the rolling update keeps the old replica serving until the new one is healthy.
  - `dump`: Postgres, MySQL/MariaDB, MongoDB (`ImportTarget::IMPORTABLE`). A logical dump (`db_export` live → `db_import`), because it loads across CPU architectures and engine builds; copying a data directory between amd64 and arm64 is not safe for every engine.
  - `files`: services with volumes, and the data volume of engines without an import (Redis, Valkey, ClickHouse). A tarball of the stopped volume (`volume_export` → `volume_import`, replace).
- Order: stateless apps, then their workers and crons (they reuse the app's new image), then databases, then services with volumes. Stateful items move one at a time, so only one copy passes through the dashboard's disk at a time.
- Expected downtime of a stateful item: `45 s + 2 × size / 20 MB/s` (export and import at an assumed 20 MB/s, plus stopping and starting), from the latest successful backup's size; unknown without a backup (the plan says so).
- Blockers: source not online, revoked or pending; source is the control plane outside a control-plane move; either server already part of a move; target not online, replaced, or without the runtime role (or unable to take it, `HostRoleLimits`); launchroomd on the source or target without `dataTransfer` (stateful items) or on the target without `preparedVolumes` (files items); private network off or a server not joined yet; a restore or import running into a stateful service; the target's free Docker disk below the data + 1 GiB; the dashboard's transfers disk below the largest copy + 1 GiB; the source is the only edge and the target can't be an edge; an architecture change with no build server for the target's platform (§13.3).
- Warnings: unknown sizes, the architecture change, and generated `….sslip.io` addresses that contain the source's IP (they stop resolving to a server once the source is gone; set a platform domain or custom domains).
- DNS (only when the source is an edge): the dashboard's host (control-plane move, unless local or sslip), `*.<apps domain>` and every custom domain, each with the addresses it should point at after the move and the source's addresses to remove; live checks (`DnsCheck`) are a deferred prop. DNS is never changed by launchroom.

**Start** (`StartServerMove`, one transaction, audited `server.move_started`): when the source is the team's only edge, the target gets the edge role first (`UpdateServerRoles`; the move records `edge_added`); the items are created; every mesh server re-renders.

**Draining.** While a move is `running` or `ready`, its source drains (`App\Services\Moves\MovingServers`, `SchedulableServer::draining`): `Scheduler::rejection` refuses it ("being moved to another server") for everything except a stateful request pinned to it by its volume. An allow-list that names the source also allows the target (`Placer::request`), so a service limited to the source moves along. Builds route to the target's platform the same way (`BuildRouting::platformFor` uses the scheduler's rejections).

**Steps of a stateful item** (`AdvanceServerMoves`, run right after the start, from `launchroom:moves:tick` every 15 s, and from `AdvanceServerMovesJob` when an export, import, backup task or a deployment finishes):

1. `pending` → `building` when the image must be rebuilt for the target's platform (§13.3), → `backing_up` with **Back up first** (`TakeSafetySnapshot` for databases, `StartVolumeBackup` per volume, reason `pre_move`; a failed backup fails the item, nothing changed), → `stopping`.
2. `stopping`: the writers are held (`MoveHolds`, part of `RestoreHolds::instanceIds()`): for `dump` the services connected to the database in its environment, for `files` the service itself and, for a database, its connected services. Their workloads leave the NodeStates and launchroomd stops them. The next step starts once none reports up, or after `restore_hold_wait_seconds` (120 s).
3. `exporting`: `db_export` of the running database, or `volume_export` (`live`; nothing writes) of each volume on the source, into download transfers; one `data_export_runs` row each, so they show in the service's history. A failed export fails the item; the writers start again on the source.
4. **Cutover**: the instance's placements on the source are deleted, its volume rows point at the target. The source's Docker volume is never touched (launchroomd never deletes undeclared volumes), so it is the rollback copy.
5. `preparing`: `dump` redeploys the database, which starts empty on the target (its connected services stay held); `files` keeps the service held and its volumes are declared on the target without a workload (`MoveHolds::preparedVolumes` → `NodeStateContent`, only for servers with the daemon feature `preparedVolumes`, which creates NodeState volumes no workload mounts, without an owner label). It waits for the deployment to be active, or for the target to report the NodeState version that declares the volumes (10 min, else roll back).
6. `importing`: one `data_import_runs` row per transfer, `replace` (a retry imports over a partial copy), into the target, from the same transfer: `DaemonTransfers::readable` lets an import task read a download transfer it references. Advanced by `AdvanceImports` as usual.
7. `files` → `starting`: the service is redeployed on the target, with its data. `dump` is done right after the import: its connected services start again against the target.

**Rollback.** A failure from `preparing` on (or a cancel) puts the item in `rolling_back`: pending imports are cancelled, the target's placements go, the volume rows return to the source, and the service is redeployed there on the data it had when it stopped; then `failed` (with the reason and "It runs on <source> again") or `rolled_back`. A failure before the cutover changes nothing on the source. **Retry** (`RetryMoveItem`, audited `server.move_item_retried`) starts a failed item from the beginning. Stateless items fail without downtime (the old replica keeps serving) and are retried the same way. A service removed meanwhile is `skipped`.

**Cancel** (`CancelServerMove`, audited `server.move_cancelled`): items not stopped yet are `cancelled`; an item being copied is rolled back; items that already run on the target stay there; the source stops draining once nothing is active. The edge role added to the target stays.

**Retire** (`RetireMovedServer`, only when `ready`, audited `server.move_completed`; `App\Services\Moves\ServerRetirement`, shared with §13.4): refused while a current service still has a serving placement or a volume on the source. The target takes the source's roles and labels (its own labels win; allow-lists naming the source stand for it through `replaced_by_server_id`); the source gets an empty decommission NodeState, is revoked (`RevokeServer`) and marked replaced, like §9.14. Its Docker volumes stay on its disk.

Audit: `server.move_started`, `server.move_item_finished` (kind, copied bytes, downtime from stop to done, attempts), `server.move_item_retried`, `server.move_cancelled` (requested, finished), `server.move_completed`.

### 13.3 CPU architecture changes

Built images are single-platform (D29); the plan compares the source's and the target's platform (`ServerPlatform`).

- **Apps built from source, stateless**: the redeploy of step 1 routes the build to the target's platform (the draining source is no longer a candidate) and rolls out when the image exists. The build happens before the switch, so there is no downtime.
- **Apps built from source with a volume**: before the service stops, `PrebuildForPlatform` creates a deployment at the active commit with `plan.prebuildFor = <platform>` (`App\Services\Moves\Prebuilds`): `BuildRouting` builds it for that platform, and after the build `AdvanceDeployment` ends it as `superseded` without rolling out. The deployment on the target then reuses the image (same build key, `TaskBuildOrchestrator::reusable`), so the build is not part of the downtime. A prebuild replaced by another deployment is started again.
- **Workers and crons** run their app's image and follow it.
- **Databases and template images** run by multi-arch index digest through the registry mirror and are pulled for the target's platform. An image service whose image only exists for the source's platform fails to start on the target; the item rolls back.
- The plan refuses the move when no online build server builds the target's platform (natively or emulated, D53) and something needs a rebuild.

### 13.4 Moving the control plane

Settings → **Move launchroom** (instance owners; changes need a recent password). The new machine installs with `install.sh --move <token>`, joins this dashboard as a regular server, everything moves onto it like a server move, then the dashboard itself is handed over during a short write freeze.

**Why this design.** A restore from the latest backup loses everything written after it and needs S3. Copying the old server's data directories is unsafe across architectures and while services write. Copying Zot's storage is large and slow, and every image can be rebuilt or re-pulled. Joining first means the new machine is a known, signed server before anything moves; the workloads move with the same tested steps as any server; the only part unique to the control plane is its own database and keys, which are small, so the freeze is short.

**Data.** `control_plane_moves` (`cpm_`, instance level, at most one open): `status` (`ControlPlaneMoveStatus`: `waiting_for_server → claimed → joining → joined → moving ⇄ ready_to_hand_over → handing_over → handover_ready → handed_over`; `cancelled` before the hand-over; `handing_over | handover_ready → ready_to_hand_over` when the hand-over is aborted), `source_server_id`, `target_server_id`, `server_move_id`, `token_hash`, `token_expires_at`, `receiver_public_key` (X25519), `claim_code`, `receiver` (hostname, arch, address), `receiver_seen_at`, `enrollment_id`, `sealed_join_token`, `handover` (the manifest), `frozen_at`, `handed_over_at`, `new_url`; secrets and the manifest are `$hidden`. `instance_settings`: `frozen_at`, `frozen_reason`, `moved_to`, `move_checklist`.

**Steps:**

1. **Token** (`StartControlPlaneMove`, audited `instance.control_plane_move_started`): refused in recovery mode, while the dashboard's server is offline or part of a server move. The token (`App\Services\Moves\MoveToken`) is `lrmv1.<base64url URL>.<cpm_…>.<base64url 32-byte secret>.<base64url Ed25519 public key>`: the dashboard's canonical origin, the move, the secret (stored as SHA-256 only) and the control plane's signing key. It is shown once, inside the command (with `--version <current release>` so both run the same release), and stops working after 24 h without a claim or when the move ends.
2. **Claim** (`POST /move/v1/claim`, `ClaimControlPlaneMove`, audited): the new machine's `launchroom:move:receive --join` makes an X25519 key pair (kept 0600 in `data/backups/move`) and sends the secret, its public key and host facts. Both sides compute the code `XXXX-XXXX` from SHA-256 over the move id and the public key; the installer prints it and the owner types it into the page, which never shows it (a page that showed it could be confirmed without looking at the terminal, which defeats the check). A second claim with another key is refused, so a real machine that loses the race sees an error, not a code.
3. **Approve** (`ApproveControlPlaneMove`, typed code, audited): a join token for the roles of the dashboard's server (edge, runtime, build), sealed to the receiver key (`crypto_box_seal`) and served once while `joining`. The new machine's launchroomd enrolls with the old dashboard (`LR_CONTROL_PLANE_URL` = the old address, its pinned `cp-key` = the token's key) and is approved right away (`AdvanceControlPlaneMoves`).
4. **Move** (`MoveControlPlaneWorkloads`): a server move from the dashboard's server to the new one with `control_plane = true` (§13.2; cancelled only from Settings, never retired, the hand-over replaces the retire step). Once it is `ready`, the move is `ready_to_hand_over`.
5. **Hand over** (`StartHandover`, typed "hand over", audited `instance.control_plane_handover_started`): refused unless the new machine's installer asked within 90 s and no deployment, build, backup, restore, import, export or other server move is in flight. It freezes writes and queues `PrepareHandoverJob`:
   - `pg_dump --format=custom` of the dashboard's database (`ControlPlaneDatabase`, through `PostgresClient`) into 8 MiB chunks, each `nonce || XChaCha20-Poly1305(chunk)` with associated data `launchroom-handover|<cpm>|<n>`, under a fresh key that exists only in memory, written to `<transfers>/<cpm_…>/` (`HandoverStore`);
   - the key bundle (`ControlPlaneKeyBundle::collect()`: APP_KEY, KEK, signing and registry keys, Reverb secrets, Headscale's state), sealed to the receiver key, next to the chunks;
   - the manifest: chunk count and size, per-chunk SHA-256 and the digest over them, the chunk key sealed to the receiver, the sealed bundle's SHA-256, `appUrl` and `canonicalUrl`.
   This dashboard can't open any of it afterwards. A failure thaws the dashboard and returns to `ready_to_hand_over` with the reason.
6. **Receive** (`launchroom:move:receive --handover`, on the new machine): every answer is verified against the pinned key before use; the sealed bundle must match the manifest and its signing key must be the pinned one; chunks are fetched one by one, opened, checked against their digests and streamed straight into `pg_restore --clean --if-exists --single-transaction` (`ControlPlaneDatabase::restore`); the keys are written with `RestoredKeyFiles` like `launchroom:restore`. On failure the installer calls `abort`.
7. **Take over** (`launchroom:move:takeover`, `TakeOverControlPlane`, audited `instance.control_plane_taken_over`): in the restored database (where the dump caught the move as `handing_over`) the new server becomes the control-plane server, the old one is retired (`ServerRetirement`: roles and labels move, empty state, revoked), the server move completes, the freeze is lifted, the move is `handed_over`, every server re-renders. Active deployments whose image isn't in this registry are marked lost (`build_key` cleared, `image_pruned_at`), so their next deploy builds from the recorded commit. When the address changed, `recovery_kit_confirmed_at` is cleared (the kit names the address). `move_checklist` opens the checklist.
8. **Complete** (`POST /move/v1/{cpm}/complete`, `CompleteHandover`, audited `instance.control_plane_handed_over`): the old dashboard stays frozen for good and records `moved_to`; every page there shows "launchroom moved" with the new address. The hand-over files are deleted.

**Freeze** (`InstanceFreeze`, `RespectInstanceFreeze`): web form writes are refused with "launchroom is moving to a new server. Changes are paused for a few minutes." (signing in and out and Settings → Move launchroom still work); the API, git webhooks and the CLI endpoints answer 503 with `Retry-After`; every scheduled command is skipped; launchroomd's endpoints, the move endpoints, `/up`, the registry realm and the installer always pass. Apps keep serving: launchroomd keeps its last desired state, and by now everything runs on the new server. A push during the freeze doesn't deploy; push again or deploy by hand afterwards.

**Abort** (`AbortHandover`, from the page or the installer): only before the new dashboard runs. The installer starts the new stack only after the restore succeeded and reports `complete` right after the takeover; aborting later would leave two dashboards giving orders to the same servers. After `complete` the way back is moving again.

**Addresses.**
- `APP_URL` on the new machine (`restored_app_url` in the installer): a domain of your own is kept and pointed at the new server's IP; an IP address or `<ip>.sslip.io` becomes the new server's (detected again, or `--domain`). A domain chosen in Settings → Dashboard domain is data and comes along (D43).
- Other servers reconnect by themselves when their address is a domain: same signing key, and DNS now points at the new server. With an IP-bound address each needs `LR_CONTROL_PLANE_URL` changed, as after a restore (§5.2 step 4); the pre-flight warns about it.
- Headscale's state comes with the key bundle, so mesh nodes keep their identity.
- Certificates aren't copied: the new edge gets them from ACME once DNS points there (HTTP-01; DNS-01 credentials are in the database).

**Registry.** Zot's storage isn't copied. Running containers keep their images in Docker's local store (image references are always `127.0.0.1:5000/…@sha256:…`, the same on every server), so nothing is pulled at the takeover. Images not in the new registry are marked lost and rebuilt from their commit on the next deploy, or all at once with **Rebuild now** in the checklist (`RebuildMissingImages`); mirrored images are mirrored again on demand. With registry storage on S3 (§9.11) nothing is lost.

**Checklist** (`App\Queries\MoveChecklist`, on the new dashboard until **Finish**, audited `instance.control_plane_move_finished`): DNS of the dashboard, the apps wildcard and custom domains (live checks against the edge addresses), images missing from the registry, other servers seen since the takeover, the old machine (delete it or run `./launchroom uninstall` there), a new recovery kit when needed.

**Expected downtime**

| Step | Downtime |
|---|---|
| Joining, plan | none |
| Stateless services | none (rolling) |
| Each database or volume | its own stop: about `45 s + 2 × size / 20 MB/s`; its connected apps stop with it |
| Hand-over (dashboard) | the freeze: dump + transfer + restore + stack start, typically 1–3 minutes for a small instance; apps keep serving |
| Dashboard address | until DNS points at the new server (lower the TTL beforehand) |

### 13.5 Recovery if something goes wrong midway

| Stage | What happens | What to do |
|---|---|---|
| Before the claim or approval | nothing changed | Cancel the move; start again |
| A stateless service fails | it keeps running on the source | Retry, or cancel |
| A stateful service fails before its cutover | nothing changed; its apps start again | Retry |
| A stateful service fails after its cutover | it is rolled back onto the source's untouched volume | Retry |
| Workloads moved, before the hand-over | moved services run on the new server, the rest on the old | Continue, or cancel (moved services stay where they are) |
| The final dump fails | the dashboard thaws, the move is ready to hand over again | Hand over again |
| The new machine can't restore | the installer aborts, the dashboard thaws | Fix the cause, run the install command again |
| The installer stops after the restore | the new dashboard has the data but didn't take over | `./launchroom move-takeover` on the new machine |
| The new machine couldn't report `complete` | the old dashboard stays frozen | Nothing; delete the old machine once DNS points at the new one |
| After the hand-over | the new server is the control plane; the old machine still holds its data | Moving back means moving again |

### 13.6 Tests

- Pest: plans and refusals (`MovePlanner`), state machines (`ServerMoveStatus`, `MoveItemStatus`, `ControlPlaneMoveStatus`), policies, the server move steps and rollbacks, the control-plane move endpoints (token, claim code, signatures, sealing), freeze middleware, takeover.
- launchroomd: `TestDiffVolumeOwnership` (prepared, owner-less volumes are created; system names never), `TestFindVolumeAcceptsPreparedVolumesOnly` (imports, exports and backups find a prepared volume, never a system one). The registry forwarder is synced before the reconciler on every pass (`syncRegistry`), so the first state that brings workloads and names the registry doesn't race the pulls.
- `make test-move` (`deploy/test/e2e-move.sh`, [11](11-installation-and-dev.md) §2.4a): both moves against fresh dind VPSes.
- **Verified (2026-10-21, `make test-move` PASS):** the control plane with Postgres, an app and its volume moved from VPS A to B: rows and a file written right before the move and a dashboard change right before the hand-over arrived; apps and data in 49 s (longest stop 31 s), the hand-over 34 s; B serves the dashboard at the same domain and the app through its edge; A is frozen and decommissioned. A regular server moved C → D in 42 s with its data, then was retired.
- **Verified in dev** (real launchroomd on the fake servers): server-2 → server-3 moved 3 apps without downtime and two Postgres databases, a MongoDB and two volume services (Uptime Kuma, Meilisearch) with their data; one app failed to rebuild (a dev git fixture's missing commit) and stayed on server-2 with Retry offered.
