# launchroom: contributor docs

launchroom is **one place to deploy**: open source, on servers you choose, yours end to end. Apps, databases, previews and environments live on one canvas; any server (one VPS or sixty, a build machine at home) joins with one command; nothing is written outside a single folder.

These docs describe how launchroom is built: architecture, protocol, decisions and conventions. User docs (install, servers, projects, builds, databases, API and CLI) live on the website, [launchroom.vantezzen.io/docs](https://launchroom.vantezzen.io/docs), built from `site/` ([21](21-website.md)).

Read the doc for the area you touch before changing code. If a change contradicts a doc, update the doc in the same change.

## The one-paragraph version

A **dashboard** (Laravel) holds all intent: teams, projects, environments, services, variables, domains and deployments. Every server, including the dashboard's own, runs **launchroomd** (Go), the launchroom daemon. launchroomd dials out to the dashboard, receives a **signed desired state** for its server, and reconciles Docker containers, Caddy routes, networks and firewall rules to match. Builds are tasks leased by daemons with the build role. They clone the repo, plan with **Railpack** plus our framework presets (or use the repo's Dockerfile), build with **BuildKit**, and push an immutable image to the embedded **Zot** registry. Deploying means changing desired state: launchroomd starts new containers, health-checks them from outside, flips Caddy upstreams and drains the old ones. A single server needs no mesh. When a second server joins, the dashboard enables **Headscale**, servers connect over WireGuard (even behind home NAT), and daemon-embedded ambassadors let `api` on server B reach `postgres` on server A by its usual name. Joining the mesh grants nothing: every daemon command is signed by the dashboard, and every daemon request is signed by launchroomd's own key.
