# 05: Networking & ingress

## 1. Networks on a single server

- **One Docker bridge network per (project, environment)**: `lr-e_<hash>`, with a subnet allocated by the dashboard from launchroom's own range (default `10.231.0.0/16`, carved into /24s). Allocation (`App\Services\Projects\EnvironmentSubnets`): lowest free /24 under a transaction advisory lock, unique index as backstop; `LAUNCHROOM_ENVIRONMENT_RANGE` configures the range. The network id in NodeStates is `net_` + the environment's ULID, its name `lr-e_` + 16 hex of sha256(environment id). Allocating explicit subnets avoids exhausting Docker's default address pool (a real-world failure at ~30 networks) **without editing `daemon.json`**. The range is configurable at install for clashes with LANs or VPNs.
- Services in the same environment reach each other by **service slug** through Docker's embedded DNS (`api`, `postgres`, `redis`), exactly like Compose. Environments are isolated: preview `pr-42`'s `postgres` is not production's.
- Caddy (edge) runs with the **host network** and proxies to container IPs on the environment bridges directly (the host can route to every local bridge), so it never joins any Docker network, app or infra (§4).
- launchroom's own control-plane containers (dashboard, postgres, valkey, zot) live on a separate `lr-system` network that app networks cannot reach. nftables rules also block app containers from:
  - the host's daemon and admin ports
  - the mesh range (`100.64.0.0/10`, `fd7a:115c:a1e0::/48`)
  - cloud metadata (`169.254.169.254`)
  - the registry
  - the control plane

  launchroomd installs these rules and re-checks them for drift.

**Firewall (launchroomd `internal/firewall`).**
- **Own table, not `DOCKER-USER`.** launchroomd owns one nftables table, `inet launchroom`, programmed over netlink with `github.com/google/nftables` (no `nft`/`iptables` binary). Base chains `forward` and `input` hook at priority `-10`. An nftables `drop` is final for the packet in every table and on every hook, so a separate table works the same whether Docker uses iptables-legacy, iptables-nft (Docker 29's default `firewall-backend: iptables`) or its native nftables backend, and Docker never flushes it. `DOCKER-USER` would only exist with the iptables backends and is flushed/recreated by Docker.
- **Scope: launchroom bridges only.** Rules match the *input interface* (the bridge of every managed `lr-e_…` network and of `lr-system-build`, discovered from Docker: `com.docker.network.bridge.name` or `br-<id[:12]>`), not source addresses, so a container spoofing its source IP is still filtered. Other Docker networks (the control plane's `lr-system`, users' own containers) are not filtered.
- **Workloads and builds (`forward` → `egress`)**, in order: same bridge → accept (containers of one environment reach each other; Docker's `br_netfilter` passes bridged traffic through this hook); `ct state established,related` → accept; DNS (udp/tcp 53, any destination: Docker's embedded resolver forwards from the container's namespace to the host's upstreams, which are often on the LAN or the metadata address, e.g. GCP's `169.254.169.254:53`) → accept; metadata `169.254.0.0/16`, `fd00:ec2::254`, `fe80::/10` → drop; mesh `100.64.0.0/10`, `fd7a:115c:a1e0::/48` → drop; any other launchroom bridge (inter-environment) → drop; any other Docker bridge (`br-*`, `docker0`) → drop; the local allow-list `LR_FIREWALL_ALLOW_PRIVATE` → accept; RFC 1918, `0.0.0.0/8`, loopback, `192.0.0.0/24`, `198.18.0.0/15`, multicast and `240.0.0.0/4`, `::1`, `fc00::/7`, `ff00::/8` → drop; everything else (the internet) → accept.
- **Host addresses (`input` → `host`)**: `established,related` → accept (replies to Caddy and launchroomd's health probes); metadata and mesh destinations → drop (a local metadata proxy, the host's own `tailscale0` address); DNS → accept; tcp 80/443 and udp 443 (Caddy's public ingress, so apps can call another app's public URL on the same server) → accept; everything else → drop: launchroomd's ask endpoint (2021), Caddy's admin API (2019), the registry forwarder (5000), sshd, databases on the host. The one exception is the build network's gateway `tcp 5000` (buildkitd → launchroomd's registry forwarder).
- **Not filtered**: host → containers (Caddy upstreams, health probes, `run_once` log streaming) runs on the output hook and is untouched.
- **Applied and checked**: at daemon start, on every reconcile pass (after new networks are created, before any container is created or started), right after buildkitd (re)creates its network, before each build's solve and before each `run_once` container. The live table is compared with the expected one (chains, hooks, priority, policy, and per chain the rules in order by their comment, which is the rule's `nft` text); any difference is repaired by replacing the whole table in one netlink transaction (add, delete, add: there is never a window without rules). Repairs of drift (rules changed by something else) are logged and counted in `HostHealth.firewall.repairs`.
- **Fail closed**: while the table cannot be applied, launchroomd creates and starts no workloads, runs no builds and no `run_once` containers; existing containers keep running. Status `HostHealth.firewall.mode` = `enforced` | `disabled` | `error`.
- **Local config only**: `LR_FIREWALL=enforce` (default) or `off` (hosts without nftables; reported as `disabled`); `LR_FIREWALL_ALLOW_PRIVATE` = comma-separated CIDRs (e.g. a NAS on the LAN). The allow-list cannot open metadata, the mesh, other environments, other Docker networks or host ports.
- **macOS servers** (D53, [11](11-installation-and-dev.md) §3.3): launchroomd runs in the engine's Linux VM (OrbStack, Docker Desktop, Colima), so the table lives in the VM's kernel, which is where every container, bridge and the mesh interface are: the rules work unchanged. The Mac itself is outside the VM and untouched (its own firewall stays the user's). The VM's ways back to the Mac (`host.docker.internal`: Docker Desktop `192.168.65.254`, OrbStack `0.250.250.254`, lima/Colima `192.168.5.2`) are RFC 1918 or `0.0.0.0/8` addresses, which `egress` already drops, so apps can't reach services listening on the Mac.
- **Uninstall**: the table is kernel state (gone after a reboot). `./launchroom uninstall` removes it with a one-off `daemon firewall remove`; on daemon-only servers run `docker compose run --rm daemon firewall remove` before deleting the folder. Stopping launchroomd leaves the rules in place on purpose: the containers keep running.
- **Mesh interface**: packets arriving from mesh peers on `tailscale0` are filtered too: `input` → `iifname "tailscale0" jump mesh-host` (established → accept; tcp 443 and tcp 5000 → accept; everything else → drop, so a peer never reaches sshd, Caddy's admin API or a database on the host, even with a permissive "bring your own Tailscale" ACL), and `forward` → `iifname "tailscale0" jump mesh-forward` (established → accept; drop). The host's own traffic over the mesh (launchroomd's registry forwarder, its API calls, Caddy's upstreams) is outbound and unfiltered; containers stay blocked from the mesh range by `egress`.
- **Mesh-published ports and per-peer allow-lists**: a base chain `prerouting` (priority `-150`: after conntrack, **before Docker's DNAT** at `-100`, so it still sees the published port) jumps `iifname "tailscale0"` to `mesh-published`, the gate for every new connection from a peer: established → accept; the `mesh-host` ports (tcp 443, 5000, and 6379 from `system.certStorage.allowFrom`) → accept; per `firewall.meshAllow` rule and peer `ip saddr <peer>/32 ip daddr <own mesh IP>/32 tcp dport <port>` → accept; everything else → drop. WireGuard binds a peer's source IP to its key, so the source is authenticated. `mesh-forward` then accepts only established connections and connections Docker DNATed (`ct status dnat`) after that gate; anything else forwarded from the mesh is dropped. Without a known mesh IP no published port is allowed. Only mesh addresses are accepted as peers (local policy). The gate sits in prerouting instead of using `ct original` matches because `github.com/google/nftables` v0.3.0 can't read back the conntrack direction attribute, which breaks drift detection.
- **Ambassador network**: the ambassador's own bridge `lr-system-ambassador` (§3) gets `forward`/`input` → `iifname <its bridge> jump ambassador`: established → accept; `ip daddr <upstream>/32 tcp dport <port>` for every listed upstream → accept; drop (no DNS, no internet, no host port). The ambassador reaches the mesh only through this bridge; environment bridges keep dropping the mesh range, so the exception is exactly "this one container, these upstreams". Tested in a real kernel with a real Headscale and kernel-mode Tailscale clients by `TestCrossServerMesh` (ITEST): a published workload waits for the mesh address, is bound only to it, is reachable from the allowed peer and not from another runtime peer the ACL lets through, allow-list changes apply without touching the container, the ambassador serves a remote service by alias while workloads still can't reach the mesh directly, a container started while the mesh is down is recreated and published again, and an environment network is removed in one pass while the ambassador is attached (launchroomd detaches it first).
- Tested in a real kernel by `TestFirewallIsolation` (dind-test, Docker 29 with the default iptables-nft backend; also run once by hand against a Docker 29 daemon with `--firewall-backend=nftables`): workloads and builds cannot reach a metadata address (local and on another bridge), another environment, another Docker network or host admin ports; they reach their own network, DNS, the internet and the host's ingress port; builds reach the registry forwarder; the host reaches containers; a deleted table is repaired; new networks are covered.

### 1.1 Volume lifecycle (deleted environments, projects, previews)

Volumes hold data, so they are **never deleted because they left the desired state** (a NodeState without them only means "don't create or mount them"). Deletion is explicit and late:

1. **Retire** (dashboard, `App\Services\Volumes\VolumeRetirements`): deleting an environment (also a preview teardown) or a project records a `volume_retirements` row for every placed volume before the rows go: volume id, Docker name, service and environment ids, label, reason (`environment_deleted`, `project_deleted`, `preview_destroyed`), `retain_until` = now + `launchroom.volumes.retention_hours` (default 7 days; `preview_retention_hours` for previews, default 7 days, `0` = delete at the next sweep; env `LAUNCHROOM_VOLUME_RETENTION_HOURS`, `LAUNCHROOM_PREVIEW_VOLUME_RETENTION_HOURS`).
2. **Backups gate: a final backup** ([14](14-backup-and-restore.md) §9.13): when the service had backups (a successful run or an enabled schedule), the deletion itself first takes a **final backup** while the workloads still run (a database dump for databases, a volume snapshot for every other service's volumes) and waits for it; only then are the workloads torn down and the retirement records the snapshot (`final_backup_snapshot`). If the final backup fails or can't start, nothing is deleted and the deletion is blocked with the reason until it is retried or an owner/admin chooses **"Delete without final backup"** (audited `backup.final_backup_skipped`), which is recorded as `confirmed_at`/`confirmed_by`. A retired backed-up volume is deleted once its retention passed and it has a final snapshot or that override. Volumes retired before final backups existed keep the old manual gate: an admin allows the deletion on the server page ("Retired volumes" → "Allow deletion", audited `server.volume_deletion_confirmed`). Snapshots stay in the destination either way.
3. **Request** (`launchroom:volumes:retire`, every 15 min): due retirements (retention passed, gate satisfied) become `requested`; their servers re-render. The NodeState then carries `deleteVolumes: [{id, name, service, environment, requestedAt}]` (optional field, only sent when non-empty; never a volume the same NodeState still declares).
4. **Delete** (launchroomd, `internal/reconcile/volumes.go`, after the pass removed undesired containers): only a volume that is managed by this server, whose `launchroom.volume`/`service`/`environment` labels match the request exactly, that is not declared in the NodeState and that no container uses (a one-off task container counts) is removed, never forced (Docker's own in-use check is the last line). Outcomes are reported in `Report.volumeDeletions` (`deleted`, `absent` = no managed volume of that name, `refused` with the reason, `failed`); refused and failed ones are retried on later passes. `deleted`/`absent` finish the retirement (`deleted`), and the next render drops the request.

The server page lists retired volumes (kept, needs confirmation, deleting, not deleted yet with the daemon's reason, deleted in the last 7 days).

## 2. Mesh (multi-server)

**Headscale with embedded DERP, running in the control-plane stack; stock `tailscale/tailscale` on each server, run by launchroomd as a system container.**

- Off with one server: no server runs a mesh client and no key exists. The `headscale` compose service runs from install on, idle (≈ 30 MB; see "Headscale is a compose service" below). When a **second server is approved** (enrolled without approval, or approved), the dashboard switches the mesh on by itself (`launchroom.mesh.auto_enable`, default on); an instance owner can also do it earlier (Servers → Network settings, `launchroom:mesh:enable`). Every server, the control plane's included, then gets the mesh client in its NodeState.
- Client (`system.tailscale`, launchroomd `internal/mesh`): container `lr-system-tailscale`, image `tailscale/tailscale` v1.104.1 pinned by digest in launchroomd's system-image allow-list (`policy.TailscaleImageDigest`), **kernel mode** (`tailscaled --tun=tailscale0`, host network, `/dev/net/tun`, `cap-drop ALL` + `NET_ADMIN`/`NET_RAW`, no-new-privileges), state in the named volume `lr-system-tailscale-state` (kept across restarts and when the mesh is switched off; a restart needs no key). launchroomd runs tailscaled directly, not containerboot, and logs it in itself: `tailscale up --reset --login-server=<url> --hostname=lr-<server id> --accept-dns=false` (**mandatory**: `/etc/resolv.conf` is never touched) `--accept-routes=false --auth-key=file:/dev/stdin`: the key only travels over the exec's stdin, never argv, env or a file. Status comes from `tailscale status --json` + `tailscale debug prefs` every reconcile pass (30 s) and is reported as `Report.host.mesh` (state, IPv4/IPv6, peers with online/`direct`/`relay`/`idle` and DERP region). A login server change (built-in ↔ own tailnet) re-authenticates (`--force-reauth`). A failed login restarts tailscaled (it otherwise keeps forcing port 443 for a while) and is retried after 30 s. A running client that reports no control connection (`Self.Online = false`) for 1 minute while launchroomd can open a TCP connection to the login server is restarted too (after a coordination-server outage tailscaled can stay disconnected and never learn a restarted peer's new endpoints). While the coordination server is down nothing is restarted: established peer paths keep working without it.
- Login servers: https only; plain http is refused by launchroomd's local policy unless the host is listed in `LR_MESH_INSECURE_LOGIN_HOSTS` (dev only). Tailscale's control client only speaks plain http on port 80.
- Hosts without TUN (some LXC, rootless setups): without `/dev/net/tun` the client container does not start and the server reports mesh state `error` with the reason. Docker Desktop, OrbStack, Colima and dind (privileged) all have TUN.
- **macOS servers** (D53): the client runs in kernel mode inside the engine's VM, so the mesh IP, mesh-published ports and the ambassador work as on Linux (OrbStack, Colima). Its UDP leaves through the VM's NAT and then the home router, so peers usually reach a Mac through the DERP relay (capability `mesh` degraded); that is fine for a build server, which mostly pushes images to the registry. Docker Desktop can't publish on the mesh address (it binds published ports on the Mac, where that address doesn't exist), so a Mac on Docker Desktop builds but runs no apps (capability `workloads`).
- **Keys**: per server a **single-use, tagged, 60-minute** Headscale pre-auth key (`IssueMeshAuthKey`), stored envelope-encrypted in `mesh_credentials` until the server has joined, sealed into its NodeState as `system.tailscale.authKey` (`MeshAuthKey {serverId, authKey}`, `protocol/schema/v1/mesh-auth-key.json`; bound to the server). Once the server's node is linked (below) the key is forgotten and dropped from its state; `launchroom:mesh:maintain` (every 5 min) re-issues keys of servers that haven't joined before they expire. Tags come from the key (Headscale 0.29 refuses `--advertise-tags` with tagged keys): `tag:lr-<role>` per role plus `tag:lr-cp` on the control-plane server. Tagged nodes don't expire. Maintenance keeps each node's tags equal to the server's roles (`SetTags`) and links servers to nodes **by identity**: the node that registered with a pre-auth key issued to that server (`servers.mesh_auth_key_ids`, the last 20; Headscale reports each node's `preAuthKey.id`) becomes `servers.mesh_node_id`, and the server's `mesh_ip`/`mesh_ipv6` are that node's addresses as Headscale reports them. The address a server reports (`Report.host.mesh`) is shown as status only; when it differs, maintenance runs. A key id claimed by two servers links neither; a node registered with an unknown key links no one (a self-reported address could otherwise make the dashboard retag or, on revoke, delete another server's node). Upgrade path: servers linked before key ids were recorded adopt their linked node's key id once.
- **Revocation** (docs/09 R25): revoking a server deletes its Headscale node(s), found by the pre-auth keys issued to it and the linked id, and expires an unused pre-auth key (`RemoveMeshNodeJob`, retried; maintenance deletes leftovers by the same identity).
- **ACL policy** (default deny, `App\Services\Mesh\MeshPolicy`, applied through the API with policy mode `database`, re-applied when it changes):
  - every `tag:lr-*` → `tag:lr-cp:443,5000` (daemon API/ingress, registry);
  - `tag:lr-edge` → `tag:lr-runtime:31000-32999` (mesh-published replicas);
  - `tag:lr-runtime` → `tag:lr-runtime:31000-32999`, further filtered per environment by nftables on the receiving node (`firewall.meshAllow`, §1);
  - `tag:lr-edge` → `tag:lr-cp:6379` (shared certificate storage, §5);
  - every `tag:lr-*` → every `tag:lr-*:7400` (link probes, §2.1; nftables narrows it to the listed peers).
  Tag owners are the dashboard's Headscale user `launchroom`. Verified in dev: server-2 reaches server-1 on 443 and 5000, while 80 (Caddy listens there), 2019 and 22 time out.
- **Dashboard ↔ Headscale**: REST API v0.29 (`App\Services\Mesh\HeadscaleClient`, 3 s connect / 10 s total) at `LAUNCHROOM_HEADSCALE_URL` (`http://headscale:8080` on lr-system). The first API key can only be minted inside the Headscale container, so the installer (and `make up-multi`) pipes it into `launchroom:mesh:bootstrap-key` (stdin → `data/keys/headscale-api-key`, 0600, never printed). On enable the dashboard creates its **own** key (180 days, rotated with 30 days left), stores it envelope-encrypted, expires the bootstrap key in Headscale and deletes the file when it can.
- **Public endpoints**: Headscale's `server_url` is the dashboard's install-time origin (`APP_URL`); it does not follow Settings → Dashboard domain (§4.1). launchroomd's Caddy terminates TLS and routes the host to the dashboard (system route); the dashboard's FrankenPHP forwards `/ts2021` (Tailscale control protocol, an HTTP upgrade), `/key`, `/machine/*`, `/derp`, `/derp/*` (DERP, an upgrade) and `/bootstrap-dns` to `headscale:8080` (`CADDY_SERVER_EXTRA_DIRECTIVES`, like Reverb's `/app/*`). `/api/v1` is never forwarded. Embedded DERP (region `lr`, only our own relay: `derp.urls: []`) runs over that HTTPS port; STUN on udp/3478 is published by the `headscale` service. `make test-install` checks `/key` through Caddy → FrankenPHP → Headscale and that `/api/v1` is not served.
- **Headscale is a compose service, not a daemon-managed system container.** A system container would need to join the compose network `lr-system` (launchroomd only attaches its own objects) and its first API key can only come from `headscale apikeys create` inside it, which the dashboard can't run (it has no Docker access). As a compose service it is reachable on lr-system, its state is a folder in `data/` (part of control-plane backups: keys and database go into the sealed key bundle, so a restored control plane keeps every node, [14](14-backup-and-restore.md) §9.6) and the installer can mint the bootstrap key. "Lazily enabled" therefore means: no clients, keys or policy until a second server joins; the Headscale process itself idles.
- **"Bring your own Tailscale"** (Servers → Network settings, instance owners; `UseOwnTailscale`): a login server (`https://controlplane.tailscale.com` or your own Headscale; https only) and an auth key that may register several servers, stored envelope-encrypted. Only the control plane and servers an **instance owner** enrolled or approved get it sealed into their NodeState until they've joined (it is the owner's tailnet key, and anyone with root on a receiving server can read it; servers a team admin enrolled stay off the tailnet until an instance owner approves them), plus `tags` (`--advertise-tags`, the key must allow them). The tailnet's ACL is yours (the settings page shows the recommended policy); node deletion on revoke is yours too. There is no API to ask, so a server's reported address is taken as its mesh address, but only inside 100.64.0.0/10 and only if no other server has it. launchroomd's `mesh-host` chain still only accepts 443/5000 from the mesh.
- **Requirement**: other servers must be able to reach the main server's HTTPS port (443/TCP; 3478/UDP helps NAT traversal but isn't required, because DERP falls back to 443). This works when the main server is reachable publicly. No manual configuration is needed: no port forwarding on the home side, no IPs to copy, no keys to exchange. The join command carries everything. If no server is reachable at all, the fallback is a small public VPS or "Bring your own Tailscale".
- LAN-only installs (Headscale behind a self-signed or internal-CA certificate) are not supported: launchroomd never mounts a CA into the client.
- UI: the servers list shows a Network column (state, mesh IP; "· direct"/"· relayed" towards the dashboard's server) and the instance's mesh mode; a server's page has a Network section with its address, path to the dashboard's server and peers (named only within the team). "Add server" says that machines at home or behind NAT need no port forwarding.
- **The mesh is transport, not trust.** Joining it lets you send packets to the few ports the ACL allows, nothing more. All authority sits at the application layer ([03](03-daemon-protocol.md), [09](09-security.md)).

### 2.1 Link quality between servers

launchroomd measures the private network between servers so the Servers topology and the server page can show real numbers ("0.4 ms · 480 Mbit/s"), not only direct / relayed / idle.

- **Who measures whom** (`App\Services\NodeStates\LinkProbePeers`): every mesh server with a mesh address, `servers.measure_links` on (per-server opt-out: server page → Settings → "Network checks", audited with the placement settings) and a launchroomd that announced the `linkProbe` feature ([03](03-daemon-protocol.md) §10) gets `system.linkProbe {enabled, peers: [{serverId, ipv4, signingKey}]}`: the other such servers of its team plus the control plane's server (the control plane lists every such server). The relation is symmetric. A change (opt-out, feature, mesh address) re-renders every mesh server.
- **Probe** (`daemon/internal/linkprobe`): launchroomd listens on `<mesh IPv4>:7400` only (never 0.0.0.0) while it has peers. A probe is one TCP connection over WireGuard: the client sends a JSON hello signed with its launchroomd Ed25519 key (domain-separated message with both server ids, time ±60 s, a 128-bit nonce, the operation and size); the server answers only if the sender is a listed peer, the TCP source is that peer's mesh IP, the hello is addressed to it, fresh, unreplayed and correctly signed, and its ack is signed with its own key over the nonce, which the client verifies (both ends prove their identity; keys come from the dashboard-signed NodeState, the source address from WireGuard). Anything else is closed silently. Then either 5 echo rounds of 8 bytes (latency = median round trip) or a download of at most 16 MiB of zeros (rate = bytes / time, partial after 15 s counts if ≥ 1 MiB).
- **Cadence and cost**: latency to every peer every minute (±10 %); a transfer per peer 2–7 minutes after it first appears, then every 6 hours (±10 %), sequentially, never two at once. That is about 64 MiB a day per peer and direction. The server side additionally serves at most one transfer at a time, at most one per peer per 5 minutes, 16 connections at once, 3 s to send the hello. A 16 MiB transfer underestimates links much faster than ~1 Gbit/s (TCP slow start); the number is a calm estimate, not a benchmark.
- **Firewall and ACL**: nftables `mesh-host` (and the `mesh-published` gate) accept tcp 7400 only from the listed peers' mesh IPs; the Headscale ACL allows `tag:lr-* → tag:lr-*:7400` (with "bring your own Tailscale" the recommended policy shows the same rule). Local kill switch: `LR_LINK_PROBE=off`. Peers outside `100.64.0.0/10` are ignored (local policy).
- **Reports and storage**: `Report.host.links` carries the latest measurement per peer (`measuredAt`, `rttMs` or `error`, `throughputMbps` + `throughputAt`) in every report. The dashboard (`RecordLinkQuality`) keeps the latest per direction in `server_links` and hourly rollups in `server_link_samples` (count, failures, sum/min/max, the hour's latest rate), counting each measurement once (only a newer `measuredAt`/`throughputAt` counts), only for peers of the same team or the control plane, nothing from the future or older than a day; `launchroom:links:prune` drops rollups after 30 days.
- **UI**: the topology labels each private link with the round trip (mean of both directions, current for 10 minutes) and the slower direction's rate (2 days), both directions on hover; lines without room carry the round trip alone, and a list under the diagram always has the full numbers; "At a glance" adds the typical (median) round trip. The server page has a **Private network** section: per peer the path and address, a 24-hour round-trip sparkline, the current round trip, the latest rates in both directions (↓ from the peer, ↑ to it), when the speed test ran and how many checks failed today.
- Measured in dev (`make up-multi`, three dind servers on one laptop): 0.2–2 ms round trips, 430–1470 Mbit/s; `TestLinkProbeMesh` (real Headscale, kernel Tailscale, nftables) moved 4 MiB over WireGuard between namespaces at ≈ 130–475 Mbit/s.

## 3. Cross-server service discovery: ambassadors

Goal: `api` on server B keeps using `postgres:5432`, placement can change without config changes, and other mesh members can't reach Postgres.

1. A provider workload consumed from another server is published **only on its server's mesh IP**, on a dashboard-allocated port: `100.64.0.7:31001 → container:5432`.
2. The provider server's daemon allows that port in nftables **only from the mesh IPs of servers currently hosting consumers in the same project environment**. WireGuard binds source IP to peer key, so the source IP is authenticated.
3. On the consumer server, launchroomd runs an **ambassador**, a TCP forwarder attached to the environment network with the alias `postgres` and port 5432. It forwards to `100.64.0.7:31001`; with several upstream replicas it load-balances with TCP health checks.
4. When everything is on one server, no ambassador exists: Docker DNS resolves the real container.

Details:

- **Who is a consumer** (dashboard, `App\Services\NodeStates\MeshLinks`): environment-relative, like Compose: every service of an environment may reach every other one by slug, so a server hosting any workload of environment E consumes every service of E that has a port and no replica on that server. There is no explicit dependency graph (a manually typed `postgres:5432` must keep working).
- **Ports** (`placements.mesh_port`, 31000–32999, unique per server; partial unique index as backstop): allocated lowest-free when a placement is first consumed from another server (a server ≠ its own hosts a workload of its environment, or it is a web service and the team has another edge). Allocation takes a single global advisory transaction lock only when a port is missing. Ports are **sticky**: kept for the placement's lifetime and published whenever set, so a database is not recreated (restarted) whenever its consumers move.
- **Provider** (server A): `publishOnMesh: {port}` on the workload; `firewall.meshAllow: [{port, from}]` with the mesh IPs of the other servers hosting workloads of the environment plus, for web services, the team's other edges. launchroomd binds the port **only on its mesh IPv4** (policy floor: a published port must be in `100.64.0.0/10`, 31000–32999; never `0.0.0.0`). Docker can bind that address only once `tailscale0` has it, so a published workload **waits** (status `pending`) until launchroomd knows its mesh IP; an existing container is left untouched while it is unknown (a daemon restart never recreates the database), and launchroomd reconciles again as soon as the address appears or changes. After a reboot Docker may fail to start such a container before the mesh is up; the next pass starts it (tested in `TestCrossServerMesh`).
- **Consumer** (server B): `ambassadors: [{network, alias: <slug>, port: <service port>, upstreams: [<mesh ip>:<mesh port>…]}]`, upstreams = serving replicas of any deployment (so a new database version is reachable during its health check), draining ones only when no serving one exists, stopped ones left out.
- **Re-renders**: a new NodeState version of a server re-renders the servers of its environments (old and new networks, so departures are covered) and the team's edges; unchanged renders trigger nothing. A mesh IP learned or changed re-renders every mesh server; revoking a server too.
- **The ambassador** (`lr-system-ambassador`, launchroomd `internal/ambassadord`, forwarder `cmd/ambassador` + `internal/ambassador`):
  - Image: built **locally from launchroomd's own `launchroom-ambassador` binary** (static Go, shipped next to launchroomd in its image; `LR_AMBASSADOR_BIN`) with the Engine's image import, tagged `lr-system-ambassador:<16 hex of its sha256>`. Nothing is pulled and the dashboard chooses nothing, so there is no digest to pin; it is exactly as trusted as launchroomd.
  - Network: its own bridge `lr-system-ambassador` (`LR_AMBASSADOR_SUBNET`, default `10.232.1.0/24`) is its default gateway (`GwPriority`), filtered by the `ambassador` chain (§1). It joins every environment network with ambassadors, with the remote services' slugs as aliases (an alias change reconnects that network only; the container is never recreated for config changes).
  - Listeners: one per (network, alias, port), bound to the ambassador's own address on that network and accepting clients only from that network's subnet, so one container serves many environments without mixing them.
  - Forwarding: least connections (ties round robin; round robin is available), TCP health checks every 5 s (2 s timeout, unhealthy after 2 failures; a failed dial marks it at once and tries the next upstream), half-close passed through, connection draining (connections of removed listeners or upstreams keep running up to 30 s).
  - Config: JSON (`internal/ambassador.Config`) copied into the volume `lr-system-ambassador-config` through the archive API; the forwarder re-reads it every second and keeps unaffected connections. The volume outlives the container: when the container is replaced (a new launchroomd/forwarder build changes its spec hash), the existing volume is re-created idempotently, and its ownership is checked against the **stored** labels (D51): Docker's create answer for an existing volume carries no labels, so checking that answer made a server whose dockerd had restarted refuse its own volume, and consumers there lost their remote services.
  - Hardening: user 65534, cap-drop ALL, no-new-privileges, read-only root, 256 MB / 1024 pids, json-file rotation; `net.ipv4.ip_unprivileged_port_start=0` for service ports below 1024. It is started only after the firewall covers its bridge (fail closed). No ambassadors → container and network are removed.
  - Local policy: listeners only on declared `lr-e_…` networks, upstreams only mesh addresses on 31000–32999; anything else is dropped and logged.
- **Mesh readiness** (`App\Services\NodeStates\MeshReadiness`, covered by the failover test): a new replica on server C counts as healthy (health step of its deployment, rolling traffic shift on the edges) only once every online server hosting a service C consumes has **applied** (reported `observed_version`) a NodeState whose `firewall.meshAllow` admits C's mesh IP on that service's port. Until then the provider's nftables drop C's ambassador upstreams, so a replica passing a static `/health` would fail every request touching its database. An applied version re-advances health-checking deployments. Providers that aren't online are not waited for.
- Previews whose workloads join a base environment's network get no ambassadors or allow-list entries for the shared base database when it lives on another server. Not implemented; see the [roadmap backlog](12-roadmap.md#backlog).

## 4. Ingress: Caddy

- **System container** (D23): Caddy is one of launchroomd's system containers (`lr-system-caddy`, NodeState `system.caddy`). Its spec is built into launchroomd, not taken from the dashboard:
  - `network_mode: host`: binds 80/443 directly and reaches container IPs on every environment bridge from the host network namespace, without joining (and bridging) any network;
  - admin API on `127.0.0.1:2019` only (`CADDY_ADMIN` plus `admin.listen` in the config). Bridge-networked containers can't reach the host's loopback;
  - `cap-drop ALL` + `NET_BIND_SERVICE`, `no-new-privileges`, json-file log rotation, memory/pids limits, `restart: unless-stopped`;
  - named volumes `lr-system-caddy-data` (`/data`: certificates, internal CA) and `lr-system-caddy-config` (`/config`: autosaved config). They are never deleted automatically;
  - command `caddy run --resume`: after a restart Caddy serves the last loaded config even while launchroomd or dashboard is down. launchroomd also re-POSTs its config after its own start and whenever the container restarts.
- **Image** (D47): launchroom's own Caddy build `ghcr.io/vantezzen/launchroom-caddy` (`deploy/images/caddy/Dockerfile`, xcaddy, multi-arch, Caddy v2.11.7 on a digest-pinned base). It adds exactly these pinned modules; the build fails if any is missing:
  - `caddy.storage.redis` (`github.com/pberkel/caddy-storage-redis` v1.9.0)
  - DNS-01 providers: `dns.providers.cloudflare` (`caddy-dns/cloudflare` v0.2.4), `dns.providers.hetzner` (`caddy-dns/hetzner/v2` v2.0.1, Hetzner Cloud DNS API), `dns.providers.route53` (`caddy-dns/route53` v1.6.2), `dns.providers.digitalocean` (`caddy-dns/digitalocean`, untagged upstream: pinned to `v0.0.0-20250606074528-04bde2867106`), `dns.providers.porkbun` (v0.3.1), `dns.providers.desec` (v1.1.0), `dns.providers.gandi` (v1.2.1), `dns.providers.ovh` (v1.1.0), `dns.providers.netcup` (v1.0.0)

  The release pins it by digest twice, from one build. `.github/workflows/release.yml` builds launchroom-caddy first and compiles its multi-arch index digest into launchroomd (`daemon/Dockerfile` `CADDY_DIGEST` → `-X …/internal/policy.launchroomCaddyDigest`; `launchroomd system-images` prints the pins, and the workflow refuses to sign a launchroomd without it). The same digest goes into the bundle's `images.env` (`LR_CADDY_IMAGE`), which compose passes to the dashboard as `LAUNCHROOM_CADDY_IMAGE`, which puts it into edge NodeStates. launchroomd accepts a `system.caddy.image` only if its digest is pinned in its own binary (`policy.DefaultSystemImageDigests`: a release build accepts only its release's launchroom-caddy, a dev build only the stock `caddy:2.11.7` digest the dev stack runs; extra digests only from host config, `LR_SYSTEM_IMAGE_DIGESTS=caddy=sha256:…`). The repository may be a mirror in the local registry. Since the pin is inside the signed binary, a compromised control plane can't run an arbitrary image with host networking, every server (control plane, or joined with `server.sh`, which installs the dashboard's `LAUNCHROOM_DAEMON_IMAGE` of the same release) pins its release's image, and a self-update brings the next pin.
  - **Rollout**: the dashboard is updated before the servers ([11](11-installation-and-dev.md) §4), so an edge still on the previous launchroomd is sent the next release's image, which it can't verify. It then keeps the Caddy it runs if its binary pins that image, and still applies the routes (`caddy.Manager.image`; logged once). When a server reports another launchroomd version, the dashboard re-renders its NodeState (`RecordReport`), so the updated launchroomd gets this dashboard's images and swaps the Caddy. With no pinned Caddy running, an unpinned image is refused (ingress `failed`). The dashboard only asks for shared storage or DNS-01 when `launchroom.ingress.caddy_modules` says the configured image has the modules (default: the image name contains `launchroom-`); an image without them would refuse such a config. `launchroom.ingress.dns_providers` (`LAUNCHROOM_CADDY_DNS_PROVIDERS`, comma-separated, empty = every provider of this release's image) narrows the providers for an older launchroom-caddy build (before D47: `cloudflare,hetzner`). Providers the image lacks are not offered and not rendered.
- **Storage module choice**: `pberkel/caddy-storage-redis` is maintained (v1.9.0, Oct 2026), speaks to Valkey, encrypts values (AES-256-GCM), uses `redislock` for Caddy's distributed locks and can start without its server (`skip_connection_check`, so `caddy run --resume` never fails on an unreachable storage). Postgres modules (`yroc92/postgres-storage`, last release 2023) and `gamalan/caddy-tlsredis` (2023) are unmaintained. Valkey already runs on the control plane; Postgres would give edges a database login.
- **Configured only by the local daemon through the admin API on `127.0.0.1:2019`.** Whole-config loads are atomic (`POST /load`). launchroomd caches the last applied config in `data/caddy/config.json`. It only re-loads when the rendered config (or the Caddy container) changed.
- **Upstreams** come from route upstreams that reference workloads (`{workload, port}`, resolved to the container IP on its primary network) or mesh addresses (`{address}`). Active health checking is launchroomd's own probe (the same one that gates rollouts): only running, probe-passing workloads are rendered as upstreams, serving ones first and draining ones only as a fallback. Caddy adds passive health checks (a failing upstream is skipped for 10 s) and retries for up to 5 s, which covers container restarts. A route with no ready upstream answers `503` with a short launchroom message.
- Per route:
  - hosts → upstreams with active health checks
  - load-balancing policy (`RouteSpec.loadBalancing`: `round_robin` default; `prefer_local`, set by the dashboard when every edge of the team runs a replica of the service, sends requests only to this edge's ready replicas and to mesh upstreams only while none is ready)
  - HTTP → HTTPS redirect
  - www ↔ apex redirect
  - compression
  - `X-Robots-Tag: noindex` on non-production
  - request size limit and timeouts
  - WebSocket and streaming pass-through (no buffering)
- **Preview protection**: routes with `protection.forwardAuth` ask the dashboard (`/auth/preview`) about every request, which checks the launchroom session, a share-link token or the CI bypass header. Like Caddy's `forward_auth`: a `GET` with the original method/URI in `X-Forwarded-Method`/`X-Forwarded-Uri` (Caddy sets `X-Forwarded-Host/Proto/For` itself and overwrites client-supplied values, since no trusted proxies are configured) and `Host` set to the auth upstream. A 2xx answer continues to the app after deleting `stripHeaders` (e.g. `X-Launchroom-Bypass`) from the request and removing the `__Host-lr-preview` cookie from its `Cookie` header (the cookie authenticates to launchroom, not to the app, and fork code must never see a member's cookie; the app's own cookies stay); any other answer (302 to the login with `Set-Cookie`, 401, …) goes back to the client unchanged; an unreachable dashboard gives 502. launchroomd only calls URLs whose origin is its control-plane URL or an `http://` `LR_ALLOWED_LOCAL_UPSTREAMS` entry ([03](03-daemon-protocol.md) §8); a protected route with any other URL answers 403 and is never proxied (fail closed, logged).
- **Preview protection, dashboard side** (`App\Http\Controllers\Previews\PreviewAuthController`, `App\Services\Previews\PreviewAccess`). The apps domain must never see the dashboard's session cookie (it runs user code, and it's a different registrable domain or at least a different host), so access is carried by the preview host's **own** cookie:
  1. `GET /auth/preview` (no session, no CSRF) resolves `X-Forwarded-Host` to a preview environment (a domain row, or an immutable deployment URL). Unknown host → 403; non-preview environment or protection off → 200. `X-Launchroom-Bypass` equal to the project's CI secret (a project-DEK MAC over a stored nonce, compared with `hash_equals`) → 200. A valid host-only cookie `__Host-lr-preview` → 200.
  2. Otherwise, for GET/HEAD: 302 to `{APP_URL}/auth/preview/start?host=<host[:port]>&path=<uri>` (other methods: 401). There the normal dashboard session applies (login, 2FA); the host must be a routed preview the user may view (`view` on the environment: same team), so it is no open redirect; the path must be origin-relative. The member gets a **single-use exchange token** (≤ 120 s, bound to host + environment + user, nonce redeemed once via the cache) appended as `__lr_token` to `https://<host>/<path>`.
  3. Back on the preview host, `/auth/preview` sees `__lr_token` in `X-Forwarded-Uri`, swaps it (exchange token, or a **share link** token: bound to the environment, valid until the link expires or is revoked) for the cookie and answers 302 to the same URL without the token, with `Set-Cookie: __Host-lr-preview=…; Secure; HttpOnly; SameSite=Lax; Path=/` (no `Domain`: host-only, never shared with sibling previews or the dashboard). Session cookies last 12 h, share cookies at most 24 h; both are re-checked on use (membership / link not revoked; cached 60 s).
  **Domain separation (recommendation).** Generated preview hosts (`{svc}-pr-N.{project}.{apps}`) share the registrable parent `{project}.{apps}` with the project's production hosts (`{svc}.{project}.{apps}`). Preview code (fork PRs included) can therefore set cookies with `Domain=.{project}.{apps}` that production apps on generated hosts then receive (cookie tossing / session fixation inside your app); it can't read production's host-only cookies. Production apps on generated hosts should use host-only (`__Host-`) cookies. Production on a **custom domain** is not affected. If `apps_domain` itself is not on the Public Suffix List, previews and production also share `{apps}`.
  Tokens: `v1.<base64url claims>.<base64url HMAC-SHA256>` with the kind (`exchange`/`cookie`/`share`) inside the MAC; key = HMAC(APP_KEY, "launchroom:preview-auth:v1"). Forged, tampered, expired, wrong-kind, other-host and other-environment tokens fail closed (tests in `tests/Feature/Previews/PreviewProtectionTest.php`). The auth endpoint is answered with `Cache-Control: no-store` and `X-Robots-Tag: noindex`. The forward-auth URL per server: `http://<LAUNCHROOM_DASHBOARD_UPSTREAM>/auth/preview` on the control-plane host, else `LAUNCHROOM_PREVIEW_AUTH_URL`, else `APP_URL/auth/preview`; if none matches launchroomd's grammar, preview routes are not rendered at all (fail closed). Dev: `http://dashboard:8000/auth/preview`.
- Unknown hosts get a short launchroom 404 response (no default "Caddy works!"). Unknown SNI on 443 fails the handshake (no certificate is requested).
- Rendered config, per route: `lr-https` server (`:443`) with host matcher → www↔apex redirect (308 to the canonical host) → forward auth for protected routes (`reverse_proxy` to the auth URL with `rewrite {method: GET, uri: /auth/preview}`, `handle_response` for 2xx that deletes `stripHeaders` and falls through; a refused URL renders a `403` instead of everything after the redirect) → response headers (`set`; an empty value deletes the header; values must not contain `{`/`}` because Caddy would expand placeholders) → `encode` (zstd, gzip) → `reverse_proxy` (round robin, `flush_interval: -1` for streaming/WebSocket). `lr-http` server (`:80`) redirects every routed host to HTTPS (308; ACME HTTP-01 challenges are answered before routing). TLS policies per route mode: `acme` (default issuers), `internal` (Caddy's internal CA, local dev `*.localhost`), `on_demand` (permission module `http` → launchroomd's ask endpoint). The renderer is pure and golden-file tested (`daemon/internal/ingress/caddy/testdata`).
- The public HTTPS port in redirects is 443 by default; local dev sets `LR_INGRESS_HTTPS_PORT=8443` on the fake server so redirects point at the host-mapped port.
- The dashboard itself is routed by the same Caddy on the control-plane host, as a "system route" in the control-plane server's NodeState, added by `App\Services\NodeStates\DashboardRoute` when `LAUNCHROOM_DASHBOARD_UPSTREAM` is set (the install compose file sets `127.0.0.1:8000`, where the dashboard container is published on loopback only): id `rt_0000000000000000000000DASH`, hosts = `APP_URL`'s host, upstream `{"address": "127.0.0.1:8000"}`, TLS `acme` (`internal` for `*.localhost`). It uses the existing address-upstream form, so the protocol is unchanged; Caddy runs with the host network and reaches the loopback port directly. launchroomd's local policy only allows address upstreams in the mesh range or in its `LR_ALLOWED_LOCAL_UPSTREAMS`; the control-plane install sets that to `127.0.0.1:${LR_DASHBOARD_PORT:-8000}` ([03](03-daemon-protocol.md) §8), so a compromised control plane can't route the internet to other loopback or host ports. The dashboard owns that host: an app domain naming it loses it in the rendered routes. No route when APP_URL is an IP, on other servers, or without edge role. With Settings → Dashboard domain the route carries the canonical host, the earlier origins' hosts and a domain being verified (§4.1). Reverb's browser path `/app/*` goes through the same route; the dashboard's FrankenPHP proxies it to Reverb.

### 4.1 Dashboard domain (D43)

The dashboard can move from its install-time origin (`APP_URL`: `https://<ip-dashed>.sslip.io`, an `install.sh --domain` name, or an IP) to a domain of your own with HTTPS: **Settings → Dashboard domain** (instance owners). It is one guided flow; nothing changes until the owner switches.

1. **Enter a domain** (`StartDashboardDomainChange`): a DNS name with at least two labels (no IP, no `sslip.io`/`nip.io`, not the current address, not at or under the platform domain, not a project's custom domain). A change still being set up is replaced. One row per attempt in `dashboard_domain_changes` (`pending` → `ready` → `active` → `reverted`, or `cancelled`; at most one open and one active, partial unique indexes).
2. **DNS** (`DashboardDomainChecks`): A/AAAA records to the **control-plane server's** public addresses, checked with the same public resolvers as custom domains (`DnsCheck`). *Decision:* only the control-plane server serves the dashboard, not every edge: the system route's upstream is the dashboard's loopback port, which exists only there, and proxying it from other edges over the mesh would expose the dashboard on the mesh and doesn't buy availability (the control plane isn't HA, D18). `*.localhost` names need no record.
3. **Certificate**: once DNS points here the name joins the control-plane server's system route (`instance_settings.dashboard_pending_host`), so Caddy obtains a certificate by **HTTP-01/TLS-ALPN-01** (ACME, like `acme` routes). Routing only after DNS is right keeps Caddy's first ACME attempt from failing into its retry back-off. DNS-01 is deliberately not used here even with a DNS provider: the record must point at the server for the dashboard to be reached anyway, and the per-host challenge then always works. The edge's certificate report for the name (`Report.ingress.certificates`) is shown with Caddy's last error (`RecordDashboardCertificate`).
4. **HTTPS test** (`App\Services\Http\DashboardProbe`): `GET https://<domain>/.well-known/launchroom/dashboard?nonce=<random>` must answer `{"proof": HMAC(nonce)}` under a key derived from `APP_KEY`, with normal WebPKI verification, so a valid certificate on somebody else's server doesn't pass. The connection is pinned (`CURLOPT_RESOLVE`) to the control-plane server's own public addresses that DNS matched, or to `LAUNCHROOM_DASHBOARD_PROBE_ADDRESS` (the compose file sets `host.docker.internal` = host-gateway, for NAT without hairpinning); never to whatever the name resolves to, no redirects, no proxy, 5 s (docs/09 R5). `*.localhost` names skip verification (Caddy's internal CA). Steps 2–4 run when the change starts, on "Check now" and every minute (`launchroom:dashboard-domain:check`); all passing makes it `ready`, a later failure sends it back to `pending`.
5. **Switch** (`SwitchDashboardDomain`): requires a passed test in the last 10 minutes (it runs again otherwise). The canonical origin becomes `https://<domain>`; the browser is sent there (Inertia location) and signs in again.

**Source of truth.** `App\Services\Instance\DashboardOrigin`: `instance_settings.dashboard_url` (null = `APP_URL`). `.env` is never edited at runtime. `DashboardOrigin::apply()` runs at the start of every request (`UseDashboardOrigin`, global middleware), queued job (`Queue::before`) and `launchroom:*` command and sets `app.url` (and the console root URL), so everything that reads it follows: links in mails and alerts, `route()` outside requests, `/install/server.sh` (new servers get the new URL), the recovery kit, preview sign-in redirects (`/auth/preview/start`), the GitHub manifest for new apps. `launchroom:dashboard-url` prints it (installer, `./launchroom status`).

**What else changes, case by case.**
- **Cookies**: sessions are host-only, so everyone signs in once at the new origin. With an https origin the session cookie is `Secure` and named `__Host-…` (no `Domain`, `Path=/`), so an app on a sibling domain can't toss it (installs upgrading to this release sign in once). CSRF tokens live in the session and follow. **HSTS** (one year, no subdomains, no preload) is sent by the dashboard over https in production, also on the new host once it is canonical.
- **Passkeys** (WebAuthn relying party): passkeys are bound to the relying party id they were registered with (`passkeys.rp_id`, existing ones backfilled with the install host). On a switch the id stays when the new host is it or below it (`example.com` → `dash.example.com`: passkeys keep working); otherwise it becomes the new host (`instance_settings.passkey_rp_id`) and the switch screen says how many passkeys (yours and everyone's) stop working. Users sign in with password (+ 2FA) and add a new passkey; Settings → Security marks old ones "For <old host>". An IP origin never had passkeys (browsers refuse IP relying parties).
- **Earlier origins** (`instance_settings.dashboard_legacy_urls`, `[{url, since, until}]`, newest first, at most 10; loopback origins are never kept): still routed by the control-plane Caddy (same system route, `rt_0000000000000000000000DASH`; `*.localhost` hosts in `rt_0000000000000000000001DASH` with the internal CA). `UseDashboardOrigin` answers there: launchroomd's endpoints (`/daemon/v1/*`, `/auth/preview`, `/registry/token`, `/up`, `/.well-known/launchroom/*`) **for good**, because they are every server's fallback; the public API, the CLI's endpoints, GitHub webhooks and `/install/server.sh` during the **transition window** (`LAUNCHROOM_DASHBOARD_TRANSITION_DAYS`, default 30); everything else (and those after the window) gets `308` to the same path on the canonical origin with `Cache-Control: no-store` (so "Switch back" never meets a cached redirect loop). Reverb (`/app/*`) and Headscale's paths are proxied by FrankenPHP before PHP and keep working on every host. A domain still being verified answers only the test request and `/up`; browsers there go to the canonical origin. Loopback hosts (the control-plane launchroomd on `127.0.0.1:8000`, SSH tunnels) are never redirected.
- **launchroomd** ([03](03-daemon-protocol.md) §4.2): servers that announce `controlPlaneUrl` get `system.controlPlane.url` = the canonical origin in their signed NodeState (never the control-plane server, whose launchroomd talks to `http://127.0.0.1:8000`). launchroomd adopts it only after a signed `GET /daemon/v1/config` there verifies against the pinned keys, persists it, and fails over to its configured `LR_CONTROL_PLANE_URL` (the old origin, still answered) on transport errors, 404/421/502–504 or an unsigned 2xx, for 2 minutes at a time; nudges and sessions follow the active URL. `Report.host.controlPlane` (`servers.daemon_control_plane`) shows which address each server uses (Settings → Dashboard domain lists them). `LR_CONTROL_PLANE_FOLLOW=off` keeps a server on its configured URL. A server's configured URL only changes when its `server.sh` runs again.
- **Preview forward auth**: launchroomd only calls forward-auth URLs on its configured or adopted origin ([03](03-daemon-protocol.md) §8), so a server's `forwardAuth.url` is `<origin it reported (adopted, else configured), if it is one of the dashboard's origins, else APP_URL>/auth/preview` (`DashboardOrigin::forServer`); a report changing it re-renders the server. On the control-plane server it stays the loopback upstream.
- **On-demand TLS ask endpoint**: unaffected. It is launchroomd's local `127.0.0.1:2021`, answered from the route table; dashboard hosts use `acme`/`internal`, never on-demand.
- **Headscale / the mesh**: kept on the install-time origin on purpose. Tailscale stores the login server in every client's prefs; a different `--login-server` means `tailscale up --force-reauth` with a new pre-auth key, i.e. a new node, new mesh addresses and re-rendered allow-lists on every server. So Headscale's `server_url` and `system.tailscale.loginServer` stay `APP_URL` (`MeshTopology::embeddedLoginServer()` uses `DashboardOrigin::installUrl()`), and that origin keeps being routed (it is in the legacy list after the first switch, and FrankenPHP forwards Headscale's paths on every host). The page says so while the built-in mesh is on.
- **GitHub Apps**: their homepage, callback, setup and webhook URLs don't follow. The page lists the owner's teams' apps with a link to each app on GitHub and the four new URLs to paste; webhooks keep arriving at the old origin during the transition window. "Another GitHub App" (Settings → Git) creates an app with the new URLs from the start.
- **Email links, alerts, recovery kit**: follow `app.url`. The control-plane key bundle keeps `APP_URL` (the install origin) as `appUrl`; the canonical origin is in the database and comes back with a restore.
- **Zot's token realm**: rendered from `app.url` the next time `./launchroom registry apply` (or the installer) writes the config; launchroomd passes registry tokens itself, so a stale realm breaks nothing.

**Switch back** (`SwitchBackDashboardDomain`, on the page while a domain set up here is active): the previous origin becomes canonical again and the domain it leaves joins the earlier origins (forwarding, launchroomd's fallback for servers that adopted it). **Escape hatch** when the domain locks you out: `./launchroom dashboard-domain-reset` on the control-plane server (typed confirmation) runs `launchroom:dashboard-domain:reset --force [--forget-old]`: `APP_URL` is canonical again, an open change is dropped, the control-plane server's routes are rendered right away (even without the queue), audited `instance.dashboard_domain_reset`. Re-running `install.sh --domain HOST` does the same when the database's origin differs from the new `APP_URL`. Every step is audited (`instance.dashboard_domain_started|cancelled|switched|reverted|reset`).

Tested: `tests/Feature/Instance/DashboardDomainTest.php` (authorization, refused names, the check sequence, a foreign answer never passing, the probe endpoint, switch and NodeState contents, redirects and the transition window, pending host, switch back, the reset command, passkey relying party, reported origins and forward auth, cancel), daemon unit tests and `TestDashboardDomainRoute` (ITEST `dashdomain`: Caddy with the internal CA serving the dashboard on two hosts), and the dashboard domain scenario of `make test-install` ([11](11-installation-and-dev.md) §2.4).

|---|---|---|
| **Platform wildcard** (`*.apps.example.com`, set in onboarding) | One DNS record → edge IP(s). Generated domains `{service}-{env}.{project}.apps.example.com`, previews `{service}-pr-{n}.{project}…`, immutable per-deployment URLs `{service}-{shortid}.{project}…` | DNS-01 wildcard if a DNS provider token is configured (instant HTTPS, no per-host rate limits); otherwise per-host HTTP-01 |

Rules:
- Hostnames are validated (RFC 1123, punycode IDNs, labels ≤ 63 chars, no underscores, which Let's Encrypt refuses; no all-numeric top-level label, so IP literals such as `10.0.0.5` are refused). Generated names are truncated with a hash suffix.
- A hostname can belong to only one team: `domains.hostname` is unique across the install (first come, first served). Custom domains at or under the platform domain (`apps_domain`) are refused: those names are launchroom's generated addresses, and claiming one would squat another project's. There is no DNS ownership verification: on a multi-team install, one team can claim a name first that another team owns.
- **Multi-edge certificates**: Caddy instances sharing storage coordinate ACME automatically (any edge can answer HTTP-01 / TLS-ALPN-01 challenges from storage). Each daemon mirrors the certs to `data/caddy/certs` so an edge restarts with valid certs even if storage is down.
- Let's Encrypt lifetimes shrink to 64 days (Feb 2027) and 45 days (Feb 2028). Renewal is automatic, and the dashboard surfaces expiry warnings.
- **Multiple edges.**
  - **Every edge routes every service of its team** (`NodeStateContent`): this edge's replicas are workload upstreams; replicas on other servers are `{"address": "<mesh ip>:<placements.mesh_port>"}` (`App\Services\NodeStates\MeshUpstreams`). `MeshLinks` (§3) allocates `placements.mesh_port` for every web replica when the team has another edge, publishes it on the provider and allows the edges in its `firewall.meshAllow`; replicas whose server has no mesh IP yet are skipped with a warning (logged once per hour). **Immutable per-deployment URLs are served by every edge** (remote replicas through their mesh address), so they work whichever edge DNS picks.
  - **NodeState `ingress`** (edge servers only, omitted when empty): `storage {address, keyPrefix, credentials}` and `dns {provider, domains, credentials}`. Credentials are `IngressSecret` documents (`{serverId, purpose: "cert_storage"|"dns", values}`) sealed to that edge's X25519 key; launchroomd refuses them for another server or purpose. launchroomd copies the values into Caddy's data volume (`/data/launchroom/secrets/*`, 0600, via the Docker archive API) and the config references them as `{file.…}` placeholders, so secrets are never in the config, the admin API or the config cache; a changed secret forces a reload (`Cache-Control: must-revalidate`). Local policy: the storage address must be in the mesh range or listed in `LR_CERT_STORAGE_ALLOW` (kept apart from `LR_ALLOWED_LOCAL_UPSTREAMS`, so the storage port can never become a route upstream).
  - **Shared edges**: the storage credentials and encryption key and the DNS-01 token are install-wide, so they only go to *shared edges*: the control-plane server, plus edges an **instance owner** admitted under Servers → Ingress & certificates ("Share certificates", audited `server.shared_edge_changed`, `servers.shared_edge_approved_at`/`_by`). A team admin can enroll a server and give it the edge role; it then serves its team's routes with its own local certificate storage (no `ingress` in its NodeState, no `tls: wildcard` routes, not in the Valkey allow-list) until an instance owner admits it. Edges are instance infrastructure: on a multi-team install, only admit edges you'd trust with every team's certificates and the platform DNS zone.
  - **Shared storage, automatic (`App\Services\Ingress\CertStorage`)**: with **two or more shared edges** (above), the mesh on, the Caddy modules available and a control-plane mesh IP, every edge gets `ingress.storage {address: <control-plane mesh IP>:6379, keyPrefix: lr-caddy}` with username `lr-caddy` and a generated password (43 characters, envelope-encrypted in `ingress_credentials`, purpose `storage_password`, sealed to each edge). The control-plane server's NodeState gets `system.certStorage {serveOnMesh: true, allowFrom: [other shared edges' mesh IPs]}`: its launchroomd serves `<mesh IP>:6379` → the local Valkey (`LR_CERT_STORAGE_UPSTREAM`, default `127.0.0.1:6380`, where the control-plane compose publishes Valkey on loopback) and allows tcp 6379 from the mesh only from those edges (`mesh-host`, §1). The Valkey ACL user is created by the dashboard on its own connection: `ACL SETUSER lr-caddy reset on #<sha256> ~lr-caddy ~lr-caddy/* resetchannels -@all +hello +auth +client|setinfo +ping +get +set +del +exists +zadd +zrem +zrange +scan +type +evalsha +eval +getrange +pexpire +pttl`: exactly the commands go-redis' handshake, caddy-storage-redis, the redislock scripts (scripts are ACL-checked, hence `getrange`) and launchroomd's mirror send, no categories, so no `CLIENT KILL/PAUSE/LIST` on the dashboard's main Valkey. `SCAN` is keyless, so the user can list key *names* of the shared Valkey, not read them (the key `lr-caddy` itself is caddy-storage-redis' top directory index; locks live under `lr-caddy/locks/`). Only the hash goes over the wire. Runtime ACL users are not persisted, so it is re-applied during the control plane's render (throttled to once a minute) and by `launchroom:ingress:cert-storage-user` every minute: a Valkey restart heals within a minute, edges run on their certificate mirror meanwhile (degraded mode). The mesh address is in launchroomd's allowed storage range by default (`LR_CERT_STORAGE_ALLOW` is only needed for non-mesh addresses). No manual configuration is needed.
  - **Shared storage, manual override**: `LAUNCHROOM_CERT_STORAGE_ADDRESS` + `LAUNCHROOM_CERT_STORAGE_PASSWORD` (username `LAUNCHROOM_CERT_STORAGE_USERNAME`, default `lr-caddy`; key prefix `lr-caddy`) still take precedence. The encryption key is generated once (32 characters) and kept envelope-encrypted (`ingress_credentials`). With one edge, every edge keeps Caddy's local file storage.
  - **Mirror and degraded mode**: every 2 minutes and after each config load launchroomd reads the shared storage itself (a minimal RESP client: AUTH, SCAN, GET; values decrypted with the shared key) and writes the certificates serving routed hosts to `data/caddy/certs/<name>.crt|.key` (0600; others removed). Before each config load it PINGs the storage; if unreachable, the config uses local file storage plus `tls.certificates.load_files` of the mirror (copied into the container), and wildcards covered by the mirror are not re-automated. `Report.ingress.storage` = `local` | `shared` | `degraded` (+ mirrored count, message). Tested end to end in `TestMultiEdgeSharedStorage`.
  - **DNS-01 wildcard**: route `tls: "wildcard"` means "served by `*.<host minus its first label>`". The dashboard sets it (`App\Services\NodeStates\EdgeRouting`, shared edges only) for routes whose hosts are all under the platform domain when a DNS provider is configured (generated domains, previews, branch aliases and immutable URLs: one `*.<project>.<apps domain>` certificate per project). launchroomd adds those wildcards to `tls.certificates.automate` with an ACME issuer using the DNS-01 provider (Caddy then skips per-host certificates for covered names); without a usable provider it falls back to per-host HTTP-01. Custom domains keep on-demand TLS.
  - **DNS provider settings** (Settings → Network → Certificates, instance owners, authorized; D47): the provider is chosen from monochrome logo cards, each with its own credential form (`App\Enums\DnsProvider::fields()`; secret fields are write-only, an empty field keeps the stored value while the provider stays, a provider change needs every field; non-secret values are grammar-checked):

    | Provider | Credentials (sealed value names) | Read-only check (`DnsProviderVerifier`, only this host) |

    | Cloudflare | API token with Zone → Zone → Read and Zone → DNS → Edit (`token`) | `api.cloudflare.com/client/v4`: `/user/tokens/verify`, `/zones?name=`, `/zones/{id}/dns_records` |
    | Hetzner | Hetzner Cloud API token (`token`; the old dns.hetzner.com API is retired) | `api.hetzner.cloud/v1/zones?name=` |

    All credentials of the provider are one envelope-encrypted `ingress_credentials` row (purpose `dns_token`, `App\Services\Ingress\DnsCredentials`: `lr-dns/1:` + a JSON object; a row from before D47 is the bare token and reads as `{token}`), rotated with `launchroom:keys:rotate-kek`; the audit entry records the provider and the *names* of replaced fields only. Providers other than Cloudflare and Hetzner go only to edges whose launchroomd announces the feature `dnsProviders` (an older one keeps per-host certificates instead of refusing the NodeState). The edge NodeState's `ingress.dns.credentials` is an `IngressSecret` holding exactly the provider's values; launchroomd validates the purpose's names and then the provider's (`state.ValidateDNSCredentials`: every name of the provider, no other, the OVH region and the netcup customer number by grammar) and otherwise falls back to per-host certificates with a note. Each value is copied into Caddy's data volume as `secrets/dns-<name>` and the module's own JSON field (`api_token`, `auth_token`, `access_key_id`, `api_secret_key`, `bearer_token`, `application_secret`, `customer_number`, …; checked against the pinned module sources, `daemon/internal/ingress/caddy/dns.go`) is a `{file.…}` placeholder, which every module resolves at provision time. Stale files of another provider are overwritten with nothing. The secret-free result of "Verify" is stored in `instance_settings.dns_verification`.
  - **Providers not built in (D47)**: RFC 2136, PowerDNS and ACME-DNS (the edge would call a self-hosted address the dashboard can't vet: an allow-list design comes first), Azure and Google Cloud DNS (large SDKs for few users), GoDaddy and Namecheap (API access gated by account size or a per-IP allow-list), DuckDNS (one TXT record per name, so no per-project wildcards), Linode/IONOS/Vultr/Bunny (fewer users among self-hosters). Adding a provider takes a module line, the enum case, its fields and a verifier.
  - **Certificate status**: launchroomd reads the certificates from the storage (shared storage, or Caddy's file storage through the Docker archive API) and Caddy's issuance log lines (`tls.obtain`/`tls.renew`: "certificate obtained/renewed successfully", "could not get certificate from issuer") and reports per routed host `Report.ingress.certificates[] {host, state: issued|pending|failed, wildcard, issuer, notBefore, notAfter, lastError, lastErrorAt}`. The dashboard (`App\Actions\Servers\RecordCertificates`) stores it on the team's domains (`domains.cert_*`); a fresh `issued` from another edge (≤ 15 min) isn't overwritten by an edge that hasn't loaded it yet. Domains show issuer, expiry and errors; `expiring` when a sixth of the lifetime (≥ 3 days) is left (renewal is due at a third), and `expired`.
  - **HSTS** (custom domains, `domains.hsts`, on by default, toggle in the domain list, immediate): edges send `Strict-Transport-Security: max-age=31536000` (no includeSubDomains, no preload) once the domain's certificate is reported `issued`; the flip re-renders the team's edges.
  - **Single point of failure**: the servers page and every project show a calm badge while exactly one edge exists and the team has other servers (one server alone gets a gentle hint instead), linking the [high-availability ingress guide](https://launchroom.vantezzen.io/docs/servers/high-availability-ingress).
- **Generated domains.** Web services (`app`/`image` with a port) get a generated domain per environment when created: `<svc>-<env>.<project>.localhost` when `launchroom.domains.localhost` is on (default in `APP_ENV=local`), else `<svc>-<env>.<project>.<apps_domain>` when `instance_settings.apps_domain` is set, else `<svc>-<env>-<project>.<ip-dashed>.sslip.io` on the team's first online edge server's public IPv4 (none if no IP is known). A hostname taken by another project gets a short project-id suffix on the project label. Domain additions and removals **apply immediately** (`App\Actions\Domains\ApplyDomainRoutes`): the service's current domains are written into a new revision on top of the last applied one (other staged changes stay staged) and the edges re-render. A never-deployed environment or a service that is itself still new keeps them for its first deploy. Routes are rendered from the environment's **last applied revision** (`App\Services\NodeStates\NodeStateContent`), one route per domain group (a domain whose `redirect_to` names another domain of the service joins that route as `redirectWwwTo`), id `rt_` + the domain's ULID, TLS `internal` for `*.localhost`, `on_demand` for custom domains, `acme` otherwise, `X-Robots-Tag: noindex` on every non-production environment. Upstreams are the edge's own workloads of the instance's active deployment plus draining ones, and replicas on other servers through their mesh address (above).
- The apps wildcard domain should differ from the dashboard's domain (cookie isolation). Onboarding recommends `dash.example.com` and `*.apps.example.com`, or better, separate registrable domains. Setting it to exactly the dashboard's host is refused; sslip.io/nip.io names are refused (sslip.io is the automatic fallback).
- **Live DNS verification.** `App\Contracts\PublicDnsResolver` (`UdpDnsResolver`): A and AAAA queries over UDP to public recursive resolvers (`LAUNCHROOM_DNS_RESOLVERS`, default `1.1.1.1,8.8.8.8`), 2 s timeout each, answers parsed for A/AAAA/CNAME only. Hostnames are grammar-checked before any query. `DnsCheck` compares the answer with the public addresses of the edge servers: `ok`, `proxied`, `mismatch` (elsewhere, or partly elsewhere), `missing`, `unknown` (no edge address to compare) or `error` (no resolver answered).
  - **Server addresses** (`servers.public_ipv4/_ipv6`, shown wherever the UI says where DNS must point: Get started, custom domains, the dashboard domain, the server page). launchroomd detects them through IP echo services (`publicip`: api.ipify.org, ipv4.icanhazip.com, ifconfig.me over tcp4; api6.ipify.org, ipv6.icanhazip.com over tcp6; at start and every 6 h, retry after 10 min) and reports `Report.host.publicAddresses`; `LR_PUBLIC_IPS` sets them by hand, `LR_PUBLIC_IP_DETECT=off` disables the echo services. Enrollment keeps the request's source address only when it is public: the control-plane daemon reaches the dashboard through the published loopback port and arrives from Docker's bridge gateway (`172.18.0.1`), which earlier releases stored and showed as the DNS target. `App\Support\Network\ServerAddress` refuses private, CGNAT, Docker, loopback, link-local, ULA and IPv4-mapped addresses on enrollment, on reports and when rendering DNS instructions (local dev allows private ones, `LAUNCHROOM_PRIVATE_SERVER_ADDRESSES`).
  - **HTTP reachability** (`App\Services\Dns\EdgeReachability`), only when nothing resolves to an edge address directly: every edge Caddy forwards `/.well-known/launchroom/check/<nonce>` on any host (HTTP and HTTPS, before all routes) to launchroomd's loopback ask server, which answers `{serverId, signature}` with an Ed25519 signature of `launchroom-reachability/v1\n<host>\n<nonce>` by its identity key (domain-separated from RFC 9421 signature bases, rate-limited to 20/s). The dashboard sends a fresh random nonce per check to `http://<name>/…` through SafeHttpClient pinned to the public addresses the lookup returned (private and reserved refused, docs/09 R5), no proxies, at most one redirect to the same URL over https, 3 s connect / 5 s total, 4 KiB cap, and accepts only a signature of a non-revoked server. A signed answer makes the check `ok` (`reachedOverHttp`); records in a known proxy's published ranges (`ProxyRanges`: Cloudflare) set `proxy` and, without a signed answer, the status is `proxied` ("Behind a proxy, not confirmed") instead of `mismatch`. `LAUNCHROOM_DNS_HTTP_CHECK=false` turns the HTTP check off (tests run with it off). Before this, the check was DNS only: a user-supplied name now leads to at most one GET to a vetted public address.
  - **Behind Cloudflare** the UI recommends SSL/TLS Full (strict) (Flexible loops on Caddy's HTTPS redirect). HTTP-01 passes through the proxy (TLS-ALPN-01 doesn't); a Cloudflare token (D47) gives DNS-01, independent of the proxy. Cloudflare's free edge certificate covers one subdomain level, and generated names are two or more levels below the platform domain, so the platform wildcard should be DNS only. The dashboard domain works proxied: once the HTTP check passes, the HTTPS test request (D43) goes to the control-plane server's own addresses instead of where DNS points. Client certificates for daemon transport (D50) need the daemons to reach the dashboard without the proxy terminating TLS.
  - Platform domain: onboarding resolves a random name `lr-check-<8 hex>.<domain>`, so only a wildcard record can answer. Saving the domain keeps the step open with the records and the live check; **Continue** (`POST /onboarding/domain/confirm`, re-checks) or **Continue anyway** (`anyway: true`) marks it done (`instance_settings.onboarding.domainConfirmed {domain, verified, at}`).
  - Custom domains: checked when added, on "Check DNS now" (`POST …/domains/{domain}/verify`, 20/min), and by `launchroom:domains:verify` every 5 minutes (domains not `ok` after 5 minutes, `ok` ones after 6 hours, at most 100 per run, one `VerifyDomainJob` each). The result is stored in `domains.verification` and never changes routing (on-demand TLS only issues for names that reach the edge anyway).
  - Records shown: A/AAAA per edge address; for subdomains (not zone apexes) under a platform domain, alternatively a CNAME to the service's generated hostname.
- **Previews and immutable URLs** (`App\Services\Previews\PreviewUrls`). Preview environments are named `pr-<n>`, so their generated domains are `{svc}-pr-{n}.{project}.{apps}` (`…-pr-{n}-{project}.{ip}.sslip.io`, `….localhost`). Web services of a preview also get a **branch alias** `{svc}-git-{branch}.…` (lowercased, non-alphanumerics → `-`, label ≤ 63 chars with a hash suffix) stored as a generated domain with `redirect_to` the PR URL, so it joins that route and redirects (308) before forward auth. **Immutable per-deployment URLs** `{svc}-{shortid}.{project}.{apps}` (shortid = the lowercased last 8 characters of the deployment's ULID; sslip/localhost forms like the generated domains) are rendered for every web deployment of every environment whose workloads run on the edge: the instance's active deployment (from its routing step on), staged (`ready`) deployments and draining ones. They use `on_demand` TLS (a certificate only when visited, `internal` for `*.localhost`), always `X-Robots-Tag: noindex`, the preview's protection for preview deployments, route id `rt_` + the deployment ULID; a domain with the same name wins. Lookup: a functional index on `lower(right(public_id, 8))`. Once a deployment's workloads are gone (superseded and drained), its URL stops resolving (Caddy refuses the unknown SNI). Old versions are not kept running for their URLs.
- **www redirect.** The switch on a custom domain adds `www.<host>` with `redirect_to = <host>` to the same service (one route with `redirectWwwTo`, see above); removing the domain removes its www redirect. Applies immediately like any domain change; audited `domain.www_redirect_changed`.
- **Certificates.** Edges report certificate state ("Certificate status" above); until the first report, custom domains say "issued on the first request once DNS points at your servers" instead of inventing a status.

## 6. Registry access from servers

- Zot runs on the control-plane host, bound to `127.0.0.1:5000`, with auth required. With the mesh on, the control-plane host's launchroomd serves **`<its mesh IP>:5000`** and forwards to Zot (`system.registry.serveOnMesh`; Zot itself stays on loopback, since a compose-published port can't bind an address that only exists once the mesh is up). Every other server's NodeState names `system.registry.forwardTo: <control plane mesh IP>:5000` once that address is known. Verified in dev: server-2 pulls `127.0.0.1:5000/mirror/docker.io/library/busybox@sha256:…` → its forwarder → `100.64.0.1:5000` over WireGuard → server-1's mesh forwarder → Zot.
- Docker accepts plain-HTTP registries on `127.0.0.0/8` without `insecure-registries` config. So every server pulls from **`127.0.0.1:5000`**:
  - on the control-plane host: Zot itself;
  - elsewhere: launchroomd's built-in TCP forwarder to Zot over the mesh.

  This avoids touching `/etc/docker/daemon.json`. Verified in a dind fake server: the nested dockerd pulls `127.0.0.1:5000/mirror/docker.io/…@sha256:…` through launchroomd's forwarder with no daemon config. The realm does not need to be reachable from launchroomd: launchroomd passes the token itself (`registrytoken`), which launchroomd sends as `Authorization: Bearer` directly.
- Credentials: launchroomd requests short-lived tokens from the dashboard (pull-only, scoped to images of workloads on that server; push only for build tasks, scoped to one repository) and passes them per pull/push through the Engine API `X-Registry-Auth`. Nothing is stored in `~/.docker/config.json`.
- The Docker daemon's local image store is the per-server cache. Per-node pull-through caches are unnecessary at our scale.
- **Details.**
  - **Tokens**: the dashboard is the Docker token-auth server. `RegistryTokenIssuer` signs ES256 JWTs (`iss` `launchroom`, `aud` = Zot's `service` `launchroom-registry`, `sub` = server id, `exp` ≤ 5 min, `access: [{type: repository, name, actions}]`) with its own key file (`launchroom.registry.token_key_path`, created by `launchroom:keys:generate`, never overwritten); Zot's `http.auth.bearer.cert` points at the public key file (`token_public_key_path`, a PEM in its own directory so Zot mounts nothing else). Zot accepts a request only if a claim names exactly that repository and action. `POST /daemon/v1/registry-token` decides scopes (all or 403, see [03](03-daemon-protocol.md) §5 notes); `GET /registry/token` is the realm Zot advertises: Basic auth whose password is a token the dashboard issued, answered with the requested scopes intersected with that token's, never outliving it (no renewal, no widening).
  - **Zot** (`dev/zot/config.json`, image `ghcr.io/project-zot/zot` v2.1.22 pinned by digest): bearer auth; `http.compat: ["docker2s2"]` so mirrored Docker-media-type manifests keep their upstream digests; on-demand sync of `registry-1.docker.io` and `ghcr.io` with `content: [{prefix: "**", destination: "/mirror/<registry>"}]`, so `mirror/docker.io/library/postgres@sha256:…` is fetched from `docker.io/library/postgres` on first pull and served from Zot afterwards (verified with Docker Hub and GHCR digests); online GC; retention keeps the 10 most recently pushed tags per `apps/**`, 2 per `cache/**`, and mirror content pulled within 30 days.
  - **Forwarders**: launchroomd listens on `127.0.0.1:5000` when it has an upstream (`system.registry.forwardTo`, else `LR_REGISTRY_UPSTREAM`; dev: `zot:5000`), and on the build network gateway `10.232.0.1:5000` for its BuildKit (`registry.launchroom.internal:5000` inside buildkitd), upstream as above or `127.0.0.1:5000` where Zot itself listens. Plain TCP pipes, ≤ 512 concurrent connections; authorization happens in Zot.
  - **Repository names**: `apps/<service id lowercased>` (tags = deployment id lowercased, never `latest`), `cache/<service>` (`:buildcache`), `mirror/<registry>/<path>`.
- **Storage on S3 ([14](14-backup-and-restore.md) §9.11).** Instance owners can put Zot's storage on an S3-compatible bucket (Settings → Registry). The dashboard renders Zot's `config.json` (S3 driver, `dedupe` off so the bucket alone is a complete registry, a local sync staging directory); `./launchroom registry apply` writes it and restarts Zot. Servers still pull from `127.0.0.1:5000` through the same forwarders: only Zot's backend changes. Images are not migrated when switching; they are rebuilt or re-mirrored on the next deploy.
