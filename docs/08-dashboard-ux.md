# 08: Dashboard UX

The dashboard should feel like a managed deploy platform that runs on your own servers. How screens look and behave is in [design-system.md](design-system.md); the journeys are in [design/flows.md](design/flows.md).

## 1. Navigation

- **Sidebar**: one header row (the launchroom mark as an icon only, linking home with `aria-label` "launchroom home", then the team selector; on the icon rail they stack), a visible "Search ⌘K" field, Get started (instance owners, until complete), **Projects** (cards with live status), **Servers**, **Analytics** (requests of every project, [15](15-observability.md) §5.4), **Security** (findings, web firewall, inventory and investigations; the number of "Action needed" findings as a badge, [22](22-security-center.md) §9), **Logs** (owners and admins, §12), **Settings** (a quiet dot when an update is ready, owners); in the footer **Activity** (team feed), **Docs**, the user menu and a muted "launchroom v0.1.0" line (shared prop `version` = `config('launchroom.version')`, from the root `VERSION` file; dev reports `<VERSION>-dev`), hidden on the icon rail.
- **Team menu**: every team and, for instance owners and team owners/admins, **Create team**: a small dialog (team name only) that creates the team with you as owner, switches to it and lands on its Projects (docs/09 R9).
- **Settings**: every settings surface (account, team and launchroom settings at `/settings/*`, project settings, the service panel's Settings tab, §16) uses one `SettingsShell` ([design-system.md](design-system.md) §13.9 "Settings shell"): a search field and a sidebar of titled groups with an icon per page beside one page (title, one sentence, cards); on phones the groups become cards of large rows with a one-line summary, and a page has an "All settings" back row. `/settings` groups: **Account** (Profile, Security: password, two-factor and passkeys, API tokens ([16](16-api-and-cli.md) §1.3), Appearance) · **Team** (Members, Git, Backups, Notifications, Dockerfile generation) · **This launchroom**, instance owners only (Updates with a dot when one is ready, Network, Dashboard domain, Registry, Security: server certificates and the audit log, Move launchroom). The sidebar's Settings goes to `/settings` (`settings.index`): Profile beside the sidebar on wide screens, the list on phones. Search finds the pages and their main rows (`features/settings/settings-index.ts`). The API reference is `/docs/api`; the CLI sign-in approval page `/cli/login?code=` is a signed-in page in the auth frame (no layout chrome).
- **Top bar**: every page has one 52 px top bar and renders in one `Page` container (`wide` 1280 / `narrow` 768 / `settings` 200 + 800 / `full`). Team pages: breadcrumb left, page-level secondary actions right (`TopBarActions`).
- **Project level**: the canvas is home. One top-bar row with `project ▾ / environment ▾`, the tabs inline as a segmented row (**Canvas · Deployments · Logs · Metrics · Analytics · Previews · Settings**; a menu on narrow bars and phones) and the staged-changes pill right (hidden when nothing is staged, when the environment has no services, and on a canvas with services, whose toolbar carries it; "3 new services · Deploy" before a first deploy; count only on phones). Adding a service is the canvas toolbar's Add ("Add a service" under the phone list). Deploy outcome toasts are mounted once by the project layout, so every project page announces "web is live" / "web failed to deploy". Project activity is in the project menu. Only the canvas and the Logs tab (`/p/{project}/{env}/logs`) are full-bleed; other project pages scroll like team pages.
- **Service level**: a route-backed right-side panel over the canvas, expandable to full page. Tabs: **Deployments · Metrics · Logs · Settings** (+ **Console** with the permission, **Data** for databases with the permission; §15). Variables and Backups are pages of Settings (§16); the old `/s/{service}/variables` and `/s/{service}/backups` URLs and `?tab=variables|backups` redirect (301) to them with their query (`?add=`, `?before=`).
- Page changes cross-fade with a 4 px settle (View Transitions); the sidebar and top bar stay still; reduced motion turns it off.

```

/projects
/p/{project}/{env}                     canvas
/p/{project}/{env}/s/{service}/{tab}   canvas + service panel
/p/{project}/{env}/s/{service}/settings/{section}   the panel's Settings tab on one page (§16)
/p/{project}/{env}/d/{deployment}      deployment detail (logs, timeline)
/p/{project}/{env}/changes             staged changes diff
/p/{project}/{env}/logs                log explorer (build and runtime lines, live tails; §12)
/p/{project}/promote?from=&to=         compare & promote between environments
/p/{project}/deployments               all deployments across environments, by day, grouped by commit
/p/{project}/activity                  the activity feed filtered to the project (§12)
/activity                              team activity feed (sidebar)
/analytics                             request analytics of every project (sidebar; drill-down to a project's Analytics tab, then a service via ?service=; docs/15 §5.4)
/logs                                  search the logs of every project (sidebar, owners and admins; §12)
/security                              findings, web firewall, inventory (sidebar; docs/22 §9); /security/findings/{finding}, /security/inventory?q=
/p/{project}/settings/{section}        general | environments | previews | config-file | logs | danger
                                       (/p/{project}/settings: General on wide screens, the list on phones)
/p/{project}/previews                  pull request previews (status, URLs, data, expiry, approve, share links)
/servers  /servers/{server}
/servers/new?step=roles&machine=home   "Add a server" wizard (steps 1–2); step 3 is /servers/enrollments/{enrollment}?machine=
/servers/{server}/replace              "Replace server" wizard and its progress (docs/14 §5.3)
/recovery                              recovery-mode checklist after `install --restore` (instance owners)
/settings                              Profile on wide screens, the settings list on phones
/settings/{section}                    incl. backups (destinations, schedules, recovery kit) and network
                                       (/settings/network; /servers/mesh and /servers/ingress redirect there)
```
Every view and tab has a URL, and log lines are anchorable (`#L42`). Use Wayfinder for typed route helpers.

**Route rules (`routes/projects.php`).** `{env}` and `{service}` are public ids (`env_…`, `svc_…`), constrained by grammar so `/p/{project}/settings` and `/p/{project}/deployments` never match an environment; controllers check nested resources belong together (`ProjectScope`). A service panel tab or settings page the service doesn't have (Backups without data, Data on an app) is a 404. **Previews**: the project tab lists pull requests (number, title, author, branch → base, head SHA, fork badge, status with reason, data strategy per database, URLs with a lock when protected, expiry) with Approve (fork PRs, `deployments.create`), Share (share-link dialog) and Canvas; Settings → Previews holds the preview settings, the CI bypass secret (shown once after generating) and the per-database "In previews" strategy with the clone source picker (latest backup sizes, size guard and production toggle reasons); preview environments are grouped under "Previews" in the environment switcher; a preview's canvas shows its pull request strip and "shared"/"cloned" badges on edges into such databases. Canvas positions save instantly via `PUT /p/{project}/{env}/layout`; the Connect popover previews through `GET …/connections/preview` (reference templates only, never values). Viewers of an environment canvas subscribe to the private channel `environments.{env id}` (`CanvasChanged`, a contentless nudge; the page reloads its props). The "We detected…" step of adding a repository calls `GET /p/{project}/plan-preview`, answered by `App\Contracts\PlanPreviewer` (`App\Services\Canvas\TaskPlanPreviewer`, see §9). `DetectedPlanData::fromSummary()` turns a protocol `BuildSummary` (plan task result, `service_instances.plan.summary` or `deployments.plan.summary`) into the UI shape: framework display name, package manager and runtime with versions and their source, commands, port, health path, release command, preset decisions, build variables, variables referenced in code (and, for an existing service, the ones not defined), warnings and Railpack's plan JSON.

## 3. Key screens

Flow follow-ups (D60): sensitive actions use the current signed-in session without another password prompt. The sidebar footer links to Docs. Repository, template and Compose project creation offer **Create without deploying** beside **Create and deploy** so variables can be configured first. Deployment detail shows the assigned build server with its device illustration while building; durations tick every second independently of status updates. Settings → Network starts with **App domains**: the same picker as the address step of Get started (`AppsDomainPicker`: "Use my domain" / "Use a free address" tiles, the field, the wildcard record card with the server's public address, the live check every 10 s with the proxy states). Settings has nothing to continue to, so instead of Continue / Continue anyway it keeps checking, says that new apps already get addresses under the domain, and records the verification by itself once DNS turns green (`POST /onboarding/domain/confirm`); switching back to free addresses asks in a confirm popover. When the wildcard is proxied by Cloudflare, an amber callout explains that its free certificate covers one level and gives the fix (DNS only, or an advanced certificate per project with Full (strict)). Domain setup records wrap inside a scrollable dialog; the Domains page refreshes pending HTTPS certificates independently of the DNS check.

## 4. Interaction principles

- **Detected default + Override toggle** everywhere (Vercel build settings pattern).
- **Optimistic UI + undo toasts** for reversible actions. Type-to-confirm only for irreversible ones (delete a volume or database).
- **Realtime by default**: status, logs, staged counts and canvas updates over Reverb. Log lines are batched (100–200 ms).
- **⌘K command palette**: jump to project, service, deployment or server; actions (redeploy, rollback, open logs, add variable, switch environment). Shortcuts: `g p`, `g s`, `g d`, `g l`, `g v`, `/` to focus log search.
- **Speak app, not container.** Docker vocabulary appears only under Advanced.
- **Honest about single points of failure**: calm badges with one-click fixes ([02](02-architecture.md) §5).
- **Empty states teach**: every empty list says what it is and offers the one action that fills it.
- **Live timers**: elapsed times of running work (deployments and their steps, the logs page, sessions, relative times like "12s ago", "Unreachable for 8 min") tick on one shared clock (`hooks/use-now.ts`: a single one-second interval per page, paused while the tab is hidden). `<Elapsed since until>` and `<Duration seconds>` (`components/elapsed.tsx`) render compact durations with tabular figures; a finished item shows its fixed duration and doesn't subscribe. Only the timer cell re-renders, never the page. Reduced motion stops animation, not the numbers.
- **Connection to launchroom** (`lib/connection.ts`, installed in `app.tsx`): while the dashboard restarts (an update, a move) the edge answers 502/503/504 or nothing. Instead of Inertia's error dialog per failed request, one non-blocking "Reconnecting to launchroom…" pill shows at the top (`ReconnectBanner`), background reloads (polls, realtime fallbacks, async partial reloads) pause, and `GET /up/version` (public, sessionless, `no-store`: the Inertia asset version) is probed with backoff (1 s doubling to 15 s). When it answers with a different build the page reloads fully; with the same build the banner goes and the page's props refresh. A 409 with `X-Inertia-Location` (asset version changed) always reloads fully, also for async visits, which Inertia itself skips. A 419 reloads (sign in again). Any other non-Inertia error page opens at most one dialog. JSON requests through Inertia's HTTP client report to the same state.
- **Heavy load notice**: when the control-plane server averaged ≥ 90 % CPU or ≥ 95 % memory over the last 5 minutes (at least 3 per-minute samples, `server_metric_samples` from Report.metrics; `App\Queries\ControlPlaneLoad`, cached 60 s), the `controlPlaneLoad` shared prop (`ControlPlaneLoadData`, only for users who may `update` that server) shows a calm card at the bottom of the sidebar: "Your launchroom server is under heavy load. The dashboard may be slow. Consider adding resources or a separate build server.", with links to the server page and the build-server docs. Hiding it lasts six hours in that browser.

## 8. Deployments, variables, staged changes, ⌘K

- **Pages** (project shell, `routes/deployments.php`): `/p/{project}/deployments` (filters `environment`, `service`, `status` incl. `in_progress`; grouped by commit), `/p/{project}/{env}/d/{deployment}` (detail), `/p/{project}/{env}/changes` (review). Deploy is `POST /p/{project}/{env}/deploy` (optional message) and lands on the project deployments; Discard is `POST …/changes/discard` with optional `paths[]`. Redeploy, rollback and cancel are `POST …/d/{deployment}/{redeploy|rollback|cancel}` and land on the new deployment. Redeploy creates a `manual` deployment of the environment's last applied revision (staged changes stay staged); cancel is only offered while queued or building (later steps already touch workloads).
- **Service panel Deployments and Settings → Variables** (`DeploymentsTab`, `VariablesSection`) and the staged-changes pill load JSON from `/p/{project}/{env}/-/…` (the `-` segment can't collide with page URLs) through TanStack Query; variable edits are JSON requests and invalidate the pill. The pill also refetches after every Inertia visit and on `canvas.changed`.
- **Realtime**: private channels `environments.{env}` (`.deployment.updated`, `.canvas.changed`) and `deployments.{dpl}` (`.deployment.updated`, `.logs.appended`), authorized by policy in `routes/channels.php`. Events carry ids and status only; clients refetch through authorized endpoints. Log nudges are one per daemon log batch; the viewer coalesces them and fetches lines after its cursor at most every 200 ms. Without Reverb every subscription falls back to polling.
- **Logs**: `GET …/d/{deployment}/logs?after={chunk id}` returns up to 5,000 lines after the cursor, numbered in arrival order (stable `#L42`). A deployment's lines come from its tasks (plan → Plan, build → Build, run_once → Release), chunks shipped for the deployment (`step` names the section) and its workloads (Runtime logs). The first error line of a failed step is found by a display heuristic (error keywords, else the first stderr line).
- **Variables** (a settings page, §16): the rows that apply to this environment (environment-targeted, branch overrides, connection-owned), shared variables with "use in this service", and system variables. Previews expand references like the resolver but mask every secret, including secrets embedded in config templates; broken references are listed per row. Secret values are never part of any list; Reveal is its own authorized and audited endpoint. Turning a secret into config requires the reveal permission. **Raw `.env` mode** shows secrets as `__LAUNCHROOM_SECRET_UNCHANGED__` (keeps the value); saving replaces this environment's rows: a changed row that also targets other environments is split, a missing key is removed from this environment only.
- **⌘K** (`/-/palette`): projects, environments, services, recent deployments and servers of the current team; actions (redeploy with an inline confirm, roll back the open deployment, open logs, add variable via `?add=variable`, switch environment); recent items in `localStorage`. Shortcuts as in §4.
- **Dev data**: `make artisan ARGS="db:seed --class=DeploymentsDemoSeeder"` (local only) seeds `acme-store` with deployment history, ANSI build logs, variables and staged changes.

## 9. Plan preview, build settings, onboarding, domains, deletion

- **Plan preview while adding a repository** (`TaskPlanPreviewer`): the first call resolves the branch head (GitHub API) and creates a `plan` task (`BuildTasks::previewPlan`: default build settings, no variables, a throwaway `svc_` id, the project's production environment id; nothing is built or pushed). The task id is cached per (team, repository, branch, root directory) for 10 minutes, so polling looks it up instead of starting new tasks. Answers: `pending` (message "Waiting for a build server" / "Inspecting the repository on the server <name>"), `ready` with the detected plan, `failed` with the reason (missing branch, plan error, the task's error), or `unavailable` when no online server has the build role. Nothing stays pending forever: a task no build server leased within 2 minutes (since created or requeued) is cancelled and answered `failed` ("No build server picked up the detection…"), and a leased one past its deadline is answered `failed` ("Detection did not finish in time…") before the lease reaper fails it. `?retry=1` forgets a failed, cancelled or overdue task and starts a new one (a running one is kept). Both the add-service sheet and the import page use `usePlanPreview` (`features/add-service/use-plan-preview.ts`): poll every 2 s, stop after 3 minutes without an answer with "Detection is taking longer than expected", and show every failure with its reason and **Retry**; the sheet offers "Add without waiting" while pending or after the timeout.

Empty values fall back to the build-time `VITE_REVERB_*` (local dev), then to the page's own origin (production proxies `/app/*` to Reverb). ## 14. Servers and fleet

- **Removing a pending server.** A server that was added but never connected (an unused enrolment) is removed from its card's ⋯ menu or its waiting page: `DELETE /servers/enrollments/{enrollment}` (`CancelEnrollment`, policy `ServerEnrollmentPolicy::delete`: ManageServers, unused, not the control plane's) deletes the enrolment row and with it the join token's hash, so the install command fails closed (`EnrollServer` finds no token); audited as `server.enrollment_canceled`. No password confirmation: it only takes access away. A server that connected but waits for approval is removed by revoking its key (the existing authorized revoke route); it then goes back to the fleet, and never-approved revoked servers are left out of the "Revoked" list. Enrolled servers keep Revoke and Replace unchanged.
- **One server is the default, not a risk.** `EdgeOverviewData.singlePointOfFailure` is only true when exactly one edge exists **and** other servers could take traffic too; with one server in total `singleServer` is true and the UI shows a gentle hint instead (the ghost card's "Use a second server to improve reliability", the topology's "One server does everything. Add another to share the work."). The project top bar badge, the Servers attention row and Settings → Network follow from the same flag ([02](02-architecture.md) §5).
- **"This server is small"** (`App\Queries\SmallServerHint`, `SmallServerHintData`): when the team's only online/unreachable build server has fewer than 2 CPUs or less than 3500 MB memory (`launchroom.server_health.small_build_server_*`; a 4 GB machine reports a bit under 4096 MB; unknown values never count), a calm, dismissible card says that a heavy build next to the running apps can slow them down or briefly make them unavailable, suggests a separate build server (a home server, a Raspberry Pi, a laptop), links the home-machines and add-a-server docs and opens Add server. Shown on Get started, the Servers page and that server's page (Overview), only to users who may add servers; hidden once another build server exists or the server grew. "Dismiss" is per user (`POST /servers/small-server-hint/dismiss`, `instance_settings.onboarding.smallServerHintDismissed`).
- **Public address** on the server page (Network → Public traffic, At a glance) is the reported public IPv4, else IPv6, never a private or Docker address ([05](05-networking-ingress.md) §5).
- **System load** comes from `FleetMetricsData.totals` (`FleetTotalsData`): per bucket, the share of the reporting servers' capacity in use, CPU weighted by cores, so a server missing a minute isn't a dip; `current` sums cores, memory and disk of servers that reported in the last 5 minutes.
- **Topology** (`FleetTopology`, `meshLinks` prop from `ServerTopology`): tiers Internet → edges → the other servers (columns when they fit, one stacked column otherwise), each server a small node with its device render and LED, name, the status word when not online, and role icons (the dashboard and image registry on the control plane, because Zot runs next to the dashboard). Lines: public traffic (foreground), private network from the latest Headscale/tailscale peer status (`Report.host.mesh.peers`) per pair of the team's servers with the best path either side saw (solid direct, dashed relayed with the relay region on hover, dotted idle). A team without the dashboard's server gets a "Dashboard" node linked by each server's path to it. The private links carry what launchroomd measured ([05](05-networking-ingress.md) §2.1): a pill on the line with the round trip and the slower direction's rate ("0.4 ms · 480 Mbit/s"; the round trip alone where the gap between tiers is too narrow, nothing on the stacked phone layout), both directions in the line's tooltip, and a list of every measured link under the diagram; "At a glance" adds "about 0.3 ms". The server page has a visible **Private network** section (per peer: name, path, mesh address, a 24 h round-trip sparkline, the round trip now, ↓/↑ rates, when the speed test ran, failed checks today) and the Settings card a "Network checks" switch (per-server opt-out); both live on the Network tab.
- **Role hints**. Under the role cards in Add server ("What should it do?") and on the server page ("What this server does") a few calm notes explain what a choice means for this kind of machine, at most two, risks first, each with an optional "Learn more" to the docs. Neutral by default; amber only where something would really go wrong. `App\Support\Servers\RoleHints::for(RoleHintContext)` is the one pure rule set (unit-tested); `App\Queries\ServerRoleHints` feeds it the machine (wizard tile or detected/picked device, battery), the roles, real size and architecture on the server page, and the team's other approved servers. The wizard gets every machine × role choice up front (`roleHints`, keyed `home:build,edge`), so switching cards needs no request; the server page gets `roleHints` for its current roles and refreshes with them. Rules:
  - *Serve traffic at home* (mini PC, tower, compact desktop, NAS, small board, laptop): it needs a public IP or ports 80/443 forwarded; most home setups build or run apps and let a cloud server take traffic.
  - *Build next to apps or traffic*: make sure the machine can build while serving; a separate build server keeps them apart. Amber when the real facts say it is small (under 2 GB memory or under 2 cores). Not shown for a lone server doing everything (the default).
  - *Laptop* (device or battery) running apps or traffic: apps stop when it sleeps; it makes a great build server.
  - *Architecture*: images are built for the platform they run on ([04](04-build-and-deploy.md) §5). An ARM build server (a small board, or arm64 facts) notes that the team's x86 servers need their own builder; a runtime server whose architecture no build server has gets an amber "No ARM build server yet".
  - *Only edge* (server page, other servers exist): all public traffic enters here; turn on Serve traffic elsewhere first, then move DNS.
  - *Registry at home* (server page, other servers exist): every server downloads new images from this machine, so deploys depend on its upload speed and uptime.
- **Server page tabs**. A server's page is the hero (device render with its LED, name, status, roles, specs), the approval callout when it waits, and a tab bar under them: **Overview · Metrics · Network · Settings** (a revoked server has no Metrics). Tabs are links, so they deep-link and work with back/forward: Overview is `/servers/{server}`, the others `/servers/{server}/{tab}` (`servers.tab`, `App\Enums\ServerTab`, other segments 404). `ServerController::show` computes only the props of the open tab: every tab gets `server`, `mesh`, `edge`, `replace`, `teamId`, `tab`; Overview adds `health`, `placement`, `roleHints`, `retiredVolumes`; Network `measureLinks`; Settings `placement`, `roleHints`, `retiredVolumes`, `canUpdateRoles`, `canConfirmVolumeDeletion`; `meshPeers` (24 h link quality, the heaviest query) is an Inertia deferred prop on Overview and Network, with skeletons until it lands. Switching keeps the scroll position and page state (the shared Hour/Day/Week range) and jumps back to the tab bar when you were further down. Usage and charts keep their one react-query with the `server.metrics` realtime nudge (polling without Reverb) on every tab.
  - *Overview*: Usage tiles, What runs here next to Health, then **At a glance**: four facts that each open the tab with the details (what it does → Settings, public traffic and private network → Network, the last report and version → Network), then attention items: retired volumes waiting for an OK (amber, → Settings) and the role hints.
  - *Metrics*: the charts ([15](15-observability.md) §2.4) with the range select in the section header; skeleton cards while loading, an empty state before the first samples.
  - *Network*: Public traffic (the edge facts; a non-edge says it doesn't serve traffic, with a link to turn on Serve traffic), Private network (mesh status right of the heading; the per-peer rows; "Turns on by itself when a second server joins" alone), **Capabilities** (D49, `Report.host.runtime`: "Docker"/"Rootless Docker" and whether Docker access is guarded, then one row per capability (Docker access, Public ports 80/443, Visitor addresses, Network isolation, Private network, Port detection) with the state as icon + word (Full / Limited / Unavailable) and the server's reason, a callout explaining what is limited when anything is not full, "Reported once the server checks in" before the first report; [11](11-installation-and-dev.md) §3.2), Connection (versions, desired state, hostname, platform, private address, approval, signing key).
  - *Settings*: What this server does (role cards + hints), Appearance (looks like, location; the hero's "Change" links here), Placement (production, previews, labels), Private network (network checks), Storage (retired volumes), Danger zone. One `UnsavedBar` covers the placement and network-check switches.
- **Spacing and the map.** The Servers page and a server's page use a 48 px section rhythm, 24 px between cards and 24 px card padding; the map's land dots use the `--map-land` token so they read in both themes ([design-system](design-system.md) §13.1, §13.9).


## 15. Console and Data tabs (D35)

Both are service-panel tabs ([03](03-daemon-protocol.md) §11 for the transport, [09](09-security.md) R33 for the rules). They appear only to members who hold the permission; everyone else doesn't see the tab at all (no locked teaser).

- **Console** (`…/s/{service}/console`, apps, workers and databases with a running replica). One calm surface: a header row with the **replica picker** (segmented chips "Replica 1 · fra-1", only running replicas; one replica = a plain line), the shell select (Automatic · sh · bash), and the one primary "Open console". Opening checks the Console permission (no password prompt, D60), then a quiet `LiveWait` ("Connecting to replica 1 on fra-1…") and the terminal: xterm.js filling the panel, Geist Mono 13 px, colours from the theme tokens (no neon, cursor in `--foreground`), 12 px inset on the recessed surface. Under it one status line: a green dot + "Connected · /bin/sh as the container's user · 4:12", idle hint after 12 minutes ("Ends in 3 minutes without input"), and a ghost "End session". When the session ends the terminal stays readable (dimmed) with one line why ("Session ended after 15 minutes without input") and "Open a new console". "This session is recorded" appears before connecting when the team records transcripts. Below: **Recent sessions** of this service (who, replica, when, duration, why it ended; owners/admins see everyone's, with End on open ones; "Recording" when there is one).
- **Data** (`…/s/{service}/data`, databases only). Two columns: the **schema sidebar** (220 px: schemas → tables/views with row estimates, a filter field; Redis/Valkey: a key pattern field and the scanned keys with type chips and "Load more") and the main area with a segmented **Browse · Query**. Browse shows the selected table (or key) in the **result grid**: sticky header, mono cells, NULL as a faint "NULL" chip, long cells cut with "…" and the full value in a popover, row numbers, Previous/Next pages of 50 ("Rows 51–100 of ~12 400"). Query: a mono editor (⌘↵ runs), the session's mode chip **Read-only** (default) with an "Allow writes" switch (confirm popover "Statements can change data in postgres for the rest of this session"), Run, and the result grid with "500 rows · 38 ms" or "3 rows affected" or the error in one calm line (no red box). History (this user's last 50 statements on this database, newest first, status dot, age, click to load) opens from a "History" button as a popover. Results are never cached in the browser beyond the open tab.
- Both tabs open their session when the user acts (never on tab visit), end it on tab change, panel close or page unload, and show the same ended state. "Connecting…" never stays: when the server can't start the session the tab says why in one line ("This image has no shell (looked for bash, ash and sh), so there is no console for it.", "The server refused to open it (dockerd-guard): …", "fra-1 didn't answer within 25 seconds…") with **Try again**; Recent sessions shows the same sentence. A reconnect replaces the previous session (docs/03 §11.1).
- The Console of a database starts with one quiet line: "To look at data or run queries, use the Data tab." (a link to the tab).

- **Temporary access (D61, D67, [09](09-security.md) R39).** The Console tab's open card has an outline **Connect via SSH** next to "Open console"; the Data tab's has **Temporary access** next to "Open data" (Postgres, Redis and Valkey; hidden where the server or engine can't do it); every placed volume has a ghost **Connect with SFTP** in its card footer (Settings → Volumes) and its row in Settings → Backups. Each opens the same dialog (`features/remote-access`, 640 px, full screen on phones):
  - **Header**: a 44 px icon tile (terminal, folder, database), the title and one quiet `MetaLine` of what it opens: service, environment, then the replica and server (SSH), the mount path and server (volume) or the engine (database).
  - **Start**: one card of rows: replica (several replicas only); **Sign in with** Public key (default once a key was used in this browser) or Password, as two radio tiles (SSH and volumes); **Who can connect** (address chips, prefilled with the address the dashboard sees, add and remove); **Allow changes** (volumes, off; on shows an amber "The service keeps running" callout) or **Allow writes** (databases, off); a database's volume shows "Opens read-only" with the pointer to Backups and Temporary access instead; **Ends after** as a segmented control (30m, 1h, 2h, 4h; "Or after 15 minutes without use"). Below the card: one sentence on what it is and the primary **Start access for 2 hours**.
  - **Open**: a session card: status word (amber spinner "Starting the endpoint" until the server reports the port, hollow signal dot "Waiting for your client", green dot "One client connected"), outline-red **End now**, two live countdowns in `stat` type ("Ends in 1:52:07", "Closes unused in 14:12") and a 2 px bar of the time left. Then the credentials card: Host, Port, User, Password (masked, reveal), Database, each a row with one-click copy; for a volume also "Folder: / is /app/data in the service" and "Saved as 1000:1000, the owner of the volume's top folder"; the key fingerprint when signed in with a key.   - **Ended**: a centred summary: "Access ended" (or "Ended by an owner or admin"), the reason when it isn't plain "Ended", that the port is closed (or the temporary user gone), how long it was open and how many connections, and **Start a new access**. **Not available**: a dashed recessed block with the reason (volume not created yet, the server doesn't announce it).
  - Owners and admins see others' open accesses under "Open for others" with End. The panel polls every 2 s while starting and 5 s while open; nothing needs Reverb.

## 16. Service settings: sidebar, pages, visual scaling

The service panel's Settings tab is a settings area of its own ([design-system.md](design-system.md) §13.9 "Service settings").

- **Full width.** Opening Settings expands the panel to full width (the width animates, `slow`); any other tab collapses it back to the remembered width. The expand toggle on Settings narrows it for this visit only (the settings switch to the phone layout below ~768 px of panel width).
- **Layout**: the shared `SettingsShell` (`components/settings/`) in client-side mode, the same look as `/settings` and project settings (§1).
- **Sidebar** (`components/settings/settings-nav.tsx`, groups from `features/service-settings/sections.ts`): every page is listed directly, with an icon, in groups with a small title (General; **Build & deploy**; **Network**; **Resources**; then Advanced and Danger zone untitled). There are no sub-menus, so every setting is one click away and the list scans at a glance. Phones and narrow panels show the same groups as lists of large rows with a one-line summary. Pages, per kind:
  - **General** (all): the service at a glance (one tile per area that matters: domain, build/source, replicas and where, private address or volume; each opens its page), then name (instant rename via the UnsavedBar) and slug.
  - **Build & deploy**: Source (repository + branch override / image / engine and versions), **Variables** (all), Build (apps only), Deploy (not databases).
  - **Network**: Domains (apps and images), Private network (everything that listens: not workers or crons), **Web firewall** (apps and images; mode tiles Off / Log only / Block, what Log only would have blocked with Turn on blocking, the last 7 days, stricter rules under Advanced, exceptions, Check this service; [22](22-security-center.md) §9.6). A group without pages for this kind is left out.
  - **Resources**: **Scaling** (all), **Volumes** (when there are volumes, or an app/image the user may change), **Backups** (databases and services with a volume), then untitled **Advanced** (read-only ids and containers) and **Danger zone** (when the user may update or delete).
- **Schedule** (cron services, under Build & deploy; D51): "Runs" On a schedule · Continuously; the schedule as one sentence ("Every weekday at 09:00") with the time zone and the next run; preset pills (Every 5 minutes, Every 15 minutes, Hourly, Every 6 hours, Daily at 03:00, Weekdays at 09:00, Weekly on Monday, Monthly on the 1st); the cron expression in mono with the five field names under it and live errors in the same words as the server; a time zone select (IANA, default the viewer's zone for a new schedule; teams have no time zone of their own); the next five runs in the schedule's zone with the viewer's time beside them when it differs. Saved as a staged change.
- **Advanced** starts with how the container starts (not for databases): Entrypoint as an argv list (one argument per row, numbered, add/remove; empty = the image's own) and Capabilities as switches, one row per entry of launchroomd's allow-list with what it allows in plain words ("Listen on ports below 1024 · NET_BIND_SERVICE"); then the read-only ids and containers. Every settings form sends the whole `deploy` group, so a page never resets fields another page owns.
- **Search** (`components/settings/settings-search.tsx`, index in `features/service-settings/settings-index.ts`): a field at the top of the sidebar (above the drill-down list on phones) finds single settings, not just pages. The index is one list of `{ target, label, hint, keywords, anchor, fallback }` (row titles plus the words people type: "healthcheck", "port", "dockerfile", "env", "replicas", "ssl/https/certificate", "volume/disk/storage", "cron/schedule/timezone" (a cron's Schedule page), "entrypoint", "capabilities/cap_add", "delete"), filtered by kind and permissions the same way as the sidebar. Every query word must start a word of the title, page or keywords; results replace the sidebar (or the drill-down list) while there is a query, grouped by page. Choosing one opens the page, scrolls the row to the middle, tints it briefly (signal-soft with a 2 px signal edge for rows, a soft halo for cards; fades over 700 ms, static under reduced motion) and focuses its control; a row that isn't drawn right now (the Dockerfile path while Railpack builds) falls back to its card, then the page top. "Variables"/"env", "import .env", "raw", "shared" find rows of the Variables page; "backup", "snapshot", "restore", "pitr", "import", "download" find the Backups page. Keyboard: `/` anywhere in settings or ⌘F/Ctrl+F while focus is in the panel focuses the field (on a phone page it goes back to the list first), ↑/↓ move, Enter opens, Esc clears and then leaves the field without closing the panel.
- **URL**: `/s/{service}/settings/{section}` (`general | source | variables | build | deploy | schedule | domains | networking | firewall | scaling | volumes | backups | advanced | danger`, `projects.services.section`); `/s/{service}/settings` is General on wide panels and the drill-down list on phones. Switching pages is a client-side Inertia visit (`router.push`), so it is instant, Back/Forward work and the page reloads on the right section. Keyboard: ↑/↓/Home/End move in the sidebar.
- **Pages stay mounted once visited**, so unsaved edits survive switching; the sidebar marks a page with unsaved edits with a signal dot, and only the open page shows its UnsavedBar (the panel's StagedBar shows otherwise).
- **Phones and narrow panels**: the sidebar becomes a drill-down list (large rows with an icon tile, label and one quiet line: "2 domains", "3 replicas · 1 CPU · 512 MB"); a page has a back row ("‹ Network").
- **Variables and Backups are settings pages** (they were panel tabs until the 2026-10 reshuffle): Variables under Build & deploy right after Source (what the service is made of), Backups under Resources after Volumes (its data). Both use the whole page width of the shell; Variables keeps its table, raw editor, import, paste-a-.env-anywhere (only while it is the open page) and `?add=NAME&value=` deep links (explained failures, ⌘K "Add variable to …", `g v`); Backups keeps protection, snapshots, restore, Move data, trend and history. Old tab links redirect (§1). Build links to Variables for "referenced in code but not set".
- **Staged vs instant**: domains (add, remove, www redirect, HSTS) apply right away through `ApplyDomainRoutes`; rename applies right away (shown as a staged change for the canvas); everything else (source branch, build, deploy, scaling, volumes, disable, remove) is staged and offered by the panel's StagedBar. Save buttons in the UnsavedBar say "Save for next deploy" where saving stages.
- **Domains**: one card per domain: hostname (open, copy), status pill (Live / Waiting for DNS / Needs attention / With the next deploy), then where a request goes as three steps, **DNS → HTTPS → Traffic** (DNS check result and when; certificate issued/pending/expiring/expired with the issuer and renewal date; which edge servers serve it); while DNS isn't there yet, the records to create with copy buttons per name and value (and the CNAME alternative for subdomains) and a live re-check every 20 s for five minutes (`POST …/verify?quiet=1`, no toast per check), then switch rows (www redirect, HSTS) and Remove behind a confirm popover. Under the cards, **Edge servers**: a title and one muted sentence (one edge: "A second server with the edge role keeps traffic flowing if it's down"; several: "These 3 answer for every domain here…"), then one tile per edge server (its device render with LED at its true 16:10 ratio in an 80 px recessed well, the name, its status), one column on phones, two or three side by side when the page is wider. **Add domain** is a guided dialog: the name with a live hint (root domain needs an A record / subdomain can use a CNAME / inside the platform domain needs nothing), then the records with a `LiveWait` that re-checks by itself until "You're all set".
- **Scaling**: the live picture first: "3 replicas · control plane, server-2" (or why it doesn't fit) over one card per runtime server: its device render with LED, the replicas standing on it as small service-logo tiles (dashed signal for ones the draft adds, hollow ghosts for ones it removes), CPU and memory bars against capacity (others' use grey, this service signal, amber only past the total) and the per-server rule (May run here / Only here / Never here). Every change asks the real scheduler (`POST …/s/{service}/scaling/preview`, read-only, 250 ms debounce; the saved state comes with the page). Then replicas (units + stepper), size per replica as sliders that end at the biggest eligible server, Spread/Pack as option cards with pictures, required labels as chips (suggestions from the servers' labels) and whether this environment's kind is allowed. Databases and services with a volume: one replica, pinned to the server with the data (the other servers are dimmed with "Its data lives on …"), with the way to move it (restore a backup elsewhere).
- **Volumes**: one card per volume: the server that holds it (device render with the volume standing on it; a dashed signal drive before the first deploy), the mount path (copy), size (from snapshots), backup protection (Protected / overdue / failing / not backed up, with when) and a link to Settings → Backups. **Add volume** is a guided dialog: where the app writes (framework suggestions such as `/app/storage` for Laravel, `/app/data` for SQLite), what changes (one replica, stays on one server, backed up as snapshots; amber when it scales down from several replicas), staged for the next deploy. The card's `⋯` menu (app and image services) has **Change mount path** (dialog with the path, "Save for next deploy") and **Remove volume** (consequences list, typed mount path, "Remove with next deploy"; a never-deployed volume goes at once without typing). The pill says In use / With the next deploy / Moves with the next deploy (plus "Running containers still use …") / Removed with the next deploy. Refusals (busy volume, nested path) show under the field. Database volumes have no menu and a line that launchroom manages them ([14](14-backup-and-restore.md) §9.12).
- **Source** (image services): the hero has **Change image** (dialog: reference, "A tag or a @sha256: digest from Docker Hub or GitHub Container Registry", Save for next deploy) and a row explaining that building from a repository means adding it as a new service ([04](04-build-and-deploy.md) §1).
- **Source / Build / Deploy / Networking / Advanced** use `SettingsCard` rows: an object hero first (repository with branch and root chips; image with its tag; the engine with its versions; the detected plan "Next.js 16 · npm · port 3000" with Detect again), the builder as option cards, every detected value as an `OverrideRow` ("Detected `npm ci`" + Override switch), the health check as a segmented HTTP/TCP/None with a live sentence ("Ready when GET /health answers 2xx within 3s"), a timeline and steppers, and the private address drawn as "Your other services → http://web:3000".

## 20. Move to another server and Move launchroom (D56, [14](14-backup-and-restore.md) §13)

- **Move to another server** (`/servers/{server}/move`, from the server page's danger zone; for the dashboard's server the link goes to Settings → Move launchroom): pick the target (device cards; **Add a new server** returns here), then the plan: "Moves without downtime" (stateless) and "Stops briefly" (each database or volume with engine, size, expected stop and which apps stop with it, a rebuild badge on an architecture change), the architecture callout, "becomes an edge" note, the DNS records to change (host, from the source's address to the target's, live check as icon + word), warnings, blockers (Start disabled), **Back up first** when a destination exists, the total downtime. Start asks for the source's name.
- **Progress** on the same page: done/total, one row per service (status icon + word, step message, copied size, attempts, **Retry** on failures), **Cancel** (services that already moved stay, the one being copied goes back), the DNS card, and once everything runs on the target **Retire <source>** with the name typed. It polls while the move runs.
- **Settings → Move launchroom** (instance owners): a stepper. 1 Prepare: pre-flight rows (this server, dashboard address, backups, app images, disk, private network, DNS TTL, recovery kit) and **Create move command**. 2 Connect: the one-time command with copy (valid 24 h), then the code and the new server's name, architecture and address; type the code to approve. 3 Move apps and data: the plan and then the same progress rows. 4 Hand over: the freeze explained, whether the new server is waiting, "hand over" typed; then the dump's progress and **Abort hand-over**. 5 Done: the new address.
- **After the move** the new dashboard shows the checklist on the same page: DNS (dashboard, apps wildcard, custom domains, live checks), images missing from the registry with **Rebuild now**, other servers reconnected, the old machine to delete, a new recovery kit, **Finish**.
- **Banner** (`instanceMove` shared prop): "launchroom is moving to a new server. Changes are paused for a few minutes." during the freeze; "launchroom moved to this server." with the checklist link for instance owners afterwards.
- **Moved page**: once the hand-over completed, every page of the old dashboard shows "launchroom moved" with the new address.
