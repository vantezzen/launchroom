# 08: Dashboard UX

The dashboard should feel like a managed deploy platform that runs on your own servers. How screens look and behave is in [design-system.md](design-system.md); the journeys are in [design/flows.md](design/flows.md).

## 1. Navigation

- **Sidebar**: one header row (the launchroom mark as an icon only, linking home with `aria-label` "launchroom home", then the team selector; on the icon rail they stack), a visible "Search ⌘K" field (the shortcut reads `Ctrl K` off Apple keyboards, `lib/platform.ts`, everywhere it is shown), Get started (instance owners, until complete), **Projects** (cards with live status), **Activity** (team feed, with the number of open alerts as a quiet count, shared prop `openAlertCount`), **Servers**, **Backups** (`/backups`, every team member; D95), **Analytics** (requests of every project, [15](15-observability.md) §5.4), **Security** (findings, web firewall, inventory and investigations; the number of vulnerabilities that need action as a badge, counted per advisory group like the Security hero, [22](22-security-center.md) §9), **Logs** (owners and admins, §12), **Settings** (a quiet dot when an update is ready, owners); in the footer **Docs**, the user menu and a muted "launchroom v0.1.0" line (shared prop `version` = `config('launchroom.version')`, from the root `VERSION` file; dev reports `<VERSION>-dev`), hidden on the icon rail. Counts stop at "99+". The team selector's second line says how the team's servers are, icon plus words ("2 servers online", "1 server down", "Disk almost full on fra-1", "No servers yet"; shared prop `fleet`, `App\Queries\ShellSignals`); people who can't see servers get their role there instead. The nav list is `features/app-shell/nav-items.ts`, which ⌘K's Navigate group shares.
- **Team menu**: the team's name and your role, the servers' line (opens Servers), every team and, for instance owners and team owners/admins, **Create team**: a small dialog (team name only) that creates the team with you as owner, switches to it and lands on its Projects (docs/09 R9).
- **Settings**: every settings surface (account, team and launchroom settings at `/settings/*`, project settings, the service panel's Settings tab, §16) uses one `SettingsShell` ([design-system.md](design-system.md) §13.9 "Settings shell"): a search field and a sidebar of titled groups with an icon per page beside one page (title, one sentence, cards); on phones the groups become cards of large rows with a one-line summary, and a page has an "All settings" back row. `/settings` groups: **Account** (Profile, Security: password, two-factor and passkeys, API tokens ([16](16-api-and-cli.md) §1.3), Appearance) · **Team** (Members, Git, Private registries, Notifications, Dockerfile generation; Backups moved to the sidebar, and `/settings/backups` redirects to `/backups`) · **This launchroom**, instance owners only (Updates with a dot when one is ready, Network, Dashboard domain, Registry, Security: server certificates and the audit log, Move launchroom). The sidebar's Settings goes to `/settings` (`settings.index`): Profile beside the sidebar on wide screens, the list on phones. Search finds the pages and their main rows (`features/settings/settings-index.ts`). The API reference is `/docs/api`; the CLI sign-in approval page `/cli/login?code=` is a signed-in page in the auth frame (no layout chrome).
- **Top bar**: every page has one 52 px top bar and renders in one `Page` container (`wide` 1280 / `narrow` 768 / `settings` 200 + 800 / `full`). Team pages: breadcrumb left, page-level secondary actions right (`TopBarActions`). On phones the launchroom mark replaces the sidebar toggle (it opens the navigation sheet with every page), a one-item breadcrumb is hidden because the page title says the same, and a fixed **bottom bar** (`features/app-shell/phone-nav.tsx`, below md) holds Projects (current on project pages too), Servers, Activity (open alerts as a count) and Search (opens ⌘K; the top bar has no second search button). It is 56 px plus the safe-area inset; the CSS variable `--phone-nav-h` (app.css, 0 on wider screens) pads page content, shortens full-bleed pages and lifts floating bars and toasts above it. Sheets and dialogs (z-50) cover it.
- **Project level**: the canvas is home. One top-bar row with `project ▾ / environment ▾`. Both switchers are small palettes (cmdk in a popover): type to filter, ↑↓ and ↵. The project menu has "Find project…", projects visited lately first (⌘K's Recent), then the rest, each with its status word and icon (production's, or the open environment's for the current project, the optional prop `projectStatuses` loaded when the menu opens), and ends with New project, All projects and Project activity. The environment switcher shows the open environment's rolled-up status after its name only when it needs you (failed, needs attention, not deployed; `environmentHealth`, refreshed on `canvas.changed`). Its menu lists each environment with its status icon (`environmentStatuses`, loaded when it opens), its branch and a quiet "Production" tag when production has another name, then the promotion hint, Compare & promote, New environment (opens settings → environments with the add dialog, `?add=environment`) and Manage environments; from 8 environments on it gets a filter field too. The same row holds the tabs inline as a segmented row (**Canvas · Deployments · Logs · Analytics · Previews · Settings**; a menu on narrow bars and phones; Deployments shows a progress ring while a deploy runs in the environment or ✕ when the latest one failed, with the words for screen readers; Previews shows its count) and the staged-changes pill right (hidden when nothing is staged, when the environment has no services, on Compare & promote, which lists the changes itself, and on a canvas with services, whose toolbar carries it; "3 new services · Deploy" before a first deploy; count only on phones). Adding a service is the canvas toolbar's Add ("Add a service" under the phone list). Deploy outcome toasts are mounted once by the project layout, so every project page announces "web is live" / "web failed to deploy". Project activity is in the project menu. Only the canvas and the Logs tab (`/p/{project}/{env}/logs`) are full-bleed; other project pages scroll like team pages.
- **Service level**: a route-backed right-side panel over the canvas, expandable to full page. Tabs: **Deployments · Logs · Settings** (+ **Console** with the permission, **Data** for databases with the permission; §15), then **Analytics ↗**, a link to the project's Analytics tab filtered to the service (Traffic for a service with a domain, else Resources; D75). The former Metrics tab (`/s/{service}/metrics`) redirects (301) there with its range. Variables and Backups are pages of Settings (§16); the old `/s/{service}/variables` and `/s/{service}/backups` URLs and `?tab=variables|backups` redirect (301) to them with their query (`?add=`, `?before=`).
- **Observe scope** (D74, `lib/observe-scope.ts`, `useObserveScope`): Logs, Analytics (both views) and Security share one time range and one service filter, kept in the URL (`?range=`, `?service=`, and from a chart or an alert an absolute `?from=&to=` in epoch seconds). Ranges have the same labels everywhere (15 min, Hour, Day, Week, Month) and every page opens on **Day** unless the URL says otherwise; a page snaps a range it doesn't have to its nearest one (Analytics has no hour, so `1h` shows the last 24 hours) and says so in one quiet line. The project tabs Logs and Analytics, Analytics' Traffic and Resources views and the service panel's Logs tab and Analytics link keep the scope, so last week's `web` in Resources stays last week's `web` in Traffic and in Logs. Links into these views are built in one place (`App\Support\Links`, `lib/links.ts`), never as hand-written paths.
- **Everything links to where it's shown**: chart markers open their deployment, a chart's bucket opens the logs of that moment, a log line links its deployment and server, a deployment opens its own runtime lines, open alerts show as an attention chip on the node, panel, server and project card they are about and link to their filtered view, and Analytics' Blocked tile opens Security for the same project or service.
- Page changes cross-fade with a 4 px settle (View Transitions); the sidebar and top bar stay still; reduced motion turns it off.

## 2. Routes

```
/                                     → /projects ("Needs you", recent deployments + project cards), or onboarding / recovery for instance owners
/projects
/p/{project}/{env}                     canvas
/p/{project}/{env}/s/{service}/{tab}   canvas + service panel
/p/{project}/{env}/s/{service}/settings/{section}   the panel's Settings tab on one page (§16)
/p/{project}/{env}/d/{deployment}      deployment detail (logs, timeline)
/p/{project}/{env}/changes             staged changes diff
/p/{project}/{env}/logs                log explorer (build and runtime lines, live tails; §12)
/p/{project}/{env}/analytics           Analytics → Traffic (requests, errors, blocked, paths; docs/15 §5.4)
/p/{project}/{env}/analytics/resources Analytics → Resources (CPU, memory, latency, bandwidth; docs/15 §2.3)
                                       (/p/{project}/{env}/metrics redirects here with its query, D75)
/p/{project}/promote?from=&to=         compare & promote between environments
/p/{project}/deployments               all deployments across environments, by day, grouped by commit
/p/{project}/activity                  the activity feed filtered to the project (§12)
/activity                              team activity feed (sidebar)
/analytics                             request analytics of every project (sidebar; drill-down to a project's Analytics tab, then a service via ?service=; docs/15 §5.4)
/logs                                  search the logs of every project (sidebar, owners and admins; §12)
/security                              findings, web firewall, inventory (sidebar; docs/22 §9); /security/findings/{finding}, /security/inventory?q=
/trace?t=                              request trace: paste a Launchroom-Trace header, see the request's path (log explorer toolbar, ⌘K; docs/23)
/backups                               what's protected, storage, recovery kit (sidebar; docs/14 §3; #setup, #setup-launchroom, #recovery-kit, #storage)
/p/{project}/settings/{section}        general | environments | previews | config-file | logs | danger
                                       (/p/{project}/settings: General on wide screens, the list on phones)
/p/{project}/previews                  pull request previews (status, URLs, data, expiry, approve, share links)
/servers  /servers/{server}
/servers/new?step=roles&machine=home   "Add a server" wizard (steps 1–2); step 3 is /servers/enrollments/{enrollment}?machine=
/servers/{server}/replace              "Replace server" wizard and its progress (docs/14 §5.3)
/recovery                              recovery-mode checklist after `install --restore` (instance owners)
/settings                              Profile on wide screens, the settings list on phones
/settings/{section}                    incl. network (/settings/backups redirects to /backups)
                                       (/settings/network; /servers/mesh and /servers/ingress redirect there)
```

Every view and tab has a URL, and log lines are anchorable (`#L42`). Use Wayfinder for typed route helpers.

**Speed on the main path (canvas → service panel → deployment).** One visible loading state at most from click to content; the only honest wait is log lines streaming in (frontend mechanics: [10](10-codebase-conventions.md) §3).
- **The panel opens from the canvas.** A click draws the panel at once from the node (logo, name, status, meta line, tabs) and the slide and logo morph start on the click; the panel's request (`only: ['panel']`) fills in the header actions (their row is reserved, so nothing shifts), the "Action needed" chip, Settings, Console and Data. The Deployments list loads in parallel with it (hovering a node starts both), and a deep link or any full visit of `/s/{service}/deployments` brings the list in the page (`deployments`, the same `ServiceDeploymentsData` the tab refetches from `…/-/services/{service}/deployments`). A failed request takes the drawn panel away again.
- **Tabs and close are client-side.** Deployments, Logs, Console and Data load their own data, so switching to them and closing the panel change only the URL and the prop (`router.push`); Settings asks the server for its page data.
- **The panel always opens on Deployments.** Clicking a node lands in the same place every time; a remembered last tab (tried in D74's round) made it hard to predict where you land. The node's hover icons (Deployments, Logs, Console, Settings), ⌘K and links open a specific tab directly.
- **The deployment page opens from the row.** Rows prefetch their page on hover (the expanded first row as soon as it appears); a click on a page that isn't loaded yet draws it at once from the row (header, overview, steps) and the server fills in the stage, the failure card, the related cards and the lines.
- **Switchers keep your page.** The environment switcher keeps Logs, Analytics (in its view) and Changes; the project switcher keeps Deployments, Previews, Activity, Settings (and its section), and Logs or Analytics (in its view) of the target's production environment. Everything else opens the target's canvas, linked straight to it (`ProjectLinkData.environmentId`, no `/p/{project}` redirect). Query strings stay behind.
- **Lifecycle actions are optimistic.** Stop, Start, Restart, Deploy, Redeploy and Roll back change the node and the header on the click ("Stopped", "Starting", "Restarting", "Queued"); Deploy, Redeploy and Roll back then open the new deployment. A failure puts everything back with one calm toast.

**Route rules (`routes/projects.php`).** `{env}` and `{service}` are public ids (`env_…`, `svc_…`), constrained by grammar (the route patterns come from each model's public-id prefix in `TeamScopedBindings`) so `/p/{project}/settings` and `/p/{project}/deployments` never match an environment; controllers check nested resources belong together (`RouteScope`, web and API alike). A service whose removal is staged still resolves (its panel, logs, deployments, console and backups work); changes to it (settings, variables, domains, volumes, firewall, Deploy/Restart/Stop/Start) answer 409 until the removal is applied or discarded. A service panel tab or settings page the service doesn't have (Backups without data, Data on an app) is a 404. **Previews**: the project tab lists pull requests (number, title, author, branch → base, head SHA, fork badge, status with reason, data strategy per database, URLs with a lock when protected, expiry) with Approve (fork PRs, `deployments.create`), Share (share-link dialog) and Canvas; Settings → Previews holds the preview settings, the CI bypass secret (shown once after generating) and the per-database "In previews" strategy with the clone source picker (latest backup sizes, size guard and production toggle reasons); preview environments are grouped under "Previews" in the environment switcher; a preview's canvas shows its pull request strip and "shared"/"cloned" badges on edges into such databases. Canvas positions save instantly via `PUT /p/{project}/{env}/layout`; the Connect popover previews through `GET …/connections/preview` (reference templates only, never values). Viewers of an environment canvas subscribe to the private channel `environments.{env id}` (`CanvasChanged`, a contentless nudge; the page reloads its props). The "We detected…" step of adding a repository calls `GET /p/{project}/plan-preview`, answered by `App\Services\Canvas\PlanPreviewer` (see §9). `DetectedPlanData::fromSummary()` turns a protocol `BuildSummary` (plan task result, `service_instances.plan.summary` or `deployments.plan.summary`) into the UI shape: framework display name, package manager and runtime with versions and their source, commands, port, health path, release command, preset decisions, build variables, variables referenced in code (and, for an existing service, the ones not defined), warnings and Railpack's plan JSON.

## 3. Key screens

Flow follow-ups (D60): sensitive actions use the current signed-in session without another password prompt. The sidebar footer links to Docs. Repository, template and Compose project creation offer **Create without deploying** beside **Create and deploy** so variables can be configured first. Deployment detail shows the assigned build server with its device illustration while building; durations tick every second independently of status updates. Settings → Network starts with **App domains**: the same picker as the address step of Get started (`AppsDomainPicker`: "Use my domain" / "Use a free address" tiles, the field, the wildcard record card with the server's public address, the live check every 10 s with the proxy states). Settings has nothing to continue to, so instead of Continue / Continue anyway it keeps checking, says that new apps already get addresses under the domain, and records the verification by itself once DNS turns green (`POST /onboarding/domain/confirm`); switching back to free addresses asks in a confirm popover. When the wildcard is proxied by Cloudflare, an amber callout explains that its free certificate covers one level and gives the fix (DNS only, or an advanced certificate per project with Full (strict)). Domain setup records wrap inside a scrollable dialog; the Domains page refreshes pending HTTPS certificates independently of the DNS check.

## 4. Interaction principles

- **Detected default + Override toggle** everywhere (Vercel build settings pattern).
- **Optimistic UI + undo toasts** for reversible actions. Type-to-confirm only for irreversible ones (delete a volume or database).
- **Realtime by default**: status, logs, staged counts and canvas updates over Reverb. Log lines are batched (100–200 ms).
- **⌘K command palette**: jump to project, service, deployment or server; per-service commands (Logs, Analytics, Open ↗, Redeploy, Restart, Variables, Data) and actions (roll back, add variable, switch environment); "Trace a request", and a pasted `Launchroom-Trace` header opens its trace; details in §8.
- **Keyboard shortcuts** (`features/command-palette/shortcuts.tsx`): `g` then a letter within a second: `g p` projects, `g s` servers, `g c` canvas, `g d` the project's deployments, `g l` the open service's Logs tab, `g a` its Analytics (Traffic with a domain, else Resources; without an open service: the environment's Logs and Analytics), `g m` the same Analytics filter on Resources (kept from before D75), `g v` the open service's Variables; `o` opens the open service's live URL; `/` focuses log and settings search; Shift+D reviews staged changes on the canvas; `?` opens a sheet listing them all. Shortcuts only navigate: nothing that changes a service (redeploy, restart, stop) is on a key; those confirm, in ⌘K too. Keys are ignored while typing or while a dialog is open.
- **Speak app, not container.** Docker vocabulary appears only under Advanced.
- **Honest about single points of failure**: calm badges with one-click fixes ([02](02-architecture.md) §5).
- **Empty states teach**: every empty list says what it is and offers the one action that fills it.
- **Live timers**: elapsed times of running work (deployments and their steps, the logs page, sessions, relative times like "12s ago", "Unreachable for 8 min") tick on one shared clock (`hooks/use-now.ts`: a single one-second interval per page, paused while the tab is hidden). `<Elapsed since until>` and `<Duration seconds>` (`components/elapsed.tsx`) render compact durations with tabular figures; a finished item shows its fixed duration and doesn't subscribe. Only the timer cell re-renders, never the page. Reduced motion stops animation, not the numbers.
- **Connection to launchroom** (`lib/connection.ts`, installed in `app.tsx`): while the dashboard restarts (an update, a move) the edge answers 502/503/504 or nothing. Instead of Inertia's error dialog per failed request, one non-blocking "Reconnecting to launchroom…" pill shows at the top (`ReconnectBanner`), background reloads (polls, realtime fallbacks, async partial reloads) pause, and `GET /up/version` (public, sessionless, `no-store`: the Inertia asset version) is probed with backoff (1 s doubling to 15 s). When it answers with a different build the page reloads fully; with the same build the banner goes and the page's props refresh. A 409 with `X-Inertia-Location` (asset version changed) always reloads fully, also for async visits, which Inertia itself skips. A 419 reloads (sign in again). Any other non-Inertia error page opens at most one dialog. JSON requests through Inertia's HTTP client report to the same state.
- **Heavy load notice**: when the control-plane server averaged ≥ 90 % CPU or ≥ 95 % memory over the last 5 minutes (at least 3 per-minute samples, `server_metric_samples` from Report.metrics; `App\Queries\ControlPlaneLoad`, cached 60 s), the `controlPlaneLoad` shared prop (`ControlPlaneLoadData`, only for users who may `update` that server) shows a calm card at the bottom of the sidebar: "Your launchroom server is under heavy load. The dashboard may be slow. Consider adding resources or a separate build server.", with links to the server page and the build-server docs. Hiding it lasts six hours in that browser.

## 8. Deployments, variables, staged changes, ⌘K

- **Pages** (project shell, `routes/deployments.php`): `/p/{project}/deployments` (filters `environment`, `service`, `status` incl. `in_progress`; grouped by commit), `/p/{project}/{env}/d/{deployment}` (detail), `/p/{project}/{env}/changes` (review). Deploy is `POST /p/{project}/{env}/deploy` (optional message) and lands on the project deployments; Discard is `POST …/changes/discard` with optional `paths[]`. Redeploy, rollback and cancel are `POST …/d/{deployment}/{redeploy|rollback|cancel}` and land on the new deployment. Redeploy creates a `manual` deployment of the environment's last applied revision (staged changes stay staged); cancel is only offered while queued or building (later steps already touch workloads).
- **Service panel Deployments and Settings → Variables** (`DeploymentsTab`, `VariablesSection`) and the staged-changes pill load JSON from `/p/{project}/{env}/-/…` (the `-` segment can't collide with page URLs) through TanStack Query; variable edits are JSON requests and invalidate the pill. The pill also refetches after every Inertia visit and on `canvas.changed`.
- **Realtime**: private channels `environments.{env}` (`.deployment.updated`, `.canvas.changed`), `deployments.{dpl}` (`.deployment.updated`, `.logs.appended`) and `members.{mem}` (the signed-in member's own channel, keyed by the membership's public id and shared as `realtime.member`: status changes of the deployments they started), authorized in `routes/channels.php`. Events carry ids and status only (a status change also carries the project id, service name and commit for the toasts); clients refetch through authorized endpoints. Log nudges are one per daemon log batch; the viewer coalesces them and fetches lines after its cursor at most every 200 ms. Without Reverb every subscription falls back to polling.
- **Logs**: `GET …/d/{deployment}/logs?after={chunk id}` returns up to 5,000 lines after the cursor, numbered in arrival order (stable `#L42`). A deployment's lines come from its tasks (plan → Plan, build → Build, run_once → Release), chunks shipped for the deployment (`step` names the section) and its workloads (Runtime logs). The first error line of a failed step is found by a display heuristic (error keywords, else the first stderr line).
- **Variables** (a settings page, §16): the rows that apply to this environment (environment-targeted, branch overrides, connection-owned), shared variables with "use in this service", and system variables. Above the table a count ("12 variables") and, past 8 rows, a search over keys and visible values. The Environments column only appears when some row reaches beyond the open environment, and then shows only the others ("Also staging"). Previews expand references like the resolver but mask every secret, including secrets embedded in config templates; broken references are listed per row. Secret values are never part of any list; Reveal is its own authorized and audited endpoint. Turning a secret into config requires the reveal permission. **Raw `.env` mode** shows secrets as `__LAUNCHROOM_SECRET_UNCHANGED__` (keeps the value); saving replaces this environment's rows: a changed row that also targets other environments is split, a missing key is removed from this environment only.
- **⌘K** (`/-/palette`, `App\Queries\CommandPalette`, `App\Queries\ServiceStatusIndex`): projects, environments, services, recent deployments and servers of the current team (team relations only; `viewAny` on projects). Services carry the status their node shows (`NodeStatusData`), the live hostname, the logo and the kind; projects the aggregate status. Statuses are production's, or for the project of `?environment=env_…` (the page's environment, when it is the team's and viewable) that environment's, and then only its services are listed. Names, statuses and addresses only, never variable values.
  - *Empty query inside a project*: the open service's commands first (with a panel open), then **Services in shop** with their status (failed and needs-attention first), then Recent, Actions, the project's pages (Canvas, Deployments, Logs, Analytics and Resources of all services, Previews, Project settings), Navigate (incl. "Keyboard shortcuts ?"), Projects (with status) and five recent deployments.
  - *Per-service commands*: Logs of api (`g l`), Analytics of api (`g a`, Traffic with a domain, else Resources), Open api.shop.dev ↗ (`o`, only with a domain), Redeploy and Restart (deploy permission; only when something was deployed, Restart not for a failed first deploy; both confirm inline), Variables of api (`g v`), Add variable (`?add=variable`, while typing), Data of postgres (databases, `QueryDatabases` permission). Typing "api logs" or "logs api" finds them for every service of the project (outside a project: of the team).
  - *Recent*: places visited lately, recorded from every Inertia visit (`recordVisit`, `localStorage` `launchroom.recent`, ids only: service panels, project canvases, deployments, servers), resolved against the index when shown (unknown or foreign ids drop out) without the page you're on; at most five.
- **Dev data**: `make artisan ARGS="db:seed --class=DeploymentsDemoSeeder"` (local only) seeds `acme-store` with deployment history, ANSI build logs, variables and staged changes.

## 9. Plan preview, build settings, onboarding, domains, deletion

- **Plan preview while adding a repository** (`PlanPreviewer`): the first call resolves the branch head (GitHub API) and creates a `plan` task (`BuildTasks::previewPlan`: default build settings, no variables, a throwaway `svc_` id, the project's production environment id; nothing is built or pushed). The task id is cached per (team, repository, branch, root directory) for 10 minutes, so polling looks it up instead of starting new tasks. Answers: `pending` (message "Waiting for a build server" / "Inspecting the repository on the server <name>"), `ready` with the detected plan, `failed` with the reason (missing branch, plan error, the task's error), or `unavailable` when no online server has the build role. Nothing stays pending forever: a task no build server leased within 2 minutes (since created or requeued) is cancelled and answered `failed` ("No build server picked up the detection…"), and a leased one past its deadline is answered `failed` ("Detection did not finish in time…") before the lease reaper fails it. `?retry=1` forgets a failed, cancelled or overdue task and starts a new one (a running one is kept). Both the add-service sheet and the import page use `usePlanPreview` (`features/add-service/use-plan-preview.ts`): poll every 2 s, stop after 3 minutes without an answer with "Detection is taking longer than expected", and show every failure with its reason and **Retry**; the sheet offers "Add without waiting" while pending or after the timeout.
- **Settings → Build**: the plan state line (`PlanStatusData`: planning / ready / failed, branch and commit, "Detect again" → `POST …/s/{service}/plan`), the detected plan with preset decisions as removable chips (stored as `build.disabledDecisions`, sent to plan and build tasks as `builder.disabledDecisions`), Override fields, "View plan JSON", and **Eject → `railpack.json`**: a client-side download of the effective settings (overrides, else detected values: `steps.install`, `steps.build`, `deploy.startCommand`, `provider`). While a plan runs, the panel reloads on `canvas.changed` (`RecordPlanResult` broadcasts it) and polls every 4 s as a fallback. `PlanService` is idempotent per (commit, build inputs) and cancels a pending plan for outdated settings.
- **Settings → General**: rename a service (`PATCH …/s/{service}/name`, project-wide, audited `service.renamed`); the slug never changes.
- **Backups on the canvas**: `CanvasNodeData.backup` (`BackupStatuses::forEnvironment`) renders as a second status line on database nodes and nodes of services with volumes ("Backed up 3 hours ago", hollow dot for none, ⚠ stale, ✕ failing). The service's Settings → Backups (`BackupsSection` around `ServiceBackups`): a protection card (status word, schedule sentence, Back up now; next backup · keeps · stored in), the snapshot timeline (six shown then "Show N older", each row with its own **Restore…**), the restore dialog with the option cards ("As a new service" default, "Into <service>" with a typed confirmation), a "ready" card after a restore as a new service and one History list of restores (with Swap in…) and the last five runs. A **Move data** section (`features/data-transfer/`, [14](14-backup-and-restore.md) §12.6) has **Import data…** (databases) / **Import files…** (per volume) and **Download now**; each snapshot row offers **Download**. Imports are a stepped sheet (source with a resumable upload or a connection URL with Check connection, target from an inspection with Replace everything / Replace contents / Merge and the apps that stop, review with "What will happen" and typed confirmation), runs show live steps and the outcome.
- **First run** (`/onboarding`, instance owners only, gate `manageInstance`): server connected (the control-plane server's status, address, server version), GitHub connected (an active installation of the team's app), platform domain (`apps_domain`, `PUT /onboarding/domain`, audited `instance.apps_domain_changed`; live wildcard check `POST /onboarding/domain/check`, see [05](05-networking-ingress.md) §5), backups (control-plane destination, passphrase and confirmed recovery kit), first project. Steps are derived from real state; the platform domain step is done once the owner continued after the DNS check (`POST /onboarding/domain/confirm`, `domainConfirmed`; domains set before this keep it done via a data migration). Skipping (GitHub, domain, backups) and dismissing are stored in `instance_settings.onboarding`. `/dashboard` (where `/` and sign-in land) redirects owners to the checklist until it is complete or dismissed, everyone else to the projects. The sidebar shows "Get started n/5" until every step is done or skipped (shared prop `onboardingProgress`). The server step polls every 5 s while launchroomd hasn't connected.
- **Domains** (Settings → Networking): see [05](05-networking-ingress.md) §5. Each custom domain shows its live DNS check, "Check DNS now", the records to create (A/AAAA to the edges, or a CNAME to the generated host for subdomains under the platform domain), the certificate state ("issued on the first request" until daemons report certificates) and the "Redirect www" switch; generated domains have a copy button.
- **Realtime in production**: Echo is configured from the `realtime` shared prop (`RealtimeConfigData`: Reverb app key plus optional `LAUNCHROOM_REALTIME_HOST/PORT/SCHEME`; signed-in users only, public values only). Empty values fall back to the build-time `VITE_REVERB_*` (local dev), then to the page's own origin (production proxies `/app/*` to Reverb). Echo is initialised before the first render and again by the app shell after an Inertia sign-in.
- **Deploy dialog**: fetches the summary with `?blockers=1` when it opens and lists broken references (Deploy disabled, link to the review page).
- **Project → Danger zone**: `DELETE /p/{project}` (typed project name; `DeleteProject`): refused while a backup or restore of one of its services runs; services with backups (databases and services with volumes; a successful run or an enabled schedule) get a **final backup** first and the project is deleted once it succeeded (a pending-deletion card shows the runs; a failure blocks it with "Retry final backup" / "Delete without final backup", owners/admins, audited; [14](14-backup-and-restore.md) §9.13); every instance is torn down through desired state (workloads leave the NodeState, edges re-render), then the rows are deleted; audited `project.deleted`. Volumes are retired (deleted after the retention period, [05](05-networking-ingress.md) §1.1) and snapshots stay in the destination. Environments (Settings → Environments → Delete) work the same way.
- **Viewers** see every new screen read-only: no chip removal, Detect again, DNS re-check, www switch, rename or delete; the checklist is not shown to non-owners.

- **Live logs follow restarts**: the live tail follows each replica across exits and restarts, with system lines at each exit and start; replicas of the live version that exited get their last lines too. Replicas without a normal tail are listed with the reason under Live (`LogTailStartedData.notes`: offline, not reachable, not running with its exit, never started, still starting).

- **Logs** (`/p/{project}/{env}/logs`, full-bleed): query bar (`service:`, `level:`, `deployment:`, `server:`, `stream:`, quoted text; `?q=` in the URL), range (15 min, Hour, Day, Week, Month; default Day, the observe scope of §1), **Live**; an absolute window (`?from=&to=`, from a chart's drill-down, an alert or a histogram bucket: clicking a bucket narrows the explorer to it) shows as a chip "14:00 to 15:00 ✕" before the range, turns Live off and clears back to the range; no source switch: build output (plan, build and release task lines) belongs to its deployment's Steps and never shows here, while rollout, health and container lifecycle events stay (the explorer asks for `source=runtime`, which is everything but build output; the API's `source=all|build` still exist); the histogram (errors stacked red, deploy markers, failed deploys red), "27 of 880 lines"; the filter rail with counts; the virtualised table (newest first; with Live it stays on the newest line at the top, scrolled down it keeps the reader's rows in place and offers "Jump to latest · N new"); selecting a line splits the lines' container into the list over a collapsible "Message" pane (the full line, JSON pretty-printed) and "Log details" on the right (in place of the list when the container is under 760 px, a sheet on phones) with facts in groups (Deployment links the deployment through `/d/{id}`, Server links the server page; `LogEntryData.serverId`), similar lines, "Only api" and "Only this deployment". `?service=` (id or slug) starts filtered. - **Log window**: `LogQueryData.from`/`to` (epoch seconds, both or neither; one alone is ignored) replace "the last `range`" with an absolute window, clamped to the last 30 days and to now and at least a minute long; chunks are read in `[from, to)` and the 60 buckets span the window. Deploy markers come from `App\Queries\DeployMarkers` (`DeployMarkerData` with `href`, the same markers as Analytics, the server pages and Security) for the window. With a window, each line's own time must be inside it too (`LogSearch::LINE_TIME`; chunks stored up to 5 minutes after the window are read, since a batch is stored after its lines), and the histogram bins lines by their own time, so the list, the count and the bars agree. Dragging across the histogram picks a window the same way; the window shows as a "10:00 to 10:04 ×" chip that replaces the range control until cleared.
- **Log search**: search runs on the server ([benchmark](notes/2026-10-log-search-benchmark.md)). `GET …/-/logs?q=` (`App\Queries\LogSearch`, the same `LogSearchQuery` language as the client: `service:`, `level:`, `deployment:`, `server:`, `stream:`, `environment:`, `project:`, `-` negates, quoted phrases, every term a case-insensitive literal substring) returns the newest 5,000 matching lines, `matches` (all matching lines of the range) and 60 `buckets` (every level, errors stacked; the level filter only narrows `matches`); typing searches after 300 ms. Scopes: the environment (the Logs tab, Live), **every environment of the project** ("production · All environments" switch on the Logs tab, `?scope=project`, `GET /p/{project}/-/logs`, View), and **the whole team** (sidebar **Logs**, `/logs`, `GET /logs/-/entries`, owners and admins: `TeamPolicy::searchLogs`). - **Trace a request** (D102, [23](23-request-trace.md)): an outline button in the toolbar of the project and team Logs opens a paste field for a `Launchroom-Trace` header and goes to `/trace?t=…`. The trace's "Open logs" comes back here with the request id as the query and a window of one minute either side.
- **Runtime log retention** (on for production, opt-in elsewhere; D41 amended): production environments keep runtime logs by default for 1 day and up to 256 MB (`Environment::PRODUCTION_LOG_DAYS`/`PRODUCTION_LOG_MAX_MB`; new production environments start with it, existing ones without a setting were switched on once). Project Settings → **Logs**, one card per persistent environment (previews keep live lines only): "Keep runtime logs" switch, Keep for (1 · 3 · 7 · 14 · 30 days, default 7), Up to (256 MB · 1 · 5 · 10 GB, default 1 GB), the stored size and since when in the footer, Save (`PATCH /p/{project}/{env}/log-retention`, `UpdateRuntimeLogRetention`, environment `update`, audited `environment.updated`). On, the environment's workloads get `shipLogs` in their NodeState (only on servers whose launchroomd announces the `shipLogs` feature; no restart) and launchroomd ships every line continuously ([03](03-daemon-protocol.md) §5). `launchroom:logs:prune` (every 15 min, `PruneRuntimeLogs`) deletes runtime chunks older than the period, then the oldest beyond the cap (bytes of the stored lines, uncompressed), and runtime lines of environments without retention (live tails) after 24 h (`LAUNCHROOM_LOG_TAIL_RETENTION_HOURS`). Build and deploy logs stay with their deployments. Retained lines live in the control plane's database, so they are part of control-plane backups.

## 14. Servers and fleet

- **Removing a pending server.** A server that was added but never connected (an unused enrolment) is removed from its card's ⋯ menu or its waiting page: `DELETE /servers/enrollments/{enrollment}` (`CancelEnrollment`, policy `ServerEnrollmentPolicy::delete`: ManageServers, unused, not the control plane's) deletes the enrolment row and with it the join token's hash, so the install command fails closed (`EnrollServer` finds no token); audited as `server.enrollment_canceled`. No password confirmation: it only takes access away. A server that connected but waits for approval is removed by revoking its key (the existing authorized revoke route); it then goes back to the fleet, and never-approved revoked servers are left out of the "Revoked" list. Enrolled servers keep Revoke and Replace unchanged.
- **One server is the default, not a risk.** `EdgeOverviewData.singlePointOfFailure` is only true when exactly one edge exists **and** other servers could take traffic too; with one server in total `singleServer` is true and the UI shows a gentle hint instead (the ghost card's "Use a second server to improve reliability", the topology's "One server does everything. Add another to share the work."). The project top bar badge, the Servers attention row and Settings → Network follow from the same flag ([02](02-architecture.md) §5).

- **Problems are sentences, raw text under Details.** Known problems map from the state that carries them to a product sentence and its consequence (`features/servers/problems.ts`): a mesh error (`MeshOverviewData.error`, always Headscale) → "launchroom can’t manage the private network right now. The service panel's Settings tab is a settings area of its own ([design-system.md](design-system.md) §13.9 "Service settings").

The expand toggle on Settings and Data narrows it for this visit only (the settings switch to the phone layout below ~768 px of panel width).
- **Layout**: the shared `SettingsShell` (`components/settings/`) in client-side mode, the same look as `/settings` and project settings (§1).
- **Sidebar** (`components/settings/settings-nav.tsx`, groups from `features/service-settings/sections.ts`): every page is listed directly, with an icon, in groups with a small title (General; **Build & deploy**; **Network**; **Resources**; then Advanced and Danger zone untitled). There are no sub-menus, so every setting is one click away and the list scans at a glance. Phones and narrow panels show the same groups as lists of large rows with a one-line summary. Pages, per kind:
  - **General** (all): the service at a glance (one tile per area that matters: domain, build/source, replicas and where, private address or volume; each opens its page), then name (instant rename via the UnsavedBar) and slug.
  - **Build & deploy**: Source (repository + branch override / image / engine and versions), **Variables** (all), Build (apps only), Deploy (not databases).

A group without pages for this kind is left out.
  - **Resources**: **Scaling** (all), **Volumes** (when there are volumes, or an app/image the user may change), **Backups** (databases and services with a volume), then untitled **Advanced** (read-only ids and containers) and **Danger zone** (when the user may update or delete).
- **Schedule** (cron services, under Build & deploy; D51): "Runs" On a schedule · Continuously; the schedule as one sentence ("Every weekday at 09:00") with the time zone and the next run; preset pills (Every 5 minutes, Every 15 minutes, Hourly, Every 6 hours, Daily at 03:00, Weekdays at 09:00, Weekly on Monday, Monthly on the 1st); then **Simple | Cron**: Simple builds the schedule from fields (every few minutes / hours at a minute / every day at a time with M T W T F S S weekday chips / every month on a day at a time) and shows the cron it writes as a preview; Cron is the expression in mono with the five field names under it and live errors in the same words as the server, and opens first when the stored expression doesn't fit the fields; a time zone select (IANA, default the viewer's zone for a new schedule; teams have no time zone of their own); the next five runs in the schedule's zone with the viewer's time beside them when it differs. Saved as a staged change.
- **Advanced** starts with how the container starts (not for databases): Entrypoint as an argv list (one argument per row, numbered, add/remove; empty = the image's own) and Capabilities as switches, one row per entry of launchroomd's allow-list with what it allows in plain words ("Listen on ports below 1024 · NET_BIND_SERVICE"); then the read-only ids and containers. Every settings form sends the whole `deploy` group, so a page never resets fields another page owns.
- **Deploy** (D89, G23, G30): the Health check card has **Restart when stuck** (switch + minutes 1–60, default 5; `healthcheck.restartAfterSeconds`, 0 = never; not for databases). The Rollout card has **Stop timeout** (seconds, "Follows launchroom's default until you change it": 10 s web, 30 s workers and crons or the framework's hint) and, when the service has volumes, **Two copies during a deploy** (`deploy.overlapOnVolumes`) with the sentence that otherwise the old version stops before the new one starts, with a short downtime.
- **Scaling warnings** (`ReplicaWarnings`): while the draft has more than one replica, the page lists what breaks with several copies: Laravel sessions or cache on `file`/`array` (or `SESSION_DRIVER` unset on Laravel 10), a worker running `schedule:work`, and multi-replica build warnings such as Next.js ISR (`isr-cache-warning`).

- **Build**: after the warnings, the plan's asks: "Needed before the first deploy" with "Add as a secret" (`?add=NAME&type=secret` on Variables), the SQLite warning, one-click volume chips and the framework variables line ([04](04-build-and-deploy.md) §4).

- **Search** (`components/settings/settings-search.tsx`, index in `features/service-settings/settings-index.ts`): a field at the top of the sidebar (above the drill-down list on phones) finds single settings, not just pages. The index is one list of `{ target, label, hint, keywords, anchor, fallback }` (row titles plus the words people type: "healthcheck", "port", "dockerfile", "env", "replicas", "ssl/https/certificate", "volume/disk/storage", "cron/schedule/timezone" (a cron's Schedule page), "entrypoint", "capabilities/cap_add", "delete"), filtered by kind and permissions the same way as the sidebar. Choosing one opens the page, scrolls the row to the middle, tints it briefly (signal-soft with a 2 px signal edge for rows, a soft halo for cards; fades over 700 ms, static under reduced motion) and focuses its control; a row that isn't drawn right now (the Dockerfile path while Railpack builds) falls back to its card, then the page top. Keyboard: `/` anywhere in settings or ⌘F/Ctrl+F while focus is in the panel focuses the field (on a phone page it goes back to the list first), ↑/↓ move, Enter opens, Esc clears and then leaves the field without closing the panel.

## 20. Move to another server and Move launchroom (D56, [14](14-backup-and-restore.md) §13)

- **Move to another server** (`/servers/{server}/move`, from the server page's danger zone; for the dashboard's server the link goes to Settings → Move launchroom): pick the target (device cards; **Add a new server** returns here), then the plan: "Moves without downtime" (stateless) and "Stops briefly" (each database or volume with engine, size, expected stop and which apps stop with it, a rebuild badge on an architecture change), the architecture callout, "becomes an edge" note, the DNS records to change (host, from the source's address to the target's, live check as icon + word), warnings, blockers (Start disabled), **Back up first** when a destination exists, the total downtime. Start asks for the source's name.
- **Progress** on the same page: a source → target strip first (both device cards, "N services left" / "N services here", a "Serving traffic" tag on whichever side takes public traffic, the current step on the arrow: "Copying postgres, 1.2 GB of 3.4 GB", "Everything moved"; Replace uses the same strip with the dead server greyed), then done/total, one row per service (status icon + word, step message, copied size, attempts, **Retry** on failures), **Cancel** (services that already moved stay, the one being copied goes back), the DNS card, and once everything runs on the target **Retire <source>** with the name typed. It polls while the move runs.
- **Settings → Move launchroom** (instance owners): a stepper. 1 Prepare: pre-flight rows (this server, dashboard address, backups, app images, disk, private network, DNS TTL, recovery kit) and **Create move command**. 2 Connect: the one-time command with copy (valid 24 h), then the code and the new server's name, architecture and address; type the code to approve. 3 Move apps and data: the plan and then the same progress rows. 4 Hand over: the freeze explained, whether the new server is waiting, "hand over" typed; then the dump's progress and **Abort hand-over**. 5 Done: the new address.
- **After the move** the new dashboard shows the checklist on the same page: DNS (dashboard, apps wildcard, custom domains, live checks), images missing from the registry with **Rebuild now**, other servers reconnected, the old machine to delete, a new recovery kit, **Finish**.
- **Banner** (`instanceMove` shared prop): "launchroom is moving to a new server. Changes are paused for a few minutes." during the freeze; "launchroom moved to this server." with the checklist link for instance owners afterwards.
- **Moved page**: once the hand-over completed, every page of the old dashboard shows "launchroom moved" with the new address.

## 21. Settings → System and Private registries

- **Settings → System** (`/settings/system`, `system.show`, `Gate::authorize('manageInstance')`, `pages/settings/system.tsx`, "This launchroom" group; D90): a summary pill, then one callout per check that needs a look with its `./launchroom doctor --fix …` command; service tiles from `servers.control_plane_health` (state, started, Docker restart count, OOM, readiness); "Restarted by launchroom" entries in words ("launchroom restarted Horizon at 14:02: its health check failed 3 times") and fallback notices (sent, or failed with the error); Background jobs (worker state, queues with waiting jobs, failed jobs of the last 24 h by class, never exception text, the scheduler beat and stale locks, "Job details" to Horizon for owners); Storage (disk meter, database size, cache memory, registry size); Protection (control-plane backup, dashboard certificate expiry); all checks; versions. Everything comes from `App\Queries\ControlPlaneHealth`; a probe that fails shows "unknown". The service tiles appear once the main server announces `watchdog`. The same checks are `php artisan launchroom:doctor --json`, the dashboard group of `./launchroom doctor` ([11](11-installation-and-dev.md) §2.3).
- **Settings → Private registries** (`/settings/registries`, team group, D91): one row per registry host with username, status and **Check**, Add, Edit and Remove. View with the team's view permission, change with `servers.manage`. The add dialog asks for a read-only token. What happens on deploy: [05](05-networking-ingress.md) §6.
- **Forgot password** (`pages/auth/forgot-password.tsx`): when mail isn't configured (`mailConfigured` false) the page shows `./launchroom reset-password you@example.com` instead of the form; while the prop is missing the form stays with a "No email arriving?" disclosure that shows the command.
