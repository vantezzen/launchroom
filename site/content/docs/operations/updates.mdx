---
title: Updates
description: One guided flow updates the control plane and then every server, with a backup first and an automatic rollback if anything fails.
---

**Settings → Updates** installs a new launchroom release in one flow. It takes a backup, updates the control plane, then rolls the new version out to your servers one at a time. If a step fails, launchroom puts the previous version back. Your apps keep running throughout.

<Screenshot id="updates" />

Updates are managed by instance owners.

## Update now

When a release is available, Settings → Updates shows **launchroom x.y.z is ready** with what's new, the three steps it will take, a link to the full release notes and **Update now**. The sidebar shows a dot on Updates too.

<Steps>
<Step>
### Backup

launchroom backs up the control plane (database, settings and keys) to your off-site backup destination before anything changes. If the backup fails, the update stops and nothing changes.
</Step>
<Step>
### Control plane

The control plane's launchroomd downloads the release bundle, verifies its signature, pulls every image **before** changing anything, then installs the new version. Database migrations run as the dashboard starts. The dashboard restarts during this step, and the page resumes when it's back.
</Step>
<Step>
### Servers

**Then update N servers, one at a time** is ticked by default. Once the new control plane runs, it updates the other servers one by one, with servers that serve traffic last. The rollout stops at the first failure, so a problem affects only one server.
</Step>
</Steps>

You can leave the page while it runs. The step list shows Queued, Backing up, Updating, Updated, Failed or Rolled back, with the latest progress line.

### Without an off-site backup

If you haven't set up a control-plane backup destination, the update dialog asks you to tick **Update without an off-site backup**. A local database dump is still taken on the control-plane server for the rollback, but there is no copy elsewhere. Set up a destination under [Backups](/docs/databases/backups) to make updates safer.

## When something fails

Every update can roll back:

- On the control plane, launchroom restores the previous configuration and the pre-update database dump and starts the old version again. Changes made in the dashboard during the update window are undone.
- On a server, the previous launchroomd configuration is restored and the old version restarted.

The Updates page then shows an amber card with what happened, step by step, and what to do:

| Outcome | What to do |
|---|---|
| Rolled back | Nothing to fix. You're on the previous version. **Try again** when you're ready, or wait for the next release |
| Backup failed | Nothing changed. Check Settings → Backups, then try again |
| Failed | Run `./launchroom status` on the control-plane server and keep the pre-update backup at hand. See [Troubleshooting](/docs/troubleshooting/install) |

If a server's update fails, the rollout stops and the Servers section explains which server went back to its previous version, with **Try again**.

## Server versions

The **Servers** section lists every server with its launchroomd version. Badges point out servers that are **Outdated** (older than the dashboard), **Newer than the dashboard**, or have an **Incompatible protocol**. The dashboard works with servers one protocol version behind, so servers can catch up gradually. **Update N servers** brings the rest to the dashboard's version.

Servers are updated only to the dashboard's own version. They are never updated past it or downgraded.

## Update channel

Under **How launchroom updates**, **Channel** is **Stable** or **Beta**. Beta includes pre-releases such as `0.1.0-rc.4`; Stable only offers final releases.

Until you pick one, launchroom chooses for you: an install made with `--unstable` is on Beta, and so is any instance that runs a pre-release. Everything else is on Stable. Pre-releases are ordered by their number, so `0.1.0-rc.10` comes after `0.1.0-rc.9`, and the final `0.1.0` after every `0.1.0-rc`.

## When the dashboard can't install a release

Once in a while a release can't be installed from Settings → Updates, for example when GitHub doesn't hand out the list of images that belongs to it. The page then says why and shows the installer command for exactly that release, with a copy button:

```sh title="On the control-plane server, in the folder that contains launchroom/"
curl -fsSL https://launchroom.vantezzen.io/install | sh -s -- --version 0.1.0-rc.4
```

Often it's temporary: **Check for updates** again a few minutes later. Otherwise run the command, see [Update manually](#update-manually) below.

After an update, by the dashboard or by hand, the page always reflects the version that runs now. A release you already have is never offered again.

## Automatic updates

Turn on **Install updates automatically** to have launchroom update itself at night. It's off by default. Automatic updates:

- Start only between **02:00 and 05:00** in the control-plane server's time zone (UTC if it can't tell).
- Need an off-site backup destination. Without one, the switch is disabled with a link to set one up.
- Run the same flow as Update now, backup first, servers included.
- Install only releases that haven't been tried before. A version that failed or was rolled back waits for a person.
- Don't start while something else is running or while launchroom is in recovery mode.

Turning automatic updates on or off is recorded in the audit log.

## Signed releases

Every release is signed with Sigstore's cosign, keylessly, from launchroom's release workflow on GitHub (`vantezzen/launchroom`, tags `v*` only). What gets verified:

- **The installers** (`install.sh` for the control plane, `server.sh` for servers) verify the release bundle's signature against the exact release identity for that version before running anything. A missing signature stops the install. An invalid signature always stops it.
- **launchroomd** pins the release identity when it is installed and never lets the dashboard change it. For each update it downloads the bundle itself, verifies the signature, the transparency log entry and the checksum, refuses any version that isn't strictly newer than its own, and takes every image digest from the verified bundle.
- **The update itself** is carried out by a short-lived helper that verifies the release once more, against a copy of the pin that launchroomd can't write. A compromised launchroomd therefore can't install a release of its choosing.
- **Images** are pinned by digest in the release, so what runs is what was signed.

## Update manually

Re-running the installer is the manual upgrade path. It keeps your `.env` and data and writes the new release's compose file and image pins.

```sh title="On the control-plane server, in the folder that contains launchroom/"
curl -fsSL https://launchroom.vantezzen.io/install | sh
```

Pass `-s -- --dir /path/to/launchroom` if you installed into another folder, and `--version x.y.z` to pick a specific release (both together: `sh -s -- --dir /path/to/launchroom --version x.y.z`). Without `--version` the installer takes the newest stable release; use `--version` for a pre-release. Run it as a user with access to Docker.

On the control plane, `./launchroom update` re-pulls the images already pinned in `.env` and restarts. It doesn't move to a new release.

<Callout type="warn" title="No backup or rollback by hand">
The manual path doesn't take a pre-update backup and doesn't roll back. Take a backup first (`./launchroom backup`) and prefer the guided flow when you can.
</Callout>

After updating the control plane by hand, update your servers from Settings → Updates.
